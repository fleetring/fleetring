# FR-094 (#144): one parent/child agent workflow on 0.8's online delegation

- **Date:** 2026-11-13
- **Build:** `release/0.8.0` at `744c07c` (`cargo build --release -p fleetringd`; the binary still reports `0.7.0`)
- **Scripts:** [`experiments/fr094/`](../../experiments/fr094/) (`workflow.py`, `measure.py`, `offline.py`, `router.py`, and the `harness.py` and `mcp_client.py` they share)
- **Decides:** which of ADR-0047 §9.6's deferred items come back after 0.8. The owner reads this and decides; the overview's "Deferred" list is updated from that decision.

## The answer, first

None of the five triggers fired. The online design carried the whole workflow. Issuance took 5 ms on the control node, every revocation took effect within a second, and no credential leaked. Every step that went wrong did so for a reason offline delegation wouldn't fix. When the control plane was down, the data path was down too: data nodes refuse every token once their denylist goes stale, and every client call starts with a `Locate` on the control plane. The real problems were in the CLI and MCP experience, listed under "Bugs and friction" below.

| Deferred item (ADR-0047 §9.1, §9.6) | Recommendation | Judged against |
|---|---|---|
| Offline biscuit delegation (`biscuit-auth`, templates, the custom verifier) | **Drop** from the deferred list for single-fleet use. Reopen it only together with a design in which data nodes serve without a fresh denylist. | Q1: did a child need a credential while the control plane was down but data nodes were up? No. With the control node killed, no child request succeeded, whatever its credential. |
| Higher limits, or offline issuance for throughput | **Keep deferred**; the limits stay as they are | Q4: issuance p95 is 41 ms end to end and 5.7 ms on the server. A workflow used at most 8 delegations, against 30 a minute per caller, 60 a minute per lineage, and 256 live. |
| Biscuit attenuation (narrowing locally in Python or TypeScript) | **Keep deferred** | Q3: the Python harness never needed to narrow a credential locally. It asked the control plane, with `agent delegate --scope`. |
| Holder keys, self-signed child certificates, `[tls] accept_holder_keys`, `Peer::HolderKey` | **Keep deferred**, with a sharper trigger (Q2 below) | Q2: every child ran beside its root's certificate. Under ADR-0048 the launcher delegates outside the sandbox, and a delegated JWT crosses the router (tested). But `db_create`, `db_fork` and `db_drop` don't cross the router. |
| Bearer self-delegation through the router | **Drop** as a separate item; it returns only as part of holder keys | Q5: a child's delegated JWT worked through the router with a libSQL-style Hrana client, and was refused there 13 ms after the parent revoked it. |
| `Revoked::Block`, revocation IDs, `token inspect` for biscuits | They follow biscuit delegation: **drop** with it | Q7: revocation by delegation ID and by principal was prompt and sufficient. |
| File-clone seeding | **Keep deferred** | Q6: forks of the agents' memory (220 KB) took 3.5 to 4.6 s, almost all of it fixed protocol steps, which file clones wouldn't shorten. A 341 MB database forked in 5.6 s. Only an 852 MB one passed 10 s (12.6 s). Each fork doubles its database's disk, by construction. |
| Ancestor-rule refinements | **None needed** | Q7: `agent remove` took 12 ms. A request was refused on the next call, and a stream ended within 0.81 s (dev node) or 1.66 s (on a separate data node). |

Question 8 found no leak. Every issued token's text was searched for in every transcript, every MCP server's stderr, every CLI capture, and every node log, 509 tokens across 9 runs, with no hit. Token IDs do appear, which the ticket allows.

## Setup

- **Machine.** Linux 6.18 under WSL2 on an x86-64 laptop: 32 threads, 46 GiB of RAM, ext4 on an NVMe disk.
- **Isolation.** Each run had its own `HOME`, and so its own `~/.fleetring`, contexts and agents directory. Each had its own loopback ports and its own dev node, started with `fleetring dev -d --port <p>`. No run touched the operator's own fleet or contexts.
- **Trusted local development.** Every agent ran as the same OS user, beside its root's certificate. Delegation narrows what a node accepts; it doesn't isolate processes. The harness itself read token files twice: for the leak check, and to play ADR-0048's credential proxy in the router test.
- **The harness.** `workflow.py` is a Python harness. It runs the CLI as subprocesses and speaks MCP over stdio to one `fleetring mcp --agent <id>` per agent, as Claude Code does. It writes every CLI call and every MCP request and result to a transcript. **The agents' reasoning is scripted:** a keyword triage of each issue's text stands in for a model. What the experiment measures is what a model-driven harness does identically: the CLI calls, the tool calls, their errors, their latency, and their round trips. No model ever saw a credential, because no MCP tool takes or returns one (ADR-0047 point 7).
- **Round trips** come from the node's `fleetring_rpc_requests_total` counters, scraped before and after each step. Their duration sums give the server-side latency of each call.
- **The task.** The ticket's: triage this repository's 8 open `flaky-test` issues (#85, #110, #120, #124, #159, #162, #166, #171; snapshot in `experiments/fr094/flaky-issues.json`) and propose a fix for each.

**A confound in this environment.** Under WSL2, the wall clock here runs fast and is stepped back about 2 s every 30 s (measured: steps of -2.06 s and -1.95 s within 60 s). Control time never goes backwards (`max(command time, State::now)`), so it stalls for about 2 s after each step. That's why a rate window reopened after about 64 s by the harness's clock, not 60. Log timestamps also go backwards in places. No safety property depended on it.

## The workflow

Root agent `42`, the parent, has its memory in `agent-42-memory` (tables `tasks`, `proposals` and `facts`) and works through its own MCP server. One run goes like this:

1. **Parent.** `agent add 42`; the parent creates its memory and writes the 8 tasks, assigning each to a child.
2. **Delegation, by the harness.** It runs `agent delegate 42.cN --ttl 20m` for N from 1 to 3, with the scopes `admin:agent-42.cN-*`, `stream:agent-42.cN-*` and `fork:agent-42-memory`. Child `42.c1` also gets `admin:agent-42.c1.*` and `grant:agent-42.c1.*`, so that it can delegate.
3. **Children, in parallel, each through `mcp --agent 42.cN`:**
   - `db_fork` of `agent-42-memory` into `agent-42.cN-memory`, and `db_create` of a scratch database that expires in an hour;
   - one `changes` call;
   - for each of its tasks, an upsert of a proposal and an update of the task's state;
   - five probes that must be refused: create `agent-42-evil`, write the parent's memory, read a sibling's memory, drop the parent's memory, and create `agent-43-memory`;
   - finally, dropping its scratch database.
4. **Grandchild.** `42.c1`'s harness runs `agent delegate 42.c1.r1 --ttl 10m`. The grandchild creates, writes and reads its own database, and is refused in its parent's prefix and when it tries to fork the root's memory. `42.c1` then removes it with `agent remove 42.c1.r1`, and drops the database it left behind.
5. **Renewal.** Once `42.c2` has forked, the parent runs `agent renew 42.c2` mid-task.
6. **Copy-back.** The parent reads each child's `proposals` and copies them into its own memory row by row, through `query` and `exec`. Then it drops each child's memory and runs `agent remove 42.cN`.
7. **An abandoned child.** `42.c4` writes to its inbox every 50 ms through MCP, with a `db watch` stream open on it. The parent removes it mid-task.
8. **A cancelled fork.** The parent forks a 64 MiB database with `--detach`, then runs `db drop` on the target while it is still `seeding`.
9. **The root removes itself.** A last child, `42.tail`, is working, with a stream open, when the root runs `agent remove 42`.

- **Run 1:** steps 1 to 9.
- **Run 2:** the same, plus the dev node stopped and restarted while the children worked. While the node was down, the harness also delegated a child (`42.late`).

Both runs completed end to end: 8 of 8 tasks done and 8 proposals copied back, and every probe refused.

## Measurements

### `DelegateToken` latency

There were 203 sequential delegations, 29 from each of 7 root agents, so that no rate limit applied.

| Measure | p50 | p95 | p99 | Max |
|---|---|---|---|---|
| `agent delegate`, the CLI's wall time | 37.5 ms | 41.5 ms | 56.5 ms | 63.3 ms |
| `DelegateToken` on the server (its duration metric) | 5.1 ms | 5.7 ms | 9.6 ms | 10.0 ms |
| Baseline: a CLI process that calls nothing | 4.5 ms | 4.9 ms | | |
| Baseline: a CLI process with one RPC (`db show`) | 6.8 ms | 7.2 ms | | |

The 30 ms the CLI spends beyond its one RPC is its own durability. `strace` shows 7 `fsync` calls of about 4.5 ms each: the CLI writes the `operation` file before it calls, then writes `token` and `identity.toml` after. This is the crash-safety ADR-0047 point 10 asks for, and it is cheap at this scale. In the workflows, delegations took 38 to 60 ms each.

### Fan-out until the limits refuse

`measure.py fanout` used root `fan`, with 8 threads running `agent delegate` at once.

| Phase | Result |
|---|---|
| The root bursts | 30 delegated in 0.29 s (about 104 a second). The 31st was refused: `too many delegations: at most 30 delegations a minute per caller`. |
| A minute later, 3 delegated children with `grant` burst at once, 30 each | 60 delegated in 0.47 s (20 each). Then: `at most 60 delegations a minute from a root lineage's delegated agents`. |
| Every minute, the root and the 3 children burst again | The 257th live delegation was refused in the third minute: `at most 256 live delegations per root lineage`. |
| Remove one grandchild, then delegate again | Accepted at once: the slot is freed immediately. |

A realistic fan-out comes nowhere near these limits. Each workflow run used 7 or 8 delegations in all, renewals included, all within one minute: 6 or 7 by the root, against its 30, and 1 by a child, against the lineage's 60. A harness that spawns tens of children a minute would meet the 30-a-minute limit, and would need to pace itself (F4).

### Forks: time and disk

Tiny forks of the agents' memory, 220 KB each:

| Situation | Time |
|---|---|
| A node up for more than 12 s, one fork | 3.5 to 4.6 s |
| Six forks at once | 4.0 to 6.1 s |
| Within 12 s of the control node starting: both workflow runs, and a fresh node in `try_forks` | 14.1 to 16.1 s |

**Why.** The node's log shows the copy itself takes about 25 ms. The rest is the fork's states, each advancing on the control node's 1 s cadence (seeded, first lease, fork-reset write, ready). In addition, `control/failover.rs` runs `drive_forks` only once `now > started + lease_duration + failover_margin`, which is 10 s + 2 s after the control node starts (F1).

By size (`measure.py forksize`: rows of `randomblob(4096)`, each spilling into an overflow page):

| Source `data.db` | Bytes the seeder ships | Copy | Seeded to fork-reset | Whole fork | Disk |
|---|---|---|---|---|---|
| 34 MB | 68 MB | 0.26 s | 1.15 s | **4.0 s** | doubles: the fork adds the source's whole footprint |
| 341 MB | 684 MB | 1.83 s | 2.66 s | **5.6 s** | doubles |
| 852 MB | 1.71 GB | 5.05 s | 5.19 s | **12.6 s** | doubles |

The seeder ships the WAL along with `data.db`, and the WAL is as large as the database (SQLite keeps the WAL file at its high-water mark), so the bytes copied are twice the database. On this disk, a fork passes 10 s somewhere between 341 MB and 852 MB.

**The cancelled fork** (64 MiB source, both runs): `db drop` 32 to 100 ms after `--detach`, while the fork was `seeding`. Each time the drop printed `cancelled the fork in progress`. Resuming with `--operation-id` then exited 1 with `operation … was cancelled before the fork was ready (dropped or expired)`. The node logged `deleted the fork's staged copies`, and `orphan list` was empty. (The run's disk total grew after the cancel. That growth was the source's own checkpoint, not a staged copy: once the source was dropped, the data directory went back to 496 KB.)

### The control plane unreachable, data nodes reachable (two-node fleet)

`offline.py` started a real, non-dev fleet on loopback: `ctl` (role `control`, with `cert issuer`) and `data1` (role `data`). Root `42` was minted with `agent add --authority`, and child `42.c1` with `agent delegate`. The child's database lived on `data1`. With a `db watch` stream open on `data1`, the control node was killed with `SIGKILL`:

| After the kill | What the child saw |
|---|---|
| Each new MCP call (sampled every 4 s, for 20 s) | `unavailable`, `Connection refused (os error 111)`, after 1.56 s of the client's retries. It never succeeded, since every call starts with a `Locate` on the control plane. |
| Each new CLI call | exit 4 after 1.57 s, with the hint `the fleet may be starting or failing over…` |
| The open stream on `data1` | ended about 4.5 s after the kill. The data node logged `ended a stream … reason="this node's token denylist is stale; retry"` (heartbeat timeout 5 s). `db watch` then kept retrying, with warnings, and never exited. |
| `agent delegate 42.c1.r1` | exit 4 after 6 sends in 7.8 s, keeping the operation ID for a resend that never records a second delegation |
| The control node restarted | the first MCP call succeeded 0.56 s later |

### The control node restarted mid-workflow (run 2, dev node)

- **The outage.** It lasted 5.4 s: `dev stop` drained for 1.6 s, 2 s passed, and `dev -d` took 0.12 s.
- **The children.** Each saw exactly one error, `unavailable` `Connection refused`, marked `retryable: true`. Each retried after 0.5 s and carried on. Their MCP servers survived, so no restart was needed.
- **Delegation during the outage.** `agent delegate 42.late`, started while the node was down, succeeded after 3.8 s through its own resends.
- **State.** The renewed `42.c2` token and every delegation record survived the restart.

## The answers

### 1. Did a child need a credential while the control plane was unreachable but data nodes were reachable?

**No, and it couldn't have used one.** With the control node killed:

- every new request from the child failed in about 1.6 s, because the MCP server and the CLI start every call with a `Locate`;
- the stream it already had open on the reachable data node ended about 4.5 s later, because a data node refuses every token once its denylist is older than the heartbeat timeout (ADR-0026 point 6), whoever minted the token;
- `agent delegate` failed cleanly and resumably.

An offline-minted credential would have met the same refusals. Restarting the control node mid-workflow cost each child one retryable error, and cost the delegation in flight a 3.8 s delay. Nothing useful was blocked that offline issuance would have unblocked.

**Recommendation:** drop offline biscuit delegation from the single-fleet deferred list. It can matter only if data nodes serve without a fresh denylist and without the control plane's placement. That would be a different availability design (cross-fleet, or edge), and it would carry its own ADR.

### 2. Did a child need to run on another machine, or in a sandbox without the root's certificate?

**Not in this workflow.** Every child ran beside its root's certificate, as 0.8 requires (ADR-0047 point 4.2). As for ADR-0048's launcher on OpenShell:

- **What works without holder keys.** The launcher, outside the sandbox, holds the root's certificate and runs `agent delegate`. The sandboxed agent's token is relay-carried through the router. The router test showed a delegated JWT working there: own database read and written; the parent's memory refused with `this token can't read database 'agent-42-memory'`; a forged signature refused with 401; revocation effective 13 ms after `agent remove`.
- **What doesn't.** The router relays only Hrana database sessions. In this workflow every child called `db_fork`, `db_create` and `db_drop` itself, which need a direct connection (ADR-0047's security analysis). They work under the launcher only if `fleetring mcp --agent <child>` runs **outside** the sandbox, as the credential proxy that ADR-0048's "direction, not a decision" describes. There it connects with the root's certificate.

**Recommendation:** keep holder keys and self-signed child certificates deferred, with this sharper trigger: bring them back if the launcher's design can't run the MCP server (or another credential proxy that makes control calls) outside the sandbox, so that sandboxed children would lose `db_fork`, `db_create` and `db_drop`; or if children must run on a machine the launcher doesn't control.

### 3. Did a workflow need to narrow a credential locally, in Python or TypeScript, without the CLI?

**No.** The harness is Python. Every narrowing was a `--scope` on `agent delegate`, answered in 5 ms on the server and about 40 ms end to end. The harness never wanted to derive a narrower token itself, and a model never sees a token to narrow. The only Python-side wish was a client library instead of a subprocess, which is a convenience, not attenuation.

**Recommendation:** keep biscuit attenuation deferred.

### 4. Did issuance latency or the limits get in the way at realistic fan-out?

**No.**

- **Latency:** p50 37.5 ms and p95 41.5 ms end to end; 5.1 ms and 5.7 ms on the server.
- **Use:** each workflow run used 7 or 8 delegations in all, all within one minute: 6 or 7 by the root and 1 by a child.
- **The limits, when pushed:** 30 in 0.29 s from the root, 60 in 0.47 s from three children, and 256 live reached in about 3 minutes. Revoking one child freed its slot at once.

**Recommendation:** keep offline delegation and higher limits deferred. Improve the refusal message instead (F4).

### 5. Did a child need a libSQL client through the router with its own credential?

**Not in the workflow,** which used MCP. When tried, a Hrana pipeline through `fleetring router` with the child's delegated JWT worked, and was refused after revocation.

**Recommendation:** drop bearer self-delegation as a separate item. It returns only if holder keys do.

### 6. Did fork seeding time or disk dominate the workflow?

**Not because of the bytes.**

- **Time.** Each child's fork took 14 to 16 s of its 19 s, but the memory was 220 KB and the copy took 25 ms. The rest was the fork's state machine (about 4 s) and the control node's 12 s settle window after it started (F1). File clones wouldn't shorten either.
- **The ticket's threshold.** "Forks of over 100 MiB took over 10 s": not met at 341 MB (5.6 s), met at 852 MB (12.6 s).
- **Disk.** A fork doubles its database's disk by construction, and copies twice the database's bytes, because the WAL goes too. On a copy-on-write filesystem, file clones would avoid both. For agents' memory and task databases, the disk was negligible.

**Recommendation:** keep file-clone seeding deferred. Two cheaper things would come first:

- truncate or leave out the WAL when seeding, which halves the bytes copied;
- let forks advance during the settle window (F1).

Reopen file clones when agent databases of several hundred MB are forked routinely.

### 7. Was revocation by the parent prompt and sufficient?

**Yes.**

- **Prompt.** `agent remove` takes 12 ms. Requests were refused on the next call, and streams ended within 0.81 s on the dev node and within 1.66 s on a separate data node.
- **Sufficient.** Removing a child ended its MCP server, its CLI and its stream. Removing the root ended its whole subtree: `42.tail`'s calls and its stream. `42.c1` removed its own grandchild under the ancestor rule.

What revocation doesn't do is clean up:

- the revoked agent's databases stay until someone with `admin` over them drops them;
- after `agent remove <root>`, the descendants' identity directories stay on disk (B4).

Neither calls for an ancestor-rule refinement.

**Recommendation:** no ancestor-rule changes. Consider an `agent remove --drop-databases`, and removing descendants' directories along with the root's (B4).

### 8. Did anything leak a credential into model context, logs, or the transcript?

**No.** The searches covered:

- the harness's transcripts (every CLI argument, stdout and stderr; every MCP request and result);
- every MCP server's stderr;
- every node's log;

for the full text, and the signature segment, of each token issued: 509 tokens across the 9 runs, with 0 hits. Token IDs appear 1,812 times (audit lines, `agent` output, revocation results), which the ticket allows. No MCP tool takes or returns a token. `mcp --agent <child>` names the parent, the owner and the expiry on stderr, never the token.

## Bugs and friction

None of these was filed as an issue: the experiment's instructions were not to post. Each is written to be filed as it stands, labelled `delegation` or `fork`.

**B1 (`delegation`): the help and `docs/cli.md` §16 show a command that fails.** `agent delegate --help` and cli.md's example give `fleetring --agent 42.c7 db create agent-42.c7-scratch`, but `--agent` is a subcommand flag. Steps: `fleetring agent add 42`, then `fleetring --agent 42 db list`, which prints `error: unexpected argument '--agent' found`. `fleetring db list --agent 42` works. Fix the example, or make `--agent` global.

**B2 (`delegation`): `agent renew <child>` breaks the child's running MCP server.**
- **What happens.** Renewing revokes the old delegation ID at once. `mcp --agent <child>` keeps the token it read at start, so every call fails with `unauthenticated: the token is revoked` until the server restarts. A model inside Claude Code can't restart its own MCP server, so a mid-task renewal ends the child's session. The hint blames expiry.
- **Steps.** Delegate `42.c1`; start `fleetring mcp --agent 42.c1` and make a call; run `fleetring agent renew 42.c1`. Every later call is refused, and a restarted server works.
- **Options.**
  - have the server re-read the token file when it changes, or once on `unauthenticated` (the same idea as ADR-0048's stable placeholders);
  - or give `renew` a grace period before it revokes the old token;
  - and in any case, word the hint for this case.

**B3 (`fork`, `delegation`): stale and wrong hints on CLI refusals.**
- A `ForkDatabase` refusal still says `until 0.8's fork action ships, forking needs admin on the source`, on a build that has the `fork` action.
- For an agent (`--agent`), the generic refusal hint suggests `--as`, `--token-file`, `--context` and `token issue`, which contradicts the skill. For a delegated agent, the useful hint is "ask your parent to delegate it with `--scope <action>:<db>`".

**B4 (`delegation`): `agent remove <root>` leaves its descendants' identities, and then misreports them.**
- **What happens.** After the root removes itself, `agent list` still shows its children with live-looking expiries. `agent remove <child>` refuses, and says that with `--no-revoke` "its token then stays valid until …". In fact the root's principal revocation already ended it.
- **Steps.** `agent add 42`; `agent delegate 42.c`; `agent remove 42 --yes`; `agent list`, which shows `42.c`; `agent remove 42.c --yes`.
- **Fix.** Remove the descendants' directories along with the root's, or say they are already revoked.

**B5 (`delegation`): renewing a child forgets its lifetime.** `agent delegate 42.c2 --ttl 20m` followed by `agent renew 42.c2` gives a 2-hour token, the default, and `agent renew` has no `--ttl`. A parent that keeps children short-lived on purpose loses that at the first renewal. Fix: record the requested lifetime and reuse it, or add `--ttl`.

**B6 (`delegation`): column misalignment.** `agent add` and `agent show` print `token expires2026-12-14T…`, because the label is wider than its column.

**B7 (`delegation`): inconsistent codes for a revoked token through the router.** Through the router, a revoked token is answered HTTP 200 with a stream error coded `PERMISSION_DENIED` ("the token is revoked"). A bad signature gets 401 `UNAUTHENTICATED`, and the same revoked token gets `UNAUTHENTICATED` over gRPC. A libSQL client would treat a revocation as a scope problem.

Friction, not bugs:

- **F1 (`fork`): forks stand still for 12 s after a control node starts.** `drive_forks` waits out `lease_duration + failover_margin` (10 s + 2 s), the window meant for promotions. A harness whose first `mcp --agent` start launches the dev node, and whose children fork at once, waits 14 to 16 s per fork instead of about 4 s. So does every fork after a control-node restart. Exempt forks from the window, or document it.
- **F2 (`fork`): a fork takes at least about 4 s, however small,** because its states advance on 1 s steps. Children that fork the parent's memory pay this each time.
- **F3 (`delegation`): revocation leaves databases.** `agent remove` doesn't drop `agent-<child>-*`. The parent must, and after the root removes itself only an operator with `fleet` can.
- **F4 (`delegation`): rate refusals don't say when to retry.** Every limit shares one hint, "revoking a delegated agent frees its slot; a rate limit reopens within a minute". A retry-after time would let a harness pace itself.
- **F5 (`delegation`): hints after a revocation suggest renewing or resuming,** which is wrong for an agent its parent revoked on purpose.
- **F6: every MCP data call makes a `Locate` round trip** to the control plane (no placement cache), so the control plane is on every request's path.
- **F7: a default grandchild loses `stream` silently.** `42.c1` held `admin` and `grant` over `agent-42.c1.*`, but not `stream`, so `agent delegate 42.c1.r1` gave only `admin:agent-42.c1.r1-*`. It is printed, but a harness has to know to grant `stream:agent-<child>.*` to a child that will have children.
- **F8: `fork` on a source also lets a child read the source's live data** (the lattice has `fork ⊇ read`), not only fork it. That's worth one line in the skill and in cli.md §16.
- **F9: `context add --tls-dir`** looks for `client.crt` and needs `--as admin`, even when the directory holds a single client certificate.

## Reproducing

Build first with `cargo build --release -p fleetringd`. Each script takes a fresh `--run-dir` and a free port, and touches nothing outside them.

```sh
cd experiments/fr094
python3 workflow.py --run-dir /tmp/fr094/run1 --port 7470
python3 workflow.py --run-dir /tmp/fr094/run2 --port 7570 --restart
python3 measure.py latency    --run-dir /tmp/fr094/latency    --port 7490
python3 measure.py fanout     --run-dir /tmp/fr094/fanout     --port 7500   # about 4 minutes
python3 measure.py revocation --run-dir /tmp/fr094/revocation --port 7520
python3 measure.py forksize   --run-dir /tmp/fr094/forksize   --port 7530   # about 5 GB of disk
python3 measure.py perchild   --run-dir /tmp/fr094/perchild   --port 7510
python3 offline.py --run-dir /tmp/fr094/offline --port 7600
python3 router.py  --run-dir /tmp/fr094/router  --port 7640
```

Each writes `result.json`, `transcript.jsonl`, and the captured stderr of every MCP server and stream into its run directory.
