# FR-097 (#147): a person forks a local database from the CLI alone

- **Date:** 2026-11-18
- **Build:** `release/0.8.0` at `aacdb21`, built and started by `experiments/fr097/kit.sh setup`
- **Kit:** [`experiments/fr097/`](../../experiments/fr097/): `TRIAL.md` gives the steps, `NOTES.md` the notes template, and `kit.sh` the isolated dev node, with `notes` (about 300 MiB of notes) and `archive` (about 1.5 GiB, notes plus attachments)
- **Trialist:** someone who didn't build forks, working only from `fleetring --help`, `docs/cli.md`, and the messages the CLI printed
- **Issues filed:** [FR-113 (#181)](https://github.com/fleetring/fleetring/issues/181), [FR-114 (#182)](https://github.com/fleetring/fleetring/issues/182), [FR-115 (#183)](https://github.com/fleetring/fleetring/issues/183), [FR-116 (#184)](https://github.com/fleetring/fleetring/issues/184), each labelled `fork` and `ux`

## The answer, first

The trialist's verdict was **"Looks good."** They forked a database, read its operation ID, its progress and its final state without help, and found nothing they couldn't work out. What confused them was around the edges: the help doesn't say that forks exist or that a fork's target is a new name (FR-113), an operation ID is printed for a request that is refused at once, under gRPC's generic wording (FR-114), the Ctrl-C message lands on the spinner's line (FR-115), and retrying a fork that had finished says only that the name exists (FR-116).

The trial covered less than the ticket asks. Steps 1 and 4 were run in part, and step 5's `orphan list`. **Not recorded:** the schema change and the check that the source was unchanged (step 2), `db list` (step 3), cancelling a fork, resuming a cancelled operation, and the conflict message for a changed argument (step 4), whether disk space came back (step 5), the failure on purpose (step 6), and the words section of the notes. This page reports nothing for those, and #147's acceptance criteria are not met: the steps above still need a run.

## Step 2: experiment on the fork

```text
$ fleetring db fork --min-replicas 2 foo bar
operation 15ft4he8h7z22w8y9x7bpjfna6: wait for it again with --operation-id 15ft4he8h7z22w8y9x7bpjfna6
fleetring: Client specified an invalid argument: min_replicas 2 is above the replication factor 1
```

The trialist: "Makes sense." The refusal itself was understood. What it shows is FR-114: the operation line invites a wait for an operation that never started, and the message opens with gRPC's generic "Client specified an invalid argument".

## Step 4: cancel and retry

The trialist pressed Ctrl-C while `bar` was seeding. The message was printed on the end of the spinner's line (shown here as it appeared):

```text
⠂ seeding bar from foo: attempt 1 of 5, seeder dev, holders 0 of 1        operation 0z09bgf5j3k69sj9bh9p9rzepb: the fork carries on. resume with `fleetring db fork foo bar --operation-id 0z09bgf5j3k69sj9bh9p9rzepb`. The operation ID is kept for 7 days after the fork finishes; after that, this command starts a new fork.
  to cancel it: fleetring db drop bar
```

That is FR-115, which also covers the lowercase "resume" after a full stop. They then ran the same command again, without `--operation-id`:

```text
$ fleetring db fork foo bar
operation 66710wg7t27w31fca97zj0twbq: wait for it again with --operation-id 66710wg7t27w31fca97zj0twbq
fleetring: Some entity that we attempted to create already exists: database 'bar' already exists
  hint: `fleetring db show bar` shows what holds the name, or pick another name
```

The fork had finished in the meantime. The refusal says only that the name is taken, so the trialist had to run `db show bar` to learn that it was their own fork, ready (FR-116). The new operation ID printed for a refused request is FR-114 again.

`db show bar` answered step 3's question, where the fork came from and whether it is usable, though the trialist didn't write down whether they read it that way:

```text
fork: ready, since 2026-11-18T00:50:06.328Z
forked from: foo (incarnation ca1da57cab3b913d) at 000000003309008f7a6c1a83000000003cea1700, chain hash 6423046d523af77ca63657f7c57aa87e4f5b9f06736a1095d090fc6d379506ab
fork operation: 0z09bgf5j3k69sj9bh9p9rzepb, requested by admin at 2026-11-18T00:49:56.79Z
```

By these timestamps, `bar` became ready about 9.5 s after it was requested.

## The words

- **`ready`, the operation ID, and the progress line** needed no explanation: the trialist read them cold and called them clear. The docs use them as the CLI prints them, and FR-095 makes the agent skill and the lexicon match: a fork is usable only once it is `ready`.
- **"The fork carries on"** is the CLI's phrase after Ctrl-C and after `--timeout`, and it held: the fork finished on its own after the trialist's Ctrl-C. `docs/cli.md` §15 and the lexicon's *operation ID* now quote it.
- **`seeded` and `opening`.** The notes never show `opening`: a spinner keeps only its latest line, and none was captured at that moment. Whether `opening` needs explaining is untested.
- **Cancellation** was never tried, so its wording is untested.

The notes' own words section was left empty.

## The fixes, ranked

The notes mark none as blocking. A suggested order, by how far each one could mislead someone about what happened:

1. **FR-116 (#184):** a retry on a name its own fork holds says only `already exists`, so the reader can't tell their fork succeeded without another command.
2. **FR-114 (#182):** an operation ID printed for a request refused at once invites a wait for nothing; and gRPC's preambles ("Client specified an invalid argument", "Some entity that we attempted to create already exists") come before the message that names the problem.
3. **FR-113 (#181):** `fleetring -h` describes `db` without forks, and `db fork -h` doesn't say that `TARGET_NAME` is a new database's name.
4. **FR-115 (#183):** the Ctrl-C message is printed on the spinner's line, with "resume" in lowercase after a full stop.

The owner decides which, if any, block 0.8.0.
