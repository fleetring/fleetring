# ADR-0049: sqlite-vec 0.1.9 is compiled into fleetringd and registered on every connection of the SQLite adapter

- **Status:** Proposed
- **Date:** 2026-11-20
- **Related:** ADR-0009 (toolchain and lints), ADR-0015 (point 7: FFI in its own crate), ADR-0016 (frame source), ADR-0021 (engine-changing migrations), ADR-0024 (logical change capture), ADR-0026 (point 8: statement confinement), ADR-0029 (archives), ADR-0041 (agent kit, schema), ADR-0045 (`db watch`); GHSA-353r-2q3f-g5wc; tickets FR-069 (#75), FR-040 (#53)

## Context

Agents need vector search for retrieval and memory. SQLite has no vector type. The usual answer, sqlite-vec, is a run-time loadable extension, and loading extensions is exactly what statement confinement refuses: `load_extension` is denied by the authorizer and extension loading is off on every connection, since GHSA-353r-2q3f-g5wc (0.2.0). That stays.

The facts that shape the decision:

- **sqlite-vec 0.1.9** (2026-03-31) is the latest stable release. Its `vec0` virtual table does exact, brute-force k-nearest-neighbour search over float32, int8, and bit vectors, with metadata columns filtered inside the search, partition keys, and auxiliary columns. The approximate (ANN) indexes exist only in the 0.1.10 alphas, which are unmaintained. Upstream has had no commits since 2026-05-18.
- **vec0 is SQLite storage.** A `vec0` table keeps everything in ordinary shadow tables of the same database (`<t>_info`, `_chunks`, `_rowids`, `_auxiliary`, `_metadatachunksNN`, `_metadatatextNN`, `_vector_chunksNN`), written through SQL and incremental blob I/O. Their pages are WAL frames like any other, so the frame source (ADR-0016) ships them, archives (ADR-0029) keep them, and a restore or a promoted follower has them, with no code of the adapter's own.
- **Shadow tables and SQLite.** SQLite recognizes a shadow table by the virtual table named before its *last* `_` and the module's `xShadowName`. 0.1.9's `xShadowName` lists every shadow table but `_vector_chunksNN` (the line naming them is commented out), and those names have a second `_` anyway. So SQLite knows the vector chunk tables as ordinary tables, at least whenever it reads the schema afresh. Defensive mode then doesn't protect them, `pragma_table_list` reports them as tables, and the change recorder (ADR-0024), which watches every ordinary table, would capture each chunk's whole blob, `chunk_size × dimensions × 4` bytes (6 MiB for 1,024 vectors of 1,536 floats), on every write.
- **The workspace forbids `unsafe_code`** (ADR-0009). Registering a statically linked extension means one call to its C entry point; ADR-0015, point 7, says FFI an engine adapter needs lives in its own crate that opts out explicitly.
- **Not built by the cross jobs.** The i686, s390x, and wasm32-wasip1 jobs build `fleetring`, `fleetring-control`, `fleetring-wal`, and `fleetring-wal-sqlite-tests`, not `fleetringd`. Every target that builds the daemon (Linux x86_64 and arm64, macOS on both architectures, Windows MSVC) is little-endian.

## Decision

1. **sqlite-vec 0.1.9 is compiled into the binary.** The `sqlite-vec` crate, pinned `=0.1.9`, builds the release's `sqlite-vec.c` with `cc` and `SQLITE_CORE`, so it calls the SQLite that rusqlite bundles directly. A new crate, `fleetring-sqlite-vec`, holds the one call into it: `register(&Connection)` calls `sqlite3_vec_init` on that connection. It is the workspace's only crate with `unsafe_code` merely denied rather than forbidden, with the call under `#[expect(unsafe_code, reason)]` and `// SAFETY:` comments; it knows nothing of fleetringd. It needs rusqlite's toolchain, 1.89, so the 1.88 MSRV check excludes it and the 1.89 check names it.

2. **Registered per connection, by the SQLite adapter alone.** The adapter registers it on every connection it opens (the primary's writer and reader, and a follower's checkpoint connection) right after turning on defensive mode and before any statement, rather than through `sqlite3_auto_extension`, which would reach every connection in the process. `sqlite3_vec_init` registers `vec0`, `vec_each`, and the scalar functions (`vec_f32`, `vec_int8`, `vec_bit`, `vec_distance_l2`, `_l1`, `_cosine`, `_hamming`, `vec_length`, `vec_to_json`, `vec_normalize`, `vec_slice`, `vec_add`, `vec_sub`, `vec_quantize_*`, `vec_type`, `vec_version`). The NumPy readers (`vec_npy_file`, `vec_npy_each`), the only code in sqlite-vec that opens files, have an entry point of their own that is never called. Nothing above the adapter learns about vectors (ADR-0021's engine neutrality): no API, protocol, control state, or CLI change.

3. **Confinement widens by nothing; it narrows twice.** Statement confinement never refused virtual tables or functions by module, so `CREATE VIRTUAL TABLE … USING vec0`, its internal statements on its shadow tables, and its functions need no new allowance. FTS5 keeps working as before. Every existing refusal stands, `load_extension` included. Two refusals are added:
   1. **A virtual table in `temp`** (`CREATE VIRTUAL TABLE temp.v …`) is refused as a temporary object. SQLite reports no temporary form of the action, only the schema's name. vec0 and FTS5 tables in `temp` were already refused through their shadow tables, which are temporary tables; a module without shadow tables, such as `dbstat`, wasn't, and could shadow a main table's name for every caller of the shared connection.
   2. **A user statement can't create, write, alter, drop, index, or put a trigger on a table whose name ends in `_vector_chunks` and two digits.** Defensive mode already refuses direct writes to every other vec0 shadow table, as to FTS5's. For the vector chunk tables the authorizer refuses them while SQLite prepares the user statement itself, a trigger body it fires included. vec0's own statements on them are prepared while the user's statement steps, never while it is prepared, so they still run: inserts, updates, deletes, and `DROP TABLE` of the vec0 table work. Reading shadow tables stays allowed: they hold only the user's own data. Because such a name can't be created, every table that has one is vec0's.
   3. **Reserved names** need nothing new: a vec0 table named into `_fleetring_` is refused by name, and one whose shadow tables would land there (a table named `_fleetring`) fails when vec0 creates them under the confinement, leaving nothing behind.

4. **Change streams record nothing for vec0 writes.** As for every virtual table (FTS5 included, since ADR-0024's FR-039 fix), the vec0 table carries no triggers and its shadow tables are skipped: those SQLite reports as shadow tables by type, the vector chunk tables of a virtual table by name. A transaction's rows on ordinary tables are recorded as before; a transaction that wrote only vec0 records no rows. The pattern that keeps a change stream meaningful, documented in the daemon README and the agent skill, is the FTS5 external-content one: keep the source row, embedding included as its float32 blob, in an ordinary table, and keep the vec0 table in step with a trigger, so a consumer receives the embedding and can rebuild its own index. The schema call (ADR-0041, point 6) lists the vec0 table as a virtual table and hides all its shadow tables unless `--all`, as for FTS5.

5. **Upgrades of vec0's on-disk format are deliberate, and gated.** The format is vec0's shadow tables, and every vec0 table records the sqlite-vec version that created it in its `_info` table (`CREATE_VERSION`). The dependency is pinned exactly, so a version moves only in a change that says so. Before a new version ships: its release notes and diff of `xCreate`, `xConnect`, and `xShadowName` are reviewed for format changes; it must open and query, read and write, tables created by the version before (a test creates a table with the old shape and checks it); and `fleetring-sqlite-vec`'s test that pins which shadow tables SQLite recognizes must be re-read, since a release that fixes `xShadowName` changes what the adapter's name rule covers. A version that changes the format incompatibly needs a new ADR that supersedes this point, with a migration path: vec0 tables are derived data, so rebuilding one from its source table (point 4's pattern) is the expected migration. Followers never run sqlite-vec while they mirror, only when promoted, so during a rolling upgrade a node of either version can open the file; a version that could not read the other's tables would make that upgrade unsafe, and is exactly what the review refuses.

6. **Determinism and platform scope.** Stored vectors are the bytes vec0 writes: float32 in the host's byte order, which on every target the daemon ships for is little-endian, so replicas and archives are byte-identical across them. A big-endian build of the daemon would read those blobs wrongly; none is built, and supporting one would need a byte-order decision first. Distances are computed in C at query time; they may differ in the last bits between architectures (fused multiply-add), so two replicas on different architectures could order exact ties differently. Placement determinism (ADR-0002, ADR-0003) doesn't cover query results, and queries run on the primary alone.

## Alternatives considered

- **Keep refusing vector search; tell agents to use FTS5 or compute distances client-side.** Retrieval is the main memory pattern for agents; brute-force distance over blobs in application code is slow and moves the data out.
- **Allow `load_extension` for an allowlisted path.** Reopens GHSA-353r-2q3f-g5wc's class of attack (a path, a writable directory, an entry point) for a fixed, known extension. Static linking has no file to swap.
- **`sqlite3_auto_extension`.** One call, but process-wide: every connection in the process, the control log's and tests' included, would get the module. Per-connection registration says exactly which connections have it.
- **Vendor `sqlite-vec.c` and patch `xShadowName`.** Tried: SQLite's last-`_` rule still misses `_vector_chunksNN` whenever it reads the schema afresh, so the patch can't make the vector chunk tables reliably shadow tables. The adapter's name rule (point 3.2) does, with the release's source unchanged and checked by Cargo's lock.
- **Capture the vec0 table's logical rows.** Virtual tables can't carry triggers. Capturing would need the adapter to decode vec0's chunk format, coupling it to that format (point 5) for data the source-table pattern already carries.
- **Capture the shadow tables.** Their rows are the module's storage: whole chunk blobs per write, meaningless to a consumer.
- **sqlite.ai's sqlite-vector** (Apache-2.0 since 2026-09-10). Maintained, with quantized and approximate search, but a younger format and API; it is the first fallback if sqlite-vec stays unmaintained (Consequences).
- **Turso's native vectors through FR-040 (#53).** Turso stores vectors natively (`F32_BLOB`, `vector_distance_cos`, DiskANN indexes) with no extension at all. It arrives with the Turso engine, not the SQLite adapter, and an engine-changing migration (ADR-0021) moves a database there; vec0 tables would be rebuilt as Turso vector columns from their source tables. sqlite-vec doesn't block that path.

## Consequences

- `SELECT vec_version()` returns `v0.1.9` on every node; `vec0` tables replicate, archive, restore, and fail over like any table, which the replication, restore, and change-stream tests show.
- **New C code parses input.** sqlite-vec parses query text (JSON vectors, `vec0` column definitions, `MATCH` arguments) and stored blobs (chunks, validity bitmaps, metadata) in C, inside the daemon. A memory-safety bug there is a bug in the daemon. SECURITY.md's threat model says so. Mitigations: only `register` runs it; its shadow tables can't be written by statements (point 3), so the blobs it reads are ones it wrote; it checks the size of each chunk blob before reading it; and the file readers are never registered.
- **Maintenance risk.** Upstream is dormant since 2026-05-18. If it stays so and a security fix is needed, the fallbacks, in order: carry the fix in a patched copy under `fleetring-sqlite-vec` (the release is one C file); move to sqlite.ai's sqlite-vector, rebuilding vec0 tables from their source tables; or move vector workloads to Turso's native vectors through FR-040 (#53).
- **Quirks users see:** `rows_affected` counts the rows vec0 writes to its shadow tables, as it counts rows triggers write, so it overstates a write to a vec0 table; `ALTER TABLE … RENAME` of a vec0 table isn't supported by 0.1.9 (it has no `xRename`) and leaves its shadow tables behind; a copy restored offline and opened with a stock `sqlite3` needs sqlite-vec 0.1.9 loaded to query its vec0 tables, and every other table reads as usual.
- **Owner decisions** (this ADR is Proposed until they are made): point 3.2, refusing direct writes to vector chunk tables and the creation of tables so named, is the safe default, against allowing them as an ordinary table's writes; point 4, recording nothing for vec0 writes and documenting the source-table pattern, is the default, against capturing logical rows (Alternatives).
- Follow-up: an upgrade of sqlite-vec follows point 5; `rows_affected` excluding virtual tables' internal writes is a possible ticket.
