# ADR-0040: The Raft control group screens commands on its leader against the log it will commit, owns its storage and wire formats, and draws openraft's randomness from an injected generator (amends ADR-0035)

- **Status:** Proposed
- **Date:** 2026-11-04
- **Related:** ADR-0035 (amends points 1, 3, 4, 5, 7, 8, 9, 11, 13, 14, and 15), ADR-0017, ADR-0018, ADR-0020, ADR-0022, ADR-0026, ADR-0031, ADR-0034, ADR-0038, ADR-0039; tickets FR-064

## Context

ADR-0035 was accepted on 2026-11-03, before the work it plans had started. Since then 0.4.0 shipped with ADR-0038 (version compatibility and upgrades), ADR-0039 (dev mode), and ADR-0034's metrics and readiness checks. ADR-0035 doesn't account for them, and checking it against the code on `main` turns up these gaps:

- **The single writer now screens commands before it logs them.** `commit_group` in `crates/fleetringd/src/control/node.rs` refuses a command that needs a fleet feature some member lacks, and a join refused for its release line or a missing feature, against a preview of the state the commands queued before it leave (`State::check_admission`), and logs nothing for a refused one. Without the screen, a control node rolled back to an older release would replay a logged join it would accept although the fleet refused it (ADR-0038, amendment). ADR-0035 point 3 stamps and hands every command to `client_write`, so a refused join would reach the log again. Under Raft only the leader proposes, many proposals are in flight at once, and leadership can move between screening a command and appending it.
- **A control group mixes two release lines during a rolling upgrade.** ADR-0038 lets a fleet run two adjacent lines, and voters are upgraded one at a time. ADR-0035 stores openraft's own serde forms in `control.db` and sends them on the wire, so the formats belong to openraft's release, not to FleetRing's: the openraft 0.10 upgrade would change both, inside a group that must keep working while it is mixed.
- **The feature gate can't see control-only nodes.** `State::check_feature` asks every fleet *member*. A node with `role = "control"` isn't a member, yet under Raft it decodes and applies every command. A lagging voter on the previous line could be handed a command it can't decode.
- **Rollback.** ADR-0038 promises that a downgrade within the window works until a new command is first used, and `fleetringd upgrade --rollback` checks features only. ADR-0035 makes the first start of the Raft release migrate `control.db` to format 2, which 0.4 can't read, and tells operators to restore a backup instead. A backup restored after the control plane committed anything can reissue lease epochs that data nodes have already seen.
- **The logs to migrate are 0.4.0's.** ADR-0035 point 5 migrates "a 0.3 log". 0.4.0 shipped, so the Raft release (0.5) meets format-1 files written by 0.4.0, often begun by 0.3.0 (an upgrade never skips a line). They hold joins and heartbeats with and without software, `Undrain`, the `undrain` feature enabled in state, and `Leave`s from `fleetringd node remove`.
- **openraft.** The newest stable release is 0.9.25 (2026-07-28); 0.10 is at `0.10.0-alpha.37`, after 37 alphas since February 2026 that changed its storage, network, and runtime traits. ADR-0035 point 15 draws every host's election timeouts from one thread-local generator, so a crash on one host shifts every other host's draws, and it isn't the per-host injected generator ADR-0020 point 2 asks for.
- **Dev mode, `node remove`, and the admin listener.** ADR-0039 runs one node with both roles on loopback, and says nothing in the daemon branches on dev mode except validation and one status field. `fleetringd node remove` takes a dead member out of the fleet, but a dead control voter would still count toward the group's quorums. ADR-0034's readiness check `leader` "gets its meaning from FR-064", and its metrics name the single writer.
- **A one-voter group restarts slowly.** openraft makes a restarted single voter wait an election timeout, up to 2 s by default, before it elects itself. Today a restarted control node serves at once, and dev mode starts in about a second.
- **The protocol's minor version.** ADR-0038 took 1.1, so the version the owner gave FR-064 (2026-11-03) is gone.

ADR-0035 is accepted, and accepted decisions are amended, not rewritten (`docs/adr/README.md`). This record amends it. Points of ADR-0035 it doesn't mention stand as written. Where this record replaces a point, the replacement is stated in full.

## Decision

1. **openraft is pinned to `=0.9.25`, without its `serde` feature, behind one runtime type in every build.** (Replaces the dependency and `AsyncRuntime` rows of ADR-0035 point 1, and the randomness of point 15.)
   - **The version.** 0.9.25 is the newest stable release, it builds with `fleetringd`'s MSRV (1.89), and its storage-v2 traits (`RaftLogStorage`, `RaftStateMachine`) and network traits are the ones ADR-0035 planned for. The 0.10 alphas are not a base for a control plane. Moving to 0.10 is its own ticket, and changes neither the disk nor the wire format (point 3). Without the `serde` feature, openraft's types can't be serialized at all, so the compiler keeps them off the disk and the wire.
   - **One runtime, `ControlRuntime`.** It implements openraft's `AsyncRuntime`. Its timers, instants, timeouts, and one-shot channels are `TokioRuntime`'s, so openraft reads time only from `tokio::time`: turmoil's simulated clock under simulation, paused time in tests, the real clock in production. Its `spawn` wraps the future in the spawning task's generator scope, a `tokio::task_local!` holding `Arc<Mutex<SplitMix64>>`. Its `ThreadLocalRng` is a zero-sized handle whose `next_u64` draws from the generator in scope. Every task openraft spawns goes through `AsyncRuntime::spawn`, so it inherits the generator of the `ControlNode::open` that created the `Raft`. The generator is the harness's SplitMix64 (`sim/rng.rs`), moved to a module both use, so a seed replays after any dependency upgrade.
   - **Where the seed comes from (ADR-0020 point 2).** The environment injects it. Under simulation it is the run's seed mixed with the XXH3-64 of the host's name, so each control host has its own stream and a crash on one host doesn't shift another's elections. In production it is eight bytes from `ring`'s `SystemRandom`, read once when the control node opens. No `cfg(feature = "simulation")` picks a different runtime. A draw outside any scope, which would be a bug, uses a generator seeded with the node's Raft ID, logs an error once, and fails a test that watches for it.
   - **This is verified against 0.9.25.** Its `AsyncRuntime` declares `type ThreadLocalRng: rand::Rng` and `fn thread_rng()`. Its only randomness is `Config::new_rand_election_timeout`, which calls `thread_rng()`. It spawns only through `AsyncRuntime::spawn` and reads time only through the runtime's `Instant`; the one exception, `SystemTime` in a display helper, formats log lines and decides nothing. Its core loop's `select!` is `biased`. The replication loop's unbiased `select!` uses Tokio's scheduler RNG, which turmoil seeds under `--cfg tokio_unstable`, as it seeds every other `select!` in the daemon. A scratch crate on 0.9.25 implemented this runtime: the same seed gave the same election timeouts across a spawned task, and another seed gave others. The plan's first phase repeats the check as a test.

2. **The leader screens each command against the state its own log will reach, and every proposal carries the leader ID it was screened under.** (Replaces the submit path of ADR-0035 point 3; group commit stays.)
   - **One proposer per control node** takes over the single writer's place. It accepts submissions only while this node leads a term *and* is *ready*: its state machine has applied an entry of that term. openraft appends a blank entry when a leader takes over, so once the leader has applied an entry of its own term, it has applied every entry its log held at takeover, the previous leader's uncommitted entries included, since its blank entry commits them. Before it is ready, a submission is answered `UNAVAILABLE` with "the control leader is catching up; retry" and the leader hint. This is the answer to a new leader that has applied less than the old one proposed. The new leader holds every committed entry, and may hold uncommitted ones. It screens nothing until it has applied all of them. Entries the old leader proposed that the new leader lacks were never committed and never acknowledged, and openraft answers their submitters `ForwardToLeader` when it truncates them.
   - **The screening state.** When the proposer becomes ready in term T, it clones the applied state into S. It takes submissions one at a time, in arrival order:
     1. It stamps the command with the clock (point 6).
     2. If the action needs screening (a join, or an action with a feature), it checks `S.check_admission(&action)` and the group gate (point 4). A refusal is answered `SubmitError::Refused`; nothing is proposed, and S doesn't change.
     3. Otherwise it applies the command to S with `apply`, rejected or not, so S stays exactly the state after the proposals so far.
     4. It hands the entry to `Raft::client_write_ff`, which returns once openraft has queued the entry on its ordered request channel, so entries reach the log in the order they were screened.
     5. It waits for the entry's responder off its own path, so proposals pipeline and openraft batches their appends into one `append` call, with one sync.
   - **The leader ID travels in the entry.** A proposal is a `ControlRequest { screened: LeaderRef { term, node }, command }`, with `command` stored and sent as raw JSON (`serde_json::value::RawValue`). The state machine applies the command only when the entry's own log ID carries the same leader ID. Otherwise it skips the entry without decoding the command, answers `Superseded`, and changes nothing, deterministically on every node and in every replay. The check exists because openraft 0.9 can refuse proposal *i* while this node briefly isn't leader, win a later term, and then read proposal *i + 1* from its queue and append it in the new term, although *i + 1* was screened assuming *i*. With the check the screen is exact. In term T, the leader's log is its log at takeover followed by its own term-T proposals, in order, which is exactly what S applied. By Raft's log-matching property, a term-T entry commits only together with every term-T entry before it. A superseded submitter gets `UNAVAILABLE`, "retry"; nothing happened. Keeping the command undecoded means a voter never decodes a command it won't apply.
   - **S is dropped** when the node stops leading T, and when its state machine applies an entry from another leader after it became ready. Submissions waiting for a responder keep waiting. openraft answers each one when the entry is applied, whichever node led when it committed, or `ForwardToLeader` when the entry is truncated, which means it never took effect. Only a deadline that expires first leaves the outcome unknown, as a timeout does today.
   - **`apply` doesn't change.** It still refuses what `check_admission` refuses, so anything that reached the log by a bug is rejected the same way everywhere. The screen exists so that an older release never meets a refused command in a log it replays (ADR-0038 point 4). `fleetring-control` doesn't change, and its replay tests stay as they are.
   - The read path is ADR-0035 point 6's: reads call `ensure_linearizable` on the leader, and the service's binding checks (ADR-0031 point 2) read the node's applied state. A per-epoch fact never changes once given, so an applied state that lags can only refuse a call that a retry then admits.

3. **FleetRing owns `control.db` format 2 and the Raft wire format; openraft's types reach neither.** (Replaces the encodings of ADR-0035 points 4, 8, and 9; the tables, transactions, and RPCs stay.)
   - **Raft IDs are text.** Raft IDs (ADR-0035 point 2) are written as 16 lowercase hex digits wherever they are stored or sent. They are 64-bit unsigned, SQLite's integers are signed, and JSON readers other than serde lose precision above 2^53.
   - **The log.** `log(log_index INTEGER PRIMARY KEY, term INTEGER NOT NULL, leader_node TEXT NOT NULL, kind TEXT NOT NULL CHECK (kind IN ('command', 'membership', 'blank')), payload TEXT NOT NULL) STRICT`.
     - A command's payload is `{"screened": {"term": <u64>, "node": "<hex>"}, "command": <Command>}`, where `<Command>` is the same JSON format 1 stores, so `fleetring-control`'s serde tests keep covering the log.
     - A membership's payload is `{"configs": [["<hex>", …], …], "nodes": {"<hex>": {"node_id": "…", "address": "…"}}}`: one config, or two during joint consensus.
     - A blank entry's payload is `{}`.
   - **`meta` and `snapshots`.** `meta` keeps `format` (`2`) and `genesis`, and adds:
     - `vote`: `{"term", "node", "committed"}`;
     - `committed` and `purged`: `{"term", "node", "index"}`.

     `snapshots(log_index, term, leader_node, membership, state)` stores a membership as above and `state` as format 1 stores it.
   - **The wire.** `RaftPayload { bytes json = 1; Software sender = 2; uint64 sent_at_ms = 3; }`. `json` holds FleetRing's wire structs for openraft's requests and replies (`AppendEntries`, `Vote`, `InstallSnapshot`, and the replies with their conflict, higher-vote, and partial-success cases). Entries in them use the encoding above. `sender` is the sending node's software (point 4); `sent_at_ms` is its clock reading (point 6).
   - **Conversion.** One module, `control/raft/codec.rs`, converts between the two type families. Golden JSON vectors for every message, entry kind, vote, and snapshot form are checked in, and are append-only, like placement's (ADR-0008).
   - **Changing the formats.** Readers ignore unknown fields, so an additive change mixes within the window. A change that isn't additive needs a new protocol minor version, and a release keeps reading and writing the previous line's form until every group member reports the new one.
   - **Why.** A rolling upgrade runs two lines in one group, so the bytes voters exchange and store must be FleetRing's to keep. openraft 0.10 then changes code, not `control.db`. The log stays readable in the `sqlite3` shell, and the simulation's replay check reads it without openraft.

4. **The feature gate and the release window cover the control group as well as the fleet's members.** (New; extends ADR-0038 points 3 and 4 and ADR-0035 points 11 and 14.)
   - **Where a group member's software comes from.** Every `RaftPayload`, request or reply, carries its sender's `Software`. The leader keeps the last software it heard from each member of its group, in memory. A new leader starts with none, and hears from every reachable member within one Raft heartbeat.
   - **The first use of a feature needs the whole group.** A command that needs a feature not yet enabled is refused before it is logged unless every voter's and learner's software is known and supports the feature. The refusal is `Rejection::FeatureUnsupported`, naming the control node and its release, or "control node '<id>' hasn't reported its software yet" while a member is unknown. A down member blocks the first use until it returns or is removed, as a down fleet member does (ADR-0038, Consequences).
   - **The window counts control nodes.** A join is refused before it is logged when its release line can't run beside a group member's (`Rejection::IncompatibleVersion`, naming the control node). This screen refuses more than `apply` does, which is safe: `apply` never sees a refused command.
   - **`control add` probes before it adds.** A new RPC, `Raft.Probe`, returns the target's node ID, its software, and whether its store holds any Raft state. `AddControlNode` refuses the target before calling `add_learner` when:
     - its node ID isn't the one named;
     - its store isn't empty, which stops a node started with the default `bootstrap = "new"` from bringing its own group in;
     - its release is outside the window with any fleet member or group member;
     - it lacks an enabled feature;
     - it has no `Raft` service. A 0.4 node answers `UNIMPLEMENTED`, refused as "node '<id>' runs fleetringd <version>, which has no control group".

     Once a feature is enabled, `upgrade` keeps refusing a release that lacks it (ADR-0038 point 4), on control nodes as on data nodes.
   - **The protocol.** `ControlNode` gains `Software software = 6`, so `DescribeControlGroup` and `fleetringd upgrade`'s window check (ADR-0038 point 3) see control-only nodes.
   - **Raft needs no fleet feature.** A fleet feature marks a command that some *member* can't read or act on. The group's entries are read only by group members, and only a node that answers `Probe` on a compatible release can join the group. Data nodes act on nothing new: a 0.4 data node ignores `control_nodes` and follows redirects as it does today.

5. **Mixed releases, the rolling upgrade, and rollback.** (Replaces ADR-0035 point 5's last two sentences and its "no downgrade" consequence.)
   - **A 0.5 control group runs beside 0.4 data nodes,** of any group size. The new protocol fields are additive, 0.4's `ControlClient` follows `fleetring-leader` redirects (ADR-0017 point 4), and it retries `UNAVAILABLE` during an election. A 0.4 data node knows only its one configured address, so while that control node is down it can't reach the group. Data nodes get `[control] addresses` by moving to 0.5.
   - **Voters may run different lines during a rolling upgrade,** within the window, because the formats are FleetRing's (point 3) and the gate covers the group (point 4).
   - **The order is ADR-0038's, extended to the group:** data nodes first, then the control group, learners before voters and the leader last. openraft 0.9 has no leader transfer, so restarting the leader costs one election, 1–2 s with the defaults.
   - **Rollback is refused by `upgrade`, before it swaps anything.** `fleetringd upgrade`, installing or `--rollback`, given `--config`, reads the format of the node's `control.db` from its data directory and refuses a binary whose `--software` reports a lower `control_format`. The error is `UpgradeError::ControlFormat`: "fleetringd 0.4.0 reads control log format 1, and <path> is format 2: rolling this control node back would leave it unable to start", with a hint. `software::running()` reports `control_format = 2` once format 2 lands. Without `--config` the check can't find the file, as the window check can't find the fleet (ADR-0038, amendment), and the README says to pass it.
   - **A rollback that bypasses the check fails safely.** 0.4's own `upgrade`, run as `fleetringd.previous`, predates the check. The 0.4 daemon it installs refuses format 2 when it opens the file (`UnsupportedFormat`) and changes nothing, and the operator rolls forward with `fleetringd.previous upgrade --rollback`.
   - **ADR-0035's "back up `control.db` and restore it" advice is withdrawn** except for a first start on the new release that never completed. A copy restored after the control plane committed anything can reissue lease epochs. Whether 0.5 should offer a down-conversion for one-voter groups is left to the owner (see the plan's open questions).

6. **The leader stamps commands, and a new leader settles before it fails anything over.** (Replaces ADR-0035 point 7.)
   - **Stamping.** The proposer stamps each command with the leader's `Clock` when it screens it (point 2), so the stamp is in the entry and every node applies the same time. `apply` already treats a stamp earlier than `State::now` as `State::now`, so time never moves back across leaders.
   - **The failover timer** (ticks, `StartPromotion`, and `Promote` notices) runs only on a ready leader. It starts when the proposer becomes ready and stops when the node stops leading.
   - **The settle window,** a lease duration plus the failover margin before any `StartPromotion` (ADR-0022 point 6), restarts at every readiness. It is measured on `tokio::time::Instant`, which is monotonic, not on the stamping clock, so a step of the new leader's wall clock can't shorten it.
   - **Promotions already in progress** are in control state with their epochs issued. Their candidates are notified again at once; only *starting* a promotion waits.
   - **Skew affects availability, never safety.** A leader whose clock runs ahead moves state time ahead, so leases look expired, but the settle window lets primaries renew under the new clock first. When a leader whose clock ran ahead is followed by one on true time, the new leader's stamps are clamped and state time stands still until real time catches up. No lease expires and no member goes down meanwhile, so a failover can be late by up to the skew. Epochs fence and W + Q > R whatever the clocks say (ADR-0018 point 6).
   - **Skew is watched, never used.** A receiver of a Raft message compares `sent_at_ms` with its own clock. The leader exports the largest offset it sees and logs a warning when it exceeds the failover margin. No decision reads it.

7. **Snapshots and compaction replace format 1's single snapshot.** (Restates ADR-0035 point 8 against what exists.)
   - **What changes.** Format 1 keeps the newest snapshot only, saved every `snapshot_every` commands, and never purges the log. Format 2 lets openraft build a control snapshot every `snapshot_every` entries (`SnapshotPolicy::LogsSinceLast`; blank and membership entries count, and the setting keeps its name). It keeps `[control] snapshots_retained` snapshots (default 2), deleting older ones in the transaction that stores a new one. It purges the log up to `[control] log_keep` entries behind the newest snapshot (default 1,000), in batches of 256; openraft never purges past the last snapshot.
   - **What a snapshot holds.** Its state, its membership, and its last log ID, in point 3's encoding. Every snapshot read or installed passes `check_state` against the genesis configuration, as format 1's do.
   - **Followers too far behind** receive the newest snapshot through `InstallSnapshot` in 1 MiB chunks.
   - **The replay check** starts at the oldest retained snapshot, or at genesis while nothing has been purged. It must reproduce each newer retained snapshot and the published state.
   - **Migration** writes the first snapshot (point 8).

8. **A format-1 log migrates on first start, from whichever release wrote it.** (Replaces ADR-0035 point 5's migration.)
   - **Which files.** The Raft release reads format-1 files written by 0.4.0, including those 0.3.0 began, with every command either release logs. Format 1 is the same file in both. The commands differ only in optional fields and in actions 0.3 never logs, and the Raft release's `fleetring-control` decodes all of them.
   - **The migration, in one `BEGIN IMMEDIATE` transaction:**
     1. Recover the state with the format-1 code (the newest snapshot and the commands after it).
     2. Replay every command from genesis and check that it reaches the same state. Format 1 never purges, so the check is possible, and it stops a corrupt snapshot from becoming the only base. A mismatch refuses to migrate and names the first index where they differ.
     3. Rename `commands` and `snapshots` to `commands_v1` and `snapshots_v1`.
     4. Create the format-2 tables.
     5. Write a control snapshot at the last index N, with term 0, leader node `0000000000000000`, and a membership with this node as its only voter.
     6. Set `committed` and `purged` to that log ID, and set `format` to 2.

     State carries members' software and enabled features, so both survive. The node then elects itself (point 9). An empty format-1 file becomes an empty format-2 store and bootstraps by `[control] bootstrap`.
   - **The node's own peer.** Migration needs the node's ID and advertised address, so the daemon binds its listener before it opens the control node.
   - **`commands_v1` and `snapshots_v1`** are kept, never read again, through the Raft release's line and dropped by the line after it. This restates the owner's decision of 2026-11-03, which said "0.4" for the release that adds Raft, now 0.5.

9. **Group membership, fleet membership, `node remove`, and dev mode.** (Amends ADR-0035 points 10, 11, and 13.)
   - **Two memberships.** A node's role puts it in the control group, in the fleet, or in both. The group is Raft configuration (ADR-0035 point 3); the fleet is `State`. A node with `role = "control"` never joins the fleet, as today. `control remove` changes only the group, and `node remove` only the fleet.
   - **`fleetringd node remove <id>` refuses a node that is a voter or learner of the group,** with `FAILED_PRECONDITION`: "node '<id>' is a member of the control group; take it out with `fleetringd control set-voters` and `fleetringd control remove` first". A dead voter it left in place would silently count toward every quorum. The leader's service checks this against its group view before it submits `Leave`, as it checks bindings (ADR-0031 point 2), and `apply` doesn't change.
   - **A removed control node** can't disrupt the group, because members refuse its Raft calls (`control peer`, ADR-0035 point 13). Once it applies a membership without itself, it stops proposing, logs the removal once, and fails its `control_group` readiness check (point 10).
   - **A one-voter group elects itself at once.** When the only voter in its membership is the node itself, `ControlNode::open` calls `Raft::trigger_elect` instead of waiting an election timeout. A single control node, which is what most fleets and every dev node run, is then ready as fast as today.
   - **Dev mode changes nothing but validation.** A dev node is a one-voter group with the defaults, and `fleetringd dev` writes no new setting. With `dev = true`, `Config::validate` also refuses `control.addresses` that aren't loopback and `control.bootstrap = "join"`, which would wait for a second node that dev mode never runs. `AddControlNode` on a dev node refuses a non-loopback address with the same loopback check (ADR-0039 point 3), so a dev node's control log never leaves the machine. Upgrading a dev node from 0.4 migrates its `control.db` like any other's.
   - **`set-voters` may shrink the group to one voter,** with a CLI warning, as the owner decided on 2026-11-03.

10. **Readiness and metrics follow the group.** (Extends ADR-0034 point 4 and its control family.)
    - **Readiness checks:**
      - `control_log`: the proposer and storage are running. `/healthz` turns `503` on an openraft storage error, as it does on `SubmitError::Storage` today.
      - `leader`: passes when this node knows a leader, itself or another, and fails with "no control leader known".
      - `control_group`, new: this node is a voter or learner. It fails while a `join` node waits to be added, and after removal.
    - **Gauges kept:** `fleetring_control_leader` (1 on the leader), `fleetring_control_log_index` (now the last log index), `fleetring_control_snapshot_index`, and `fleetring_control_mailbox_depth` (now the submissions waiting for the proposer or for their responders).
    - **Gauges added:** `fleetring_control_committed_index`, `fleetring_control_applied_index`, `fleetring_control_term`, `fleetring_control_voters`, `fleetring_control_learners`, `fleetring_control_replication_lag_max` (on the leader, the most entries any member is behind; 0 elsewhere), and `fleetring_control_clock_offset_max_seconds`.
    - **Counters added:** `fleetring_control_elections_total` (terms this node saw begin), and `fleetring_control_proposals_total{outcome}` with the closed set `committed`, `refused`, `superseded`, `not_leader`.
    - **`fleetring_control_commands_total`** now counts the commands this node applied, on every member.
    - **Labels** carry no peer ID, and no new name contains "leader" (`observe/names.rs` allows only `fleetring_control_leader`).

11. **The protocol moves to 1.2.** ADR-0038 took 1.1. FR-064's additions are the `Raft` service with `Probe`, `RaftPayload` with fields 2 and 3, `ControlNode.software = 6`, `JoinResponse.control_nodes = 4`, `HeartbeatResponse.control_nodes = 4`, and the four group RPCs of ADR-0035 point 11. Together they are 1.2, and FR-066 takes the minor after whichever of the two lands first.

## Alternatives considered

- **Rewriting ADR-0035 in place and returning it to Proposed.** It holds every decision in one file, but the record was accepted, and the project's rule is to amend accepted decisions, never rewrite them.
- **openraft 0.10 (alpha).** Its runtime and storage traits are cleaner, but it is an alpha whose traits changed across 37 releases this year. Pinning one would make every patch release a port. Revisit once 0.10.0 is final.
- **Screening against the applied state only.** It misses the proposals in flight. A pending join of a 0.4 node followed by a join of a 0.6 node, screened without the first, passes the screen, so the second reaches the log, where `apply` rejects it, and a 0.5 voter that later replays without software would accept it. That is the hazard of ADR-0038's amendment again.
- **Screening in `apply` alone** (logging everything and letting the state machine reject). Refused joins would be in the log, which ADR-0038's amendment rules out.
- **Proposing one command at a time** (waiting for each to apply before screening the next). It makes the screening state exact without the leader ID, but costs a replication round per command and gives up group commit, at the control plane's busiest path, the heartbeats.
- **Keeping openraft's serde forms on disk and on the wire** (ADR-0035 as accepted). Less code, but the formats would follow openraft's releases, a mixed group would depend on two openraft builds agreeing on JSON, and 0.10 would force a third `control.db` format.
- **One thread-local generator for every host** (ADR-0035's plan). It replays, but one host's crash shifts every other host's elections, which makes failing seeds harder to read, and it isn't the per-host injected generator ADR-0020 asks for.
- **A `cfg(feature = "simulation")` runtime beside `TokioRuntime`.** Tests built with `--all-features` would then run a different runtime from production, and two runtimes would need two sets of tests. One runtime whose seed the environment supplies has neither problem.
- **Recording control nodes' software in `State`.** It would make the gate pure, but it puts the group into control state, which ADR-0035 point 3 keeps out, and it needs a new command. Only the leader needs the group's software, and only before it logs.
- **A fleet feature that gates the Raft group.** Point 4: no fleet member reads the group's entries, and `Probe` keeps nodes without Raft out of the group.
- **Leaving `node remove` free to remove a control voter.** One command would then do half the job, and a dead voter would keep counting toward quorums unseen.

## Consequences

- Rolling upgrades and rollbacks keep ADR-0038's guarantees with a control group. The one new refusal is rolling a control node back to a release that can't read its `control.db`.
- Upgrading openraft is a code change behind `codec.rs`, not a migration, and the golden vectors catch any accidental change to either format.
- The leader applies each command twice, once to the screening state and once in the state machine, as the single writer's preview already does for commands that need screening.
- A down control node blocks the first use of a new feature, and its absence from `control list` is the fix, as `node remove` is for a fleet member.
- Control calls stay at-least-once across a lost deadline, as today. A leader change itself loses nothing and duplicates nothing, because every waiting submitter learns whether its entry was applied, truncated, or superseded.
- A leader whose clock ran ahead can delay failovers after it loses leadership by up to its skew, and denylist entries are forgotten by state time, so they can go up to the skew early, as with one control node today. The new clock-offset gauge shows it, and the README asks for NTP.
- The plan grows a fixture step that writes `control.db` files with the 0.3.0 and 0.4.0 code at their tags, and an upgrade check, `UpgradeError::ControlFormat`.
- When this record is accepted, ADR-0035's status line reads "Accepted (points 1, 3, 4, 5, 7, 8, 9, 11, 13, 14, 15 amended by 0040)", and FR-064's plan follows this record wherever the two differ.
