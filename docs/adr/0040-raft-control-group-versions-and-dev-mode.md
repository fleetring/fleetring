# ADR-0040: The Raft control group screens commands on its leader against the log it will commit, owns its storage and wire formats, and draws openraft's randomness from an injected generator (amends ADR-0035)

- **Status:** Accepted (2026-11-25, by the owner, with decisions D1 to D9 as recommended; see [Owner decisions](#owner-decisions-2026-11-25)); points 2 and 6 amended by [amendment 1](#amendment-1-2026-11-26-one-batch-in-flight-and-a-discarded-entrys-outcome-is-unknown) (accepted 2026-11-26); points 3, 4, 5, 9, and 11 amended by [amendment 2](#amendment-2-2026-11-28-leader-hand-over-the-probes-certificate-check-and-d7-on-plaintext) (proposed 2026-11-28); point 6 amended by [amendment 3](#amendment-3-2026-11-28-fork-actions-that-act-on-reports-dont-wait-out-the-settle-window) (proposed 2026-11-28); points 9, 11, and 12 amended by [amendment 4](#amendment-4-2026-11-28-the-router-learns-the-group-from-locate-and-a-member-moves-to-a-new-address) (proposed 2026-11-28)
- **Date:** 2026-11-04 (revised on 2026-11-25 against `main` at 0.9.0, before acceptance)
- **Related:** ADR-0035 (amends points 1, 3, 4, 5, 6, 7, 8, 9, 11, 12, 13, 14, and 15), ADR-0017, ADR-0018, ADR-0020, ADR-0022, ADR-0026, ADR-0031 (amendment 2), ADR-0034, ADR-0038, ADR-0039, ADR-0043, ADR-0046 (FR-110 amendment), ADR-0047, ADR-0050; tickets FR-064 (#67), FR-065 (#68), FR-127 (#216), FR-128 (#217)

## Context

ADR-0035 was accepted on 2026-11-03, before the work it plans had started. This record was first written on 2026-11-04, against 0.4.0. It stayed Proposed while 0.5.0 to 0.9.0 shipped, and was revised on 2026-11-25 against `main` at 0.9.0. Checking ADR-0035 against that code turns up these gaps:

- **The single writer does more than "stamp, screen, append".** `commit_group` in `crates/fleetringd/src/control/node.rs` now has six duties, and ADR-0035 point 3's `client_write` covers only the first:
  1. It stamps each command with the clock and with its own node ID as `recorded_by` (ADR-0047 point 6.1).
  2. It refuses, unlogged, a command that needs a fleet feature some member lacks, and a join refused for its release line or a missing feature, against a preview of the state the commands queued before it leave (`State::check_admission`, ADR-0038's amendment). Without this screen, a control node rolled back to an older release would replay a logged join it would accept although the fleet refused it.
  3. It logs an enabling command of its own just before the command that first needs it: `EnableHandover` before the first membership change that would keep a replica set (`handover_due`, ADR-0031 amendment 2), `EnableIncarnations` before the first creation under `always` (`incarnations_due`, ADR-0046's FR-110 amendment), and `SetTombstoneWindow` before a drop while the state's window isn't the configured one (`tombstones_due`, ADR-0050 point 5). Without them, replays diverge.
  4. It refuses, unlogged, any command that needs `delegation` and that `apply` would reject on the preview (`refused_unlogged`, ADR-0047 point 6.2).
  5. It answers a `RecordDelegation` that resends a recorded operation from the state, with `Resent::Yes`, without logging it, and only once the group is durable (ADR-0047's note of 2026-11-17).
  6. It answers nothing before the whole group is durable.

  Under Raft only the leader proposes, many proposals are in flight at once, and leadership can move between screening a command and appending it.
- **A control group mixes two release lines during a rolling upgrade.** ADR-0038 lets a fleet run two adjacent lines, and voters are upgraded one at a time. ADR-0035 stores openraft's own serde forms in `control.db` and sends them on the wire, so the formats belong to openraft's release, not to FleetRing's.
- **The feature gate can't see control-only nodes.** `State::check_feature` asks every fleet *member*. A node with `role = "control"` isn't a member, yet under Raft it decodes and applies every command.
- **Nobody runs a release before 0.9.** Every compatibility step of the first draft targeted 0.3.0 and 0.4.0. The Raft release, R (0.10), meets format-1 files written by 0.9.x, often begun by 0.3.0 (an upgrade never skips a line). They hold every command through 0.9: joins and heartbeats with software, `Undrain`, forks, delegations, the hand-over, incarnations, and tombstones.
- **openraft 0.10 is final.** 0.10.1 was released on 2026-11-19, with MSRV 1.88. The 0.9 line (newest 0.9.26) carries non-optional `chrono`, `rand 0.8`, `thiserror 1`, `clap`, and `byte-unit`; `chrono` contradicts `deny.toml`, whose ignore of RUSTSEC-2026-0543 says chrono reaches us only through rmcp and schemars. 0.10.1 needs `rand 0.10` (already in the lock) and `thiserror 2`, and `clap` only behind its default feature. 0.10 adds leader transfer (`trigger().transfer_leader`), `WriteOption::expect_leader` (new in 0.10.1), `ReadPolicy` for linearizable reads, and a runtime hook for randomness. Its `AsyncRuntime` lives in `openraft-rt` and also asks for channel and mutex types, and its default `spawn_blocking` starts an OS thread.
- **ADR-0035 point 15 draws every host's election timeouts from one thread-local generator,** so a crash on one host shifts every other host's draws, and it isn't the per-host injected generator ADR-0020 point 2 asks for. The simulation's `SimEntropy` is also seeded with `seed ^ elapsed` and no host name today, so two hosts that start together draw identical streams.
- **The failover timer has six duties now:** ticks (including the delegation and tombstone purge ticks), promotions, `Promote` notices, fork actions (`fork::actions`), and kept-set releases (`release_kept_replicas`), plus the expiry sweep, a task of its own. Its settle window starts from `clock.now()`, a wall clock, and a submit error ends its loop for good.
- **Dev mode, `node remove`, and the admin listener.** ADR-0039 runs one node with both roles on loopback. `fleetring node remove` takes a dead member out of the fleet, but a dead control voter would still count toward the group's quorums. ADR-0034's readiness check `leader` "gets its meaning from FR-064", and its metrics name the single writer.
- **A one-voter group restarts slowly.** openraft makes a restarted single voter wait an election timeout before it elects itself. Today a restarted control node serves at once, and dev mode starts in about a second.
- **Wire numbers moved.** `PROTOCOL_VERSION` is 1.3: 1.1 went to ADR-0038, 1.2 to metadata (FR-070), and 1.3 to `Database.Session` (FR-066). `HeartbeatResponse` uses fields 4 (`forks`) and 5 (`tombstones`), so ADR-0035 point 14's `control_nodes = 4` collides; `JoinResponse` field 4 is free.
- **Some per-node settings leak into commands.** The leader fills commands from its own configuration: the tombstone window, the `[fork]` limits, the default replication factor and durability. Under Raft the leader changes, and so can those values.
- **The CLI is `fleetring`** (ADR-0043); `fleetringd` is its compatibility name until 1.0. The process file keeps its name, `fleetringd.process`.

ADR-0035 is accepted, and accepted decisions are amended, not rewritten (`docs/adr/README.md`). This record amends it. Points of ADR-0035 it doesn't mention stand as written. Where this record replaces a point, the replacement is stated in full.

## Decision

1. **openraft is pinned to `=0.10.1`, with default features off and without its `serde` feature, behind one runtime type in every build.** (Replaces the dependency and `AsyncRuntime` rows of ADR-0035 point 1, and the randomness of point 15.)
   - **The version.** 0.10.1 is final, builds with `fleetringd`'s MSRV (1.89), and drops `chrono`, `rand 0.8`, and `thiserror 1` from the dependency graph. `default-features = false` keeps `clap` out. It is MIT or Apache-2.0, with no RUSTSEC entries. It is new (released 2026-11-19), so it is pinned with `=`, and a later openraft release is its own change. Moving to it changes neither the disk nor the wire format (point 3). Without the `serde` feature, openraft's types can't be serialized at all, so the compiler keeps them off the disk and the wire.
   - **One runtime, `ControlRuntime`.** It implements 0.10's `AsyncRuntime` (from `openraft-rt`). Its timers, instants, timeouts, channels, and mutexes are Tokio's, so openraft reads time only from `tokio::time`: turmoil's simulated clock under simulation, paused time in tests, the real clock in production. Two functions differ from openraft's Tokio runtime:
     - `spawn` wraps the future in the spawning task's generator scope, a `tokio::task_local!` holding `Arc<Mutex<SplitMix64>>`, so every task openraft spawns inherits the generator of the `ControlNode::open` that created the `Raft`;
     - `spawn_blocking` runs on Tokio, never on an OS thread of its own, which neither paused time nor turmoil can see.

     The runtime's random-number hook draws from the generator in scope, through `rand 0.10`'s traits. The generator is the harness's SplitMix64 (`sim/rng.rs`), moved to a module both use, so a seed replays after any dependency upgrade. openraft 0.10's `DeterministicRng` (a `SmallRng`) isn't used, for the same reason.
   - **Where the seed comes from (ADR-0020 point 2).** The environment injects it: `Environment::entropy()`, which exists, mixed with the host. Under simulation it is the run's seed mixed with the XXH3-64 of the host's name, so each control host has its own stream and a crash on one host doesn't shift another's elections. In production it is eight bytes from `ring`'s `SystemRandom`, read once when the control node opens. No `cfg(feature = "simulation")` picks a different runtime. A draw outside any scope, which would be a bug, uses a generator seeded with the node's Raft ID, logs an error once, and fails a test that watches for it.
   - **This is verified again against 0.10.1 before anything builds on it.** The first draft verified the hook against 0.9.25 in a scratch crate: the same seed gave the same election timeouts across a spawned task, and another seed gave others. The plan's PR 2 repeats the check as a test against 0.10.1: openraft's randomness goes only through the runtime's hook, it spawns only through the runtime, it reads time only through the runtime's instant, and its core loop's `select!` is `biased` or seeded by Tokio's scheduler RNG, which turmoil seeds under `--cfg tokio_unstable`. If the check fails, the work stops there and goes back to the owner.

2. **The leader screens each command against the state its own log will reach, through the single writer's own screen, and every proposal carries the leader ID it was screened under.** (Replaces the submit path of ADR-0035 point 3, and amends point 6's reads; group commit stays.)
   - **One screen, two callers.** The single writer's screening moves, with no change in behaviour, into a pure module, `control/screen.rs`, before any Raft code lands. Both the single writer and the proposer call it, so the six duties in the Context can't drift between them. It takes the screening state and an action and returns what to do: refuse it unlogged, answer it from the state as a resend, or log it, preceded by at most one enabling command.
   - **One proposer per control node** takes over the single writer's place. It accepts submissions only while this node leads a term *and* is *ready*: its state machine has applied an entry of that term. openraft appends a blank entry when a leader takes over, so once the leader has applied an entry of its own term, it has applied every entry its log held at takeover, the previous leader's uncommitted entries included, since its blank entry commits them. Before it is ready, a submission is answered `UNAVAILABLE` with "the control leader is catching up; retry" and the leader hint. The new leader holds every committed entry and may hold uncommitted ones, and it screens nothing until it has applied all of them. Entries the old leader proposed that the new leader lacks were never committed and never acknowledged, and openraft answers their submitters `ForwardToLeader` when it truncates them.
   - **The screening state.** When the proposer becomes ready in term T, it clones the applied state into S. It takes submissions one at a time, in arrival order:
     1. It asks the screen. A join, or an action with a feature, is checked with `S.check_admission(&action)` and the group gate (point 4). A refusal is answered `SubmitError::Refused`; nothing is proposed, and S doesn't change.
     2. If the screen says an enabling command is due (`EnableHandover`, `EnableIncarnations`, or `SetTombstoneWindow`), the proposer stamps it, passes it through the group gate, applies it to S, and proposes it first. If the group gate refuses it, the triggering command follows point 4's fallback for that command.
     3. It stamps the command with the clock (point 6) and with this node's ID as `recorded_by`.
     4. A `RecordDelegation` that resends an operation S records is answered with the record, `Resent::Yes`, and not proposed. The answer waits until this node has **committed and applied** every entry it proposed before the resend, and is then read from the applied state, not from S. If the applied state lacks the record, because an entry was superseded or truncated, the resend is answered `UNAVAILABLE`, "retry". Under Raft, "durable" in ADR-0047 means committed and applied, never proposed: otherwise a token could be signed for a delegation that a truncation erases, which revocation then can't find.
     5. Otherwise it applies the command to S with `apply`, so S stays exactly the state after the proposals so far. A command that needs `delegation` and that `apply` rejects is answered `SubmitError::Refused` and not proposed; a rejection changes nothing, so S is the same either way. Any other rejected command is proposed, as the single writer logs it.
     6. It hands the entry to openraft's fire-and-forget write, with `WriteOption::expect_leader` set to the leader it screened under. openraft queues the entry on its ordered request channel, so entries reach the log in the order they were screened, and refuses it, rather than appending it in a later term, if this node no longer leads under that leader ID.
     7. It waits for the entry's responder off its own path, so proposals pipeline and openraft batches their appends into one `append` call, with one sync.
   - **The leader ID travels in the entry as well (decision D6).** A proposal is a `ControlRequest { screened: LeaderRef { term, node }, command }`, with `command` stored and sent as raw JSON (`serde_json::value::RawValue`). The skip rule applies only to entries of kind `command`; blank and membership entries are openraft's own, carry no `screened` field, and are always applied. The state machine applies a command only when the entry's own log ID carries the same leader ID. Otherwise it skips the entry without decoding the command, answers `Superseded`, and changes nothing, deterministically on every node and in every replay. `expect_leader` prevents most superseded entries; the in-entry check makes the skip deterministic whatever openraft's queue does. With both, the screen is exact: in term T, the leader's log is its log at takeover followed by its own term-T proposals, in order, which is exactly what S applied, and by Raft's log-matching property a term-T entry commits only together with every term-T entry before it. A superseded submitter gets `UNAVAILABLE`, "retry"; nothing happened. Keeping the command undecoded means a voter never decodes a command it won't apply.
   - **`recorded_by` is stamped by the proposer and checked by the state machine (decision D5).** After the leader-ID check, the state machine decodes the command and requires `raft_id(command.recorded_by) == entry.leader.node`, where `raft_id` is ADR-0035 point 2's XXH3-64 of the node ID. A command whose `recorded_by` is missing or names another node is skipped as `Superseded`, and changes nothing. The check is pure and needs no membership lookup, so replay checks without openraft run it too, and the payload stays byte-equal to format 1's command JSON. It makes `recorded_by` agree with the entry's leader on every replica. It stays advisory against a compromised leader, which chooses its entries' leader IDs as well as their payloads (ADR-0047 point 6.1).
   - **S is dropped** when the node stops leading T, and when its state machine applies an entry from another leader after it became ready. Submissions waiting for a responder keep waiting. openraft answers each one when the entry is applied, whichever node led when it committed, or `ForwardToLeader` when the entry is truncated, which means it never took effect. Only a deadline that expires first leaves the outcome unknown, as a timeout does today.
   - **`apply` doesn't change.** It still refuses what `check_admission` refuses, so anything that reached the log by a bug is rejected the same way everywhere. The screen exists so that an older release never meets a refused command in a log it replays (ADR-0038 point 4). `fleetring-control` doesn't change, and its replay tests stay as they are.
   - **Reads.** Reads on the leader call `ensure_linearizable` with `ReadPolicy::ReadIndex`, never `ReadPolicy::LeaseRead`: a lease read depends on bounds on clock drift, and safety never depends on clocks (ADR-0018). The linearizable reads are `Locate`, `ListDatabases`, opening `WatchMembership`, `DescribeControlGroup`, `GetForkOperation` (a client polls the fork it just started, so it must see it), and `ListDelegations` (incident response must see every recorded delegation). `ListTombstones` and the tombstones in heartbeat replies read the leader's committed state without a read round: a lagging state can only *miss* tombstones, which keeps copies (ADR-0050 point 8), and they are still answered by the leader. The service's binding checks (ADR-0031 point 2) read the node's applied state; a per-epoch fact never changes once given, so an applied state that lags can only refuse a call that a retry then admits.
   - **The injected enabling commands are temporary.** FR-127 (#216) replaces them with explicit feature finalization. FR-064 keeps today's injection, through the shared screen.

3. **FleetRing owns `control.db` format 2 and the Raft wire format; openraft's types reach neither.** (Replaces the encodings of ADR-0035 points 4, 8, and 9; the tables, transactions, and RPCs stay.)
   - **Raft IDs are text.** Raft IDs (ADR-0035 point 2) are written as 16 lowercase hex digits wherever they are stored or sent. They are 64-bit unsigned, SQLite's integers are signed, and JSON readers other than serde lose precision above 2^53.
   - **The log.** `log(log_index INTEGER PRIMARY KEY, term INTEGER NOT NULL, leader_node TEXT NOT NULL, kind TEXT NOT NULL CHECK (kind IN ('command', 'membership', 'blank')), payload TEXT NOT NULL) STRICT`.
     - A command's payload is `{"screened": {"term": <u64>, "node": "<hex>"}, "command": <Command>}`, where `<Command>` is the same JSON format 1 stores, `recorded_by` included, so `fleetring-control`'s serde tests keep covering the log.
     - A membership's payload is `{"configs": [["<hex>", …], …], "nodes": {"<hex>": {"node_id": "…", "address": "…"}}}`: one config, or two during joint consensus.
     - A blank entry's payload is `{}`.
   - **`meta` and `snapshots`.** `meta` keeps `format` (`2`) and `genesis`, and adds:
     - `vote`: `{"term", "node", "committed"}`;
     - `committed` and `purged`: `{"term", "node", "index"}`.

     `snapshots(log_index, term, leader_node, membership, state)` stores a membership as above and `state` as format 1 stores it.
   - **The wire.** `RaftPayload { bytes json = 1; Software sender = 2; uint64 sent_at_ms = 3; }`. `json` holds FleetRing's wire structs for openraft's requests and replies (`AppendEntries`, `Vote`, `InstallSnapshot`, and the replies with their conflict, higher-vote, and partial-success cases). Entries in them use the encoding above. `sender` is the sending node's software (point 4); `sent_at_ms` is its clock reading (point 6). openraft 0.10's network trait hands the network a whole snapshot; the network sends it as `InstallSnapshot` chunks of at most 1 MiB, and the receiver reassembles them before it gives openraft the snapshot.
   - **Conversion.** One module, `control/raft/codec.rs`, converts between the two type families. Golden JSON vectors for every message, entry kind, vote, and snapshot form are checked in, and are append-only, like placement's (ADR-0008).
   - **Changing the formats.** Readers ignore unknown fields, so an additive change mixes within the window. A change that isn't additive needs a new protocol minor version, and a release keeps reading and writing the previous line's form until every group member reports the new one.
   - **Why.** A rolling upgrade runs two lines in one group, so the bytes voters exchange and store must be FleetRing's to keep. A later openraft release then changes code, not `control.db`. The log stays readable in the `sqlite3` shell, and the simulation's replay check reads it without openraft.

4. **The feature gate and the release window cover the control group as well as the fleet's members.** (New; extends ADR-0038 points 3 and 4 and ADR-0035 points 11 and 14.)
   - **Where a group member's software comes from.** Every `RaftPayload`, request or reply, carries its sender's `Software`. The leader keeps the last software it heard from each member of its group, in memory, with the time it heard it (`tokio::time::Instant`). A new leader starts with none, and hears from every reachable member within one Raft heartbeat.
   - **A report goes stale.** A member's software counts as known only while the member has answered this leader within one shortest election timeout (`[control] election_timeout_ms`, four Raft heartbeats by default). After that it is unknown, and the "hasn't reported its software yet" refusal below covers it. A member whose reported release or features changed since the last report is unknown until the leader has applied every entry it proposed before it heard the change, so a command screened against the old report can't commit unnoticed.
   - **The first use of a feature needs the whole group.** A command that needs a feature not yet enabled is refused before it is logged unless every voter's and learner's software is known and supports the feature. The refusal is `Rejection::FeatureUnsupported`, naming the control node and its release, or "control node '<id>' hasn't reported its software yet" while a member is unknown. A down member blocks the first use until it returns or is removed, as a down fleet member does (ADR-0038, Consequences).
   - **Each injected enabling command has a fallback that fails closed.** The group gate screens the proposer's own enabling commands like any other. When it refuses one, nothing is enabled, and:
     - **`SetTombstoneWindow` refused:** the drop proceeds without a tombstone, so every replica keeps its copy as an orphan (ADR-0050 point 7).
     - **`EnableIncarnations` refused:** the creation under `always` is refused with `FeatureUnsupported` for `incarnations`, unlogged, and the service submits it again under `once_forked`, as it does today when a member lacking the feature joined meanwhile (ADR-0046's FR-110 amendment, item 14). The service's choice of `IncarnationRule::Always` asks the group gate as well as the fleet's members, so it rarely needs the retry.
     - **`EnableHandover` refused:** the membership change proceeds without keeping a replica set, as in a fleet where `handover` isn't enabled yet. That is ADR-0031 amendment 2's accepted path for a mixed fleet (its point 6, "in a mixed fleet"), and it leaves open the window that amendment closes until every group member supports `handover`.
   - **What remains is fail-stop.** A voter that meets an entry it can't decode stops applying at that entry and never applies past it. Its `control_log` readiness check fails with "entry <i> needs fleet feature '<f>', which fleetring <version> lacks; upgrade this node", and the leader logs the same once. Rolling the node forward resumes it, and the rest of the group keeps its quorum. In R this can't happen through an upgrade: R is the first release with a group, so every group member runs R (below), and rolling a voter back below R is refused (point 5). The first mixed group can form in R+1. Announcing a voter's next software before its binary changes, which would close the race between a first use and a rollback, is deferred to the first feature after Raft (decision D4).
   - **The window counts control nodes.** A join is refused before it is logged when its release line can't run beside a group member's (`Rejection::IncompatibleVersion`, naming the control node). This screen refuses more than `apply` does, which is safe: `apply` never sees a refused command.
   - **`control add` probes before it adds.** A new RPC, `Raft.Probe`, returns the target's node ID, its software, and whether its store holds any Raft state. `AddControlNode` refuses the target before it adds it as a learner when:
     - its node ID isn't the one named;
     - its store isn't empty, which stops a node started with the default `bootstrap = "new"` from bringing its own group in;
     - its release is outside the window with any fleet member or group member;
     - it lacks an enabled feature;
     - it has no `Raft` service. A 0.9 node answers `UNIMPLEMENTED`, refused as "node '<id>' runs fleetring <version>, which has no control group".

     Once a feature is enabled, `upgrade` keeps refusing a release that lacks it (ADR-0038 point 4), on control nodes as on data nodes.
   - **The protocol.** `ControlNode` gains `Software software = 6`, so `DescribeControlGroup` and `fleetring upgrade`'s window check (ADR-0038 point 3) see control-only nodes.
   - **Raft needs no fleet feature.** A fleet feature marks a command that some *member* can't read or act on. The group's entries are read only by group members, and only a node that answers `Probe` on a compatible release can join the group. Data nodes act on nothing new: a 0.9 data node ignores `control_nodes` and follows redirects as it does today.

5. **Mixed releases, the rolling upgrade, and rollback (decisions D2 and D3).** (Replaces ADR-0035 point 5's last two sentences and its "no downgrade" consequence.)
   - **The compatibility path is the slim one.** Nobody runs a release before 0.9, so R keeps one 0.9.0 fixture, the `ControlFormat` refusal, the group gate with its staleness rule, and fail-stop. It keeps no fixtures from older tags, no down-conversion, and no software announcement.
   - **An R control group runs beside 0.9 data nodes,** of any group size. The new protocol fields are additive, 0.9's `ControlClient` follows `fleetring-leader` redirects (ADR-0017 point 4), and it retries `UNAVAILABLE` during an election. A 0.9 data node knows only its one configured address, so while that control node is down it can't reach the group. Data nodes get `[control] addresses` by moving to R.
   - **Voters may run different lines during a rolling upgrade,** within the window, from R+1 on, because the formats are FleetRing's (point 3) and the gate covers the group (point 4).
   - **A field an older line would drop must not decide anything.** Under Raft, a newer leader routinely hands an older voter `InstallSnapshot` with a `State` whose unknown fields the older line drops when it decodes, and the older voter's log entries can likewise carry action fields it drops. ADR-0038 gates commands, not fields, so a new field filled by an existing command (one recorded from heartbeats, say) would leave older voters silently diverged, and a replay check running on one release can't see it. So a `State` field, or a field of an existing `Action`, that the previous line doesn't decode must either:
     - be set only by commands that need a fleet feature, so it keeps its default until every member and group member reads it; or
     - be derivable from the log and from fields the previous line does read: a cache that `apply` recomputes, so dropping it changes no decision.

     `fleetring-control` checks this with a list of the previous line's JSON field paths, written at the `fleetringd-v0.9.0` tag (`fields-0.9.0.txt`), and a register of new fields, each naming its feature or "derived". R+1's leaders will send R's voters snapshots, so the register starts with R. The plan's simulation phase checks it by installing snapshots on "older" hosts through a filter that drops the fields the previous line lacks.
   - **The order is ADR-0038's, extended to the group:** data nodes first, then the control group, learners before voters and the leader last. A leader that shuts down gracefully, as `upgrade`'s restart makes it, first hands leadership to a caught-up voter with openraft's leader transfer, so a planned restart of the leader costs no election.
   - **Rollback is refused by `upgrade`, before it swaps anything.** `fleetring upgrade`, installing or `--rollback`, given `--config`, reads the format of the node's `control.db` from its data directory and refuses a binary whose `--software` reports a lower `control_format`. The error is `UpgradeError::ControlFormat`: "fleetring 0.9.0 reads control log format 1, and <path> is format 2: rolling this control node back would leave it unable to start", with the hint "roll forward". `software::running()` reports `control_format = 2` once format 2 lands; `upgrade --software`'s report gains `control_format` beside `config_check`, and a binary that doesn't report it reads format 1. Without `--config` the check can't find the file, as the window check can't find the fleet (ADR-0038, amendment), and the README says to pass it.
   - **A rollback that bypasses the check fails safely, and leaves a trace R tolerates.** 0.9's own `upgrade`, run as the previous binary, predates the check. The 0.9 daemon it installs refuses format 2 (`UnsupportedFormat`), but 0.9's `CommandLog::open` runs its `CREATE TABLE IF NOT EXISTS` schema before it reads `format`. On a format-2 file, where migration renamed `commands` to `commands_v1`, that leaves a new, empty `commands` table; its `meta` and `snapshots` already exist and are left alone. The operator then rolls forward. Format-2 code tolerates the stray table: on open, it drops an empty `commands` table in its own transaction and logs it at info, and it refuses a non-empty one as corrupt. A fixture written by running 0.9.0's code at its tag against a format-2 file tests it, and the nightly rolling-upgrade test repeats it with the real 0.9.0 binary.
   - **No down-conversion.** It would serve only rollback, which has no users. The first start on R is a one-way door for a control node, and `upgrade` says so before swapping.
   - **ADR-0035's "back up `control.db` and restore it" advice is withdrawn** except for a first start on the new release that never completed. A copy restored after the control plane committed anything can reissue lease epochs.

6. **The leader stamps commands, and a new leader settles before it fails anything over.** (Replaces ADR-0035 point 7.)
   - **Stamping.** The proposer stamps each command with the leader's `Clock` and its node ID when it screens it (point 2), so the stamp is in the entry and every node applies the same time. `apply` already treats a stamp earlier than `State::now` as `State::now`, so time never moves back across leaders.
   - **The leader's timers.** The failover timer (ticks, including the delegation and tombstone purge ticks; `StartPromotion`; `Promote` notices; fork actions; kept-set releases) and the expiry sweep run only on a ready leader. They start when the proposer becomes ready, and pause, without ending, when a submit answers `NotLeader`, `CatchingUp`, or `Superseded`; they resume at the next readiness. Only `Stopped` and `Storage` end them. Every `SubmitError` is matched by name, so a new variant can't end a timer by default.
   - **The settle window,** a lease duration plus the failover margin (ADR-0022 point 6), restarts at every readiness, and gates the start of a promotion, fork actions, and kept-set releases: each acts on liveness and on primaries' reports, which a new leader's state can show stale for the same reason leases look expired. It is measured on `tokio::time::Instant`, which is monotonic, not on the stamping clock, so a step of the new leader's wall clock can't shorten it.
   - **Promotions already in progress** are in control state with their epochs issued. Their candidates are notified again at once; only *starting* a promotion waits.
   - **Skew affects availability, never safety.** A leader whose clock runs ahead moves state time ahead, so leases look expired, but the settle window lets primaries renew under the new clock first. When a leader whose clock ran ahead is followed by one on true time, the new leader's stamps are clamped and state time stands still until real time catches up. No lease expires and no member goes down meanwhile, so a failover can be late by up to the skew. While control time leads the new leader's clock by more than `MAX_CONTROL_LEAD` (30 s), it refuses to delegate (ADR-0047 point 5.4), and expiries can fire early. Epochs fence and W + Q > R whatever the clocks say (ADR-0018 point 6).
   - **Skew is watched, never used.** A receiver of a Raft message compares `sent_at_ms` with its own clock. The leader exports the largest offset it sees and logs a warning when it exceeds the failover margin. No decision reads it.

7. **Snapshots and compaction replace format 1's single snapshot.** (Restates ADR-0035 point 8 against what exists.)
   - **What changes.** Format 1 keeps the newest snapshot only, saved every `snapshot_every` commands, and never purges the log. Format 2 lets openraft build a control snapshot every `snapshot_every` entries (`SnapshotPolicy::LogsSinceLast`; blank and membership entries count, and the setting keeps its name). It keeps `[control] snapshots_retained` snapshots (default 2), deleting older ones in the transaction that stores a new one. It purges the log up to `[control] log_keep` entries behind the newest snapshot (default 1,000), in batches of 256; openraft never purges past the last snapshot.
   - **What a snapshot holds.** Its state, its membership, and its last log ID, in point 3's encoding. Every snapshot read or installed passes `check_state` against the genesis configuration, as format 1's do.
   - **Followers too far behind** receive the newest snapshot through `InstallSnapshot` in 1 MiB chunks (point 3).
   - **The replay check** starts at the oldest retained snapshot, or at genesis while nothing has been purged. It must reproduce each newer retained snapshot and the published state. Checks that need a replay from genesis run only while nothing is purged, so scenarios that rely on them set `log_keep` high enough.
   - **Migration** writes the first snapshot (point 8).

8. **A format-1 log migrates on first start, from whichever release wrote it.** (Replaces ADR-0035 point 5's migration.)
   - **Which files.** R reads format-1 files written by 0.9.x, including those 0.3.0 began, with every command any release through 0.9 logs. Format 1 is the same file in every release. The commands differ only in optional fields and in actions older releases never log, and R's `fleetring-control` decodes all of them.
   - **The migration, in one `BEGIN IMMEDIATE` transaction:**
     1. Recover the state with the format-1 code (the newest snapshot and the commands after it).
     2. Replay every command from genesis and check that it reaches the same state. Format 1 never purges, so the check is possible, and it stops a corrupt snapshot from becoming the only base. A mismatch refuses to migrate and names the first index where they differ: the node fails closed and stays down until an operator acts. Format-1 commands replay with `apply` alone; point 2's skip rules, the `recorded_by` check among them, apply only to format-2 entries, so a command logged before 0.8 without `recorded_by` replays as it applied.
     3. Rename `commands` and `snapshots` to `commands_v1` and `snapshots_v1`.
     4. Create the format-2 tables.
     5. Write a control snapshot at the last index N, with term 0, leader node `0000000000000000`, and a membership with this node as its only voter.
     6. Set `committed` and `purged` to that log ID, and set `format` to 2.

     State carries members' software and enabled features, so both survive. The node then elects itself (point 9). An empty format-1 file becomes an empty format-2 store and bootstraps by `[control] bootstrap`. A fixture written by 0.9.0's code at its tag, holding forks, delegations, the hand-over, incarnations, and tombstones, tests it.
   - **The node's own peer.** Migration needs the node's ID and advertised address, so the daemon binds its listener before it opens the control node.
   - **`commands_v1` and `snapshots_v1`** are kept, never read again, through R's line and dropped by the line after it. This restates the owner's decision of 2026-11-03, which said "0.4" for the release that adds Raft, now 0.10.

9. **Group membership, fleet membership, `node remove`, and dev mode.** (Amends ADR-0035 points 10, 11, and 13.)
   - **Two memberships.** A node's role puts it in the control group, in the fleet, or in both. The group is Raft configuration (ADR-0035 point 3); the fleet is `State`. A node with `role = "control"` never joins the fleet, as today. `control remove` changes only the group, and `node remove` only the fleet.
   - **`fleetring node remove <id>` refuses a node that is a voter or learner of the group (decision D7),** with `FAILED_PRECONDITION`: "node '<id>' is a member of the control group; take it out with `fleetring control set-voters` and `fleetring control remove` first". A dead voter it left in place would silently count toward every quorum. The refusal covers only a principal's `Leave` (the `fleet` scope); a node's own `Leave` under its certificate, such as a role-`both` voter's `on_shutdown = "leave"`, passes, because it changes the fleet and not the group. The leader's service checks this against its group view before it submits `Leave`, as it checks bindings (ADR-0031 point 2), and `apply` doesn't change.
   - **A removed control node** can't disrupt the group, because members refuse its Raft calls (`control peer`, ADR-0035 point 13). Once it applies a membership without itself, it stops proposing, logs the removal once, and fails its `control_group` readiness check (point 10).
   - **A one-voter group elects itself at once.** When the only voter in its membership is the node itself, `ControlNode::open` triggers an election instead of waiting an election timeout. A single control node, which is what most fleets and every dev node run, is then ready as fast as today.
   - **Dev mode changes nothing but validation.** A dev node is a one-voter group with the defaults, and `fleetring dev` writes no new setting. With `dev = true`, `Config::validate` also refuses `control.addresses` that aren't loopback and `control.bootstrap = "join"`, which would wait for a second node that dev mode never runs. `AddControlNode` on a dev node refuses a non-loopback address with the same loopback check (ADR-0039 point 3), so a dev node's control log never leaves the machine. Upgrading a dev node from 0.9 migrates its `control.db` like any other's.
   - **`set-voters` may shrink the group to one voter,** with a CLI warning, as the owner decided on 2026-11-03.

10. **Readiness and metrics follow the group.** (Extends ADR-0034 point 4 and its control family.)
    - **Readiness checks:**
      - `control_log`: the proposer and storage are running. `/healthz` turns `503` on an openraft storage error, as it does on `SubmitError::Storage` today.
      - `leader`: passes when this node knows a leader, itself or another, and fails with "no control leader known".
      - `control_group`, new: this node is a voter or learner. It fails while a `join` node waits to be added, and after removal.
    - **Gauges kept:** `fleetring_control_leader` (1 on the leader), `fleetring_control_log_index` (now the last log index), `fleetring_control_snapshot_index`, and `fleetring_control_mailbox_depth` (now the submissions waiting for the proposer or for their responders).
    - **Gauges added:** `fleetring_control_committed_index`, `fleetring_control_applied_index`, `fleetring_control_term`, `fleetring_control_voters`, `fleetring_control_learners`, `fleetring_control_replication_lag_max` (on the leader, the most entries any member is behind; 0 elsewhere), and `fleetring_control_clock_offset_max_seconds`.
    - **Counters added:** `fleetring_control_elections_total` (terms this node saw begin), and `fleetring_control_proposals_total{outcome}` with the closed set `committed`, `refused`, `superseded`, `not_leader`.
    - **`fleetring_control_commands_total`** now counts the commands this node applied, on every member.
    - **Labels** carry no peer ID, and no new name contains "leader" (`observe/names.rs` allows only `fleetring_control_leader`).

11. **The protocol moves to 1.4.** 1.1 went to ADR-0038, 1.2 to metadata (FR-070), and 1.3 to `Database.Session` (FR-066). FR-064's additions are the `Raft` service with `Probe`; `RaftPayload` with fields 2 and 3; `ControlNode`, with `software = 6`; `JoinResponse.control_nodes = 4`; `HeartbeatResponse.control_nodes = 6` (fields 4 and 5 are `forks` and `tombstones`); and the four group RPCs of ADR-0035 point 11. Together they are 1.4. (Replaces the field numbers of ADR-0035 point 14.)

12. **Data nodes and the router reach the group through any of its addresses.** (Extends ADR-0035 point 12.) `[control] addresses` is accepted by data nodes and by the router (FR-066), which has a single `[control] address` today. `control/client.rs`'s `ControlClient` keeps a list of addresses, configured and learned, and parses them as `fleetring-client`'s contexts already parse address lists (ADR-0043).

13. **Per-node settings that leak into commands are documented, and the leader warns on a mismatch (decision D9).** The leader fills some commands from its own configuration, so they can change with the leader:
    - `[control] tombstone_window_ms`: a new leader whose window differs from the state's logs `SetTombstoneWindow` before its next drop, so unequal values flap the window at each leader change. A tombstone already kept keeps its time (ADR-0050 point 5), so the flapping changes no deletion.
    - The `[fork]` limits, recorded with each fork the leader accepts.
    - The default replication factor and durability, which the service fills into a creation that doesn't name them.
    - The delegation issuer pair, per node by design (ADR-0047).

    At readiness the leader compares each setting control state records (the tombstone window, and the `[fork]` limits of the newest fork it holds) with its own configuration, and logs one warning per differing setting, naming both values. The daemon README says to set these equally on every control node. FR-128 (#217) moves fleet-wide settings into control state.

## Amendment 1 (2026-11-26): one batch in flight, and a discarded entry's outcome is unknown

- **Status:** Accepted (2026-11-26, by the owner, after an independent review of FR-064's PR 3).
- **Amends:** point 2 (the screening state's steps 6 and 7, and "S is dropped"), and point 6's list of errors that pause the leader's timers.

The review checked point 2 against openraft 0.10.1's source and found two places where the point's reasoning doesn't hold for that release.

1. **The proposer keeps one batch in flight (owner's answer to Q1).** Point 2 says the screen is exact because, in term T, the leader's log is its log at takeover followed by its own term-T proposals in order, which is exactly what S applied. openraft 0.10.1 breaks the "exactly": it refuses a write on a leader whose leader lease has expired (`ForwardToLeader::empty()` with reason `LeaseExpired`, `core/raft_core.rs` lines 692–700 and `proposer/leader.rs` lines 319–327) while that node stays leader in the same term. A refused proposal never reaches the log, but S already applied it, and a proposal screened after it, before the refusal arrives, is screened against a state holding a command that never took effect. So:
   - the proposer screens and proposes the next batch only after openraft has answered every proposal of the previous one. Submissions keep queuing in the mailbox meanwhile and form the next batch, so group commit stays: a burst still becomes one append;
   - any answer other than `Applied` marks S as poisoned, as PR 3 built it. The next batch is screened against S cloned again from the applied state, which then holds exactly what took effect, since nothing else is in flight;
   - a node that isn't a ready leader screens nothing, so it answers submissions at once while its old proposals wait, and a shutdown stops the proposer even while a batch waits;
   - a batch openraft hasn't answered within four shortest election timeouts (twice the longest), as on a leader cut off from its quorum that still believes it leads, makes the proposer answer what queues behind it `UNAVAILABLE` ("the control leader is catching up; retry", without a leader hint), unscreened and unproposed, so clients try another control node instead of waiting out their deadlines. It screens again once the batch is answered.

   This replaces step 7's "proposals pipeline": the cost is one replication round between batches, not between commands, which the alternative "proposing one command at a time" would cost.
2. **A discarded entry's outcome is unknown (owner's answer to Q2).** Point 2 says openraft answers a truncated entry's submitter `ForwardToLeader`, "which means it never took effect". In openraft 0.10.1 a truncated or purged entry is answered `ClientWriteError::LogEntryDiscarded` (`core/raft_core.rs` lines 2643–2675), and its own comment says another node may still commit it: a later leader that holds the entry can commit it after this node truncated its copy. So:
   - `LogEntryDiscarded` is answered `SubmitError::Unknown`, "the control leader changed before the command was known to be logged; retry", and the `Control` service answers it `UNAVAILABLE` *without* a leader redirect;
   - the leader's timers pause on it as on `Superseded` (point 6), and never end on it;
   - a retry is safe, because the next leader screens a resent command against the state its own log reaches: a command that did commit meets itself as already done (a join of a member already joined, a delegation answered as a resend), and one that didn't is screened afresh. This is the same at-least-once outcome as a lost deadline (Consequences).
   - `ForwardToLeader`, which openraft gives a proposal it never appended (no longer leader, or the lease refusal above), keeps its meaning: nothing happened, `NotLeader`.

   The proposals metric counts `Unknown` as `not_leader`, so the closed set of point 10 doesn't change.

## Amendment 2 (2026-11-28): leader hand-over, the probe's certificate check, and D7 on plaintext

- **Status:** Proposed (2026-11-28, with FR-064's PR 5, after an independent review of it; for the owner to accept).
- **Amends:** point 3's and point 11's lists of the `Raft` service's calls, point 4's checks before a node is added, point 5's leader hand-over, and point 9's refusal of a principal's `Leave` (decision D7). The accepted text above stands; this amendment adds to it.

Building PR 5 against openraft 0.10.1 showed that the hand-over of point 5 needs a call the accepted points don't list, and that openraft treats a leader demoted by a membership change differently from what point 5 assumed. It also settled two details points 4 and 9 left open.

1. **`Raft.TransferLeader` is the service's fifth call** (adds to points 3 and 11). openraft's `trigger().transfer_leader` reaches the target through `RaftNetworkV2::transfer_leader`, whose default answers `Unreachable`, so without the call a transfer can't succeed. Like the other calls it is a `node` call bound to `control peer`. Its payload is FleetRing's JSON, as point 3 requires:
   - the request `TransferLeaderWire { from_leader: <vote>, to: "<hex>", last_log_id: <log id or null> }`;
   - the reply `TransferLeaderReply`, tagged by `result`: `accepted`, `vote_changed { expected, actual }`, or `log_not_flushed { expected, actual }`.

   Four golden vectors pin both forms in `raft-wire-v1`: `transfer-leader.json`, `transfer-leader-reply-accepted.json`, `transfer-leader-reply-vote-changed.json`, and `transfer-leader-reply-log-not-flushed.json`. The receiver refuses, with `PERMISSION_DENIED`, a request whose `from_leader` names another node than the caller's certificate. A member that sends its own vote rather than the leader's changes nothing, because openraft ignores a transfer whose vote isn't the one the receiver holds. The call joins protocol 1.4, which no release has shipped, so the protocol version doesn't change.
2. **When a leader hands over** (extends point 5).
   - A leader that shuts down gracefully hands its leadership to the most caught-up of its other voters that it heard from within one election timeout, by the leader's matched index, with the lowest Raft ID among equals. It waits at most the longest election timeout, then stops anyway. A voter that is down is never chosen, and with no other voter heard nothing is handed over.
   - The daemon hands over while its server still answers, so the new leader's first messages reach it. It doesn't try again once the server has stopped.
   - **`set-voters` hands over too when the new voters leave the leader out.** openraft 0.10.1 lets a leader that a membership change leaves as a learner keep leading; only one removed from the membership altogether steps down (`removed_leader_step_down`). A group whose leader doesn't vote loses that leader at its next restart anyway, so the change hands over at once.
   - The answer to a group change is the group as the node that made the change then knows it, read without a read round. A change that handed the leadership over is therefore never redirected and sent again.
3. **The leader checks the certificate of a node it adds** (extends point 4). A `Probe` reply names its node only as that node says, so before it adds a node the leader makes one TLS handshake of its own to the address. It refuses the node unless the server's certificate names the node the operator asked for. On a plaintext fleet nothing names the server, and the check passes. The check pins the node's identity only when it is added. After that the `control peer` binding judges each call by the caller's certificate, and certificates that mark a node as a control node stay a later decision (ADR-0035 point 13).
4. **D7 on a plaintext fleet** (qualifies point 9). `Leave` is refused when the request boundary resolved the caller as a principal, or when the request carries no boundary context at all (the refusal fails closed). An anonymous `Leave` on a plaintext fleet passes, because nothing tells a node's own leave from an operator's. Only `insecure_plaintext` and the simulation run so. The refusal is audited with the principal and its credential.

## Amendment 3 (2026-11-28): fork actions that act on reports don't wait out the settle window

- **Status:** Proposed (2026-11-28, with FR-064's PR 6; for the owner to accept). It records the owner's choice of option A on FR-118 (#186).
- **Amends:** point 6's settle window, which gated every fork action. Promotions and kept-set releases stay gated as written.

Point 6 gated "fork actions" with promotions and kept-set releases, because each "acts on liveness and on primaries' reports, which a new leader's state can show stale". For most fork actions that isn't so. Gating them all made every fork stand still for a lease duration plus the failover margin (12 s by default) after a control node started or a new leader took over: FR-094's friction F1, listed as a known limit in 0.8.0.

1. **The fork driver withholds only the retries that rest on liveness or elapsed time while the leader settles.** `fleetring_control::fork::actions` takes the leader's place in its window as a typed argument, `Settle::Settling` or `Settle::Settled`, and stays pure. While settling, it withholds exactly two proposals:
   - `RetryForkSeed` with `RetryCause::SeederDown`, which it proposes when the seeder left the fleet or the replica set, or its last heartbeat is older than the heartbeat timeout plus the fork's seeder timeout;
   - `RetryForkSeed` with `RetryCause::AttemptTimedOut`, which it proposes when the attempt has run for the fork's attempt timeout.

   A new leader's state time comes from its own clock while members' heartbeats are still on their way to it, so a live seeder can look down and an attempt overdue, for the same reason leases look expired. These wait out the window, as promotions do. `SeederDown` also covers a seeder that left; it is one cause, and it waits as a whole.
2. **Everything else the driver proposes goes at once.** Each acts only on reports that carry the fork's identity, or on membership, and neither is stale on a new leader in a way that matters:
   - `CompleteFork` needs a completion quorum of reports naming the fork's identity, its attempt, and the source's incarnation, at log epoch 0;
   - `MarkForkReady` needs the bootstrap quorum's reset reports, naming the fork's identity and an epoch the database issued;
   - `ReleaseForkHolders` needs the lease holder's report, at the lease's epoch and the current membership epoch;
   - `RecordForkDiskRefusal` and `FailFork` on a reported permanent failure, and `RetryForkSeed` on a reported seed failure (`TransferFailed`, `PinExpired`) or a disk refusal (`SeederDiskRefused`), each act on a report about this fork;
   - `FailFork` for a source dropped or recreated reads the source's record in control state;
   - `DropForkHolder` acts on a holder's report that it lost its copy, or on a holder that is no longer a fleet member.

   A report reaches control state only through a committed heartbeat, so a new leader holds every report the old one acted on, and a report that is old is still about the fork it names: `apply` checks the identity and the attempt again. Where a retry picks its next seeder, it picks among members that look live, so a stale view can only make it wait for one, never pick a member that looks down.
3. **Deadlines are unchanged.** The driver's `Tick` for a fork past its deadline, or an operation past its retention, was gated with the rest; it now goes at once, as the leader's idle tick, which never waited for the window, already failed deadlines on a quiet control plane.
4. **What stays gated.** Starting a promotion still waits out the window, since it acts on liveness and leases, which a new leader's state shows stale. Releasing a kept replica set waits too, by the owner's choice on FR-118, pending a follow-up: it has the shape of the now-ungated `ReleaseForkHolders`, a lease holder's report at the lease's epoch and the current membership epoch, with no liveness and no time, so the same argument would exempt it. Notices for promotions in progress go out at once, as before.

`fleetring-control`'s `apply`, `State`, `Command`, and their serde forms don't change; only the driver's signature does. A replay of the control log doesn't run the driver, so replays are unaffected.

## Amendment 4 (2026-11-28): the router learns the group's addresses from `Locate`

- **Status:** Proposed (2026-11-28, with FR-064's PR 6; for the owner to accept).
- **Amends:** point 11's list of protocol 1.4's fields, and point 12's learning.

PRs 4 and 5 left the router without the group's addresses: it calls only `Locate`, whose reply named no group, so it never learned more than the address it was configured with.

1. **`LocateResponse.control_nodes = 2`** (adds to point 11). It carries one entry per voter and learner of the control group, with only `address` and `leader` set: the leader's address marked, and every other field of `ControlNode` (the node ID, the voter flag, the matched index, and the software) left empty. The field is additive and joins protocol 1.4, which no release has shipped, so the protocol version doesn't change.
2. **The router and the data client behind `fleetring db` learn from it** as data nodes learn from heartbeat replies (point 12): the addresses join those tried once an address fails, the leader's first, and the client keeps calling the address that answers. A router `Locate` that doesn't answer within a second moves the client on from the address it was sent to, and only from that one, so concurrent timeouts move it once.
3. **What it discloses.** Any caller that may read a database learns where the control nodes listen and which of them leads. A fleet's control addresses are no secret, since every client is configured with at least one. What `DescribeControlGroup` gives only to the `fleet` scope, the members' node IDs, roles, progress, and releases, stays out of the reply.

Moving a member to a new address, which an earlier draft of this amendment proposed, is left for a later amendment: its guards need `Probe` to report the node's membership and last log ID, a check that the old address no longer answers as the node, and the target's Raft ID in every Raft request.

## Alternatives considered

- **Rewriting ADR-0035 in place and returning it to Proposed.** It holds every decision in one file, but the record was accepted, and the project's rule is to amend accepted decisions, never rewrite them.
- **openraft `=0.9.26`.** The first draft pinned 0.9.25 while 0.10 was an alpha. 0.10 is final now, and 0.9 brings `chrono`, `rand 0.8`, and `thiserror 1` into the graph, has no leader transfer and no `expect_leader`, and would make the move to 0.10 a second port. The formats are ours either way, so the move would cost code, not a migration; it costs less now.
- **Keeping all of the first draft's compatibility** (fixtures from 0.3.0 and 0.4.0, the announcement, a down-conversion). It serves fleets on releases nobody runs, and rollbacks nobody makes, at about twice the slim path's cost.
- **A bare path** (a whole-fleet upgrade with no group gate). Cheapest, but a mixed group in R+1 could log a command a voter can't decode, and nothing would refuse it first.
- **The announcement in R.** It closes a race only a mixed group has, and R has none (point 4).
- **The state machine sets `recorded_by` from the entry's leader through the membership.** It needs a lookup from Raft ID to node ID that replay without openraft can't easily do. Verifying the proposer's stamp against `raft_id` is pure.
- **Leaving `recorded_by` advisory and unchecked.** Replicas would agree, since they apply the same payload, but nothing would tie the stamp to the entry's leader.
- **`expect_leader` alone.** It depends on openraft's queue to make every skip happen, and a skip that happens on one node and not in a replay is a divergence. The entry check is deterministic by construction.
- **Screening against the applied state only.** It misses the proposals in flight. A pending join of a node two lines back followed by a join of a node two lines ahead, screened without the first, passes the screen, so the second reaches the log, where `apply` rejects it, and a voter that later replays without software would accept it. That is the hazard of ADR-0038's amendment again.
- **Screening in `apply` alone** (logging everything and letting the state machine reject). Refused joins and refused delegations would be in the log, which ADR-0038's amendment and ADR-0047 point 6.2 rule out.
- **A proposer with its own screening code.** It would have to repeat the single writer's six duties, and would drift from them; one module that both call can't.
- **Proposing one command at a time** (waiting for each to apply before screening the next). It makes the screening state exact without the leader ID, but costs a replication round per command and gives up group commit, at the control plane's busiest path, the heartbeats.
- **Answering a resend from the screening state.** The record may be in an entry that a truncation erases, and a token signed for it would name a delegation revocation can't find (ADR-0047's release blocker).
- **Lease reads.** They save a round per read, but depend on bounds on clock drift.
- **Keeping openraft's serde forms on disk and on the wire** (ADR-0035 as accepted). Less code, but the formats would follow openraft's releases, a mixed group would depend on two openraft builds agreeing on JSON, and every openraft upgrade could force a new `control.db` format.
- **One thread-local generator for every host** (ADR-0035's plan). It replays, but one host's crash shifts every other host's elections, which makes failing seeds harder to read, and it isn't the per-host injected generator ADR-0020 asks for.
- **A `cfg(feature = "simulation")` runtime beside Tokio's.** Tests built with `--all-features` would then run a different runtime from production, and two runtimes would need two sets of tests. One runtime whose seed the environment supplies has neither problem.
- **Recording control nodes' software in `State`.** It would make the gate pure, but it puts the group into control state, which ADR-0035 point 3 keeps out, and it needs a new command. Only the leader needs the group's software, and only before it logs.
- **A fleet feature that gates the Raft group.** Point 4: no fleet member reads the group's entries, and `Probe` keeps nodes without Raft out of the group.
- **Leaving `node remove` free to remove a control voter.** One command would then do half the job, and a dead voter would keep counting toward quorums unseen.
- **Refusing every `Leave` of a group member.** It would also refuse a voter's own shutdown leave, the default for a role-`both` node, which changes nothing in the group.
- **Requiring equal per-node settings across the group** (`Probe` compares them), **or moving them into control state now.** The first refuses a join over a setting whose mismatch is harmless; the second is FR-128's work, and needs commands of its own.

## Consequences

- Rolling upgrades keep ADR-0038's guarantees with a control group from R+1 on. The one new refusal is rolling a control node back to a release that can't read its `control.db`; the first start on R is one-way for a control node.
- Upgrading openraft is a code change behind `codec.rs`, not a migration, and the golden vectors catch any accidental change to either format.
- The single writer's screening becomes a module of its own, `control/screen.rs`, in a pull request with no behaviour change, before any Raft code lands. The proposer then reuses it rather than reimplementing it.
- The leader applies each command twice, once to the screening state and once in the state machine, as the single writer's preview already does for commands that need screening.
- A down control node blocks the first use of a new feature, and its absence from `control list` is the fix, as `node remove` is for a fleet member.
- Control calls stay at-least-once across a lost deadline, as today. A leader change itself loses nothing and duplicates nothing, because every waiting submitter learns whether its entry was applied, truncated, or superseded. A delegation resend is answered only from committed and applied state.
- Some leader state lives only in memory and is lost on a leader change: the fork driver's seed progress, the failover's notified promotions, and drop notices (which tombstones in heartbeat replies cover). Clients see an availability blip, never a safety issue.
- Every heartbeat is a replicated entry, and heartbeats now carry unreported copies, free disk, and seed progress, and their replies forks, tombstones, and revocations. Group commit keeps syncs few; heartbeats off the log stay roadmap E4.
- The time rules assume two things of the leader's wall clock, and break only availability when either fails, since epochs fence and W + Q > R (ADR-0018):
  - **No forward step after readiness.** The settle window protects only the start of a term. A forward step of the leader's wall clock after its window has passed moves state time forward at once, so every lease can look expired together, and promotions start without a settle window.
  - **No running fast.** If the wall clock runs faster than the monotonic clock by more than the ratio of the lease duration to the renewal interval (5 by default), leases expire between a primary's renewals however long the window was.
- A leader whose clock ran ahead can delay failovers after it loses leadership by up to its skew, and denylist entries are forgotten by state time, so they can go up to the skew early, as with one control node today. The new clock-offset gauge shows it, and the README asks for NTP. FR-065's control-group step skews control clocks by up to ±60 s, beyond `MAX_CONTROL_LEAD`, so delegation is refused for a while after a fast leader is replaced; that is availability, as above.
- The plan grows a fixture step that writes `control.db` files with 0.9.0's code at its tag, and an upgrade check, `UpgradeError::ControlFormat`.
- The injected enabling commands stay until FR-127 (#216) replaces them with explicit feature finalization; per-node settings stay per node until FR-128 (#217).
- ADR-0035's status line reads "Accepted (points 1, 3, 4, 5, 6, 7, 8, 9, 11, 12, 13, 14, 15 amended by 0040)", and FR-064's plan follows this record wherever the two differ.
