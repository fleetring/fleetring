# ADR-0031: Node-to-node calls are bound to placement: a node acts only on databases placed on it, at epochs control state gives it

- **Status:** Accepted (2026-11-03); points 1, 2, and 4 refined by the [amendment](#amendment-2026-11-03-fr-050) below; point 4 and its stream binding extended by [amendment 2](#amendment-2-2026-11-11-fr-102-a-membership-change-hands-a-replica-set-over-on-joint-quorums) (accepted 2026-11-12)
- **Date:** 2026-11-02
- **Related:** ADR-0017 (control state machine), ADR-0018 (epochs), ADR-0022 (failover), ADR-0025 (principals and scopes), ADR-0026 (scope enforcement, proposed with FR-047); tickets FR-046, FR-047, FR-050

*Note (2026-11-08):* [ADR-0046](0046-forks-name-an-incarnation-and-complete-on-a-write-quorum.md) (accepted 2026-11-10, its amendment of 2026-11-12 accepted the same day) proposes one more binding, **`seeding`**: under it, the source's primary serves a fork's seeder, and the seeder serves the fork's other replicas, on `Replication.Snapshot`, each checked against the fork's full identity (ADR-0046, points 4.1 and 4.4). It also proposes that, from a fork's completion until it is ready, `replicas_of` (point 4) returns the fork's recorded holders rather than its ring's replica set (ADR-0046, point 3.10). Both are proposed, not part of this decision, until ADR-0046 is accepted. The text below is unchanged.

*Note (2026-11-09):* FR-085 builds both, for forks only: the RPC table, the protocol's `Binding:` line, and the daemon README name `Replication.Snapshot`'s binding `follower or seeding`, by whether the request names a fork, and a refusal under the second names `seeding` in its `fleetring-binding` metadata. The primary of a seeded fork that isn't ready streams to, and counts toward its write quorum, only the fork's recorded holders. Nothing else in this record changes.

## Context

FR-046 made node identity unforgeable: a node's certificate names its ID, and the membership calls refuse a request that names another node. FR-047 narrows node certificates to node calls. But a node call still accepts any node for any database. A stolen node key can open a `Replicate` stream to any replica at a higher epoch, which the replica records durably, fencing the real primary out, and then have it apply forged batches; fence any replica for a promotion that doesn't exist; read any database whole through `Snapshot` or `Fetch`; and report itself as a candidate. Epochs contain much of this, since a forged epoch is above nothing the control plane granted, but no code verifies that the node presenting an epoch is the one control state gave it to.

Kubernetes' NodeRestriction admission plugin is the model: a kubelet's credential may only modify its own Node object and the pods bound to it. For FleetRing the equivalent is placement: a stolen node key should reach only the databases placed on that node, and only in the role control state gives it there.

Three constraints: `apply` stays pure and unaware of who called (ADR-0025 point 5); replicas keep accepting their primary while the control plane is down (ADR-0018 point 6); and placement is in flux during membership changes, and later during live migrations (roadmap E6), when an old and a new replica set are both legitimate for a while.

## Decision

1. **Every node call names a binding, and the receiver checks it before touching state.** A binding says which role the calling node must have for the database the request names. The requirement table of ADR-0026 gains a binding for every `node` row, and a test refuses a node RPC without one:

   | RPC | Caller | Binding | Checked by | Against |
   |---|---|---|---|---|
   | `Control.Join`, `Heartbeat`, `Leave`, `Drain` | the node | **self**: the request names the caller | control service | certificate (FR-046) |
   | `Control.AcquireLease` | the node | **self**, and a live, undraining replica-set member | control service, then `apply` | certificate, then control state (existing `NotInReplicaSet`) |
   | `Control.RenewLease` | the node | **self**, and the holder at the epoch | control service, then `apply` | certificate, then control state (existing `NotLeaseHolder`) |
   | `Control.StartPromotion` | a node | **replica**: in the database's replica set | control service | control state |
   | `Control.RecordFenced`, `CompletePromotion` | the candidate | **candidate** at the request's epoch | control service | control state |
   | `Control.TransferLease` (from a node) | the holder | **holder** at the current epoch | control service | control state |
   | `Replication.Replicate` | the primary | **holder or candidate** at the stream's epoch, and the receiver is a replica | receiving follower | its epoch record, else control state |
   | `Replication.Fence` | the candidate | the request's `candidate` is the caller, and **candidate** at the epoch | receiving replica | control state |
   | `Replication.Fetch` | the candidate | **candidate** the replica was fenced for at the epoch | receiving replica | its epoch record |
   | `Replication.Snapshot`, `Repair` (FR-045) | a follower | **follower**: one the primary streams the database to, at the epoch it serves | primary | its own follower set |
   | `Replication.Promote` | the control node | the receiver is the **candidate** at the epoch | receiving node | control state |

2. **The control node checks against its state before it submits; `apply` doesn't change.** A promotion's candidate, a lease's holder at an epoch, and a database's replica set are all in control state. The service reads the published state and refuses before logging anything. For the rows that name an epoch (candidate, holder), the answer for that epoch never changes once given (an epoch has one candidate and one holder), so a check made against one state stays true when the command applies later, under Raft too. `AcquireLease` and `RenewLease` are already bound: FR-046 checks the requesting node against its certificate, and `apply` already requires a replica-set member or the holder. No command gains a caller field, so logs replay unchanged.

3. **A data node learns who may lead an epoch from control state, once, and then trusts its durable record.** A replica already records durably the highest epoch it has seen and the node it named as holder (ADR-0022 point 4). Before it records a *new* holder for an epoch, from a stream or a fence, it asks the control plane who leads the database now: `Locate`, whose `Placement` gains the candidate of a promotion in progress. It accepts the caller only if control state names it the holder or the candidate at exactly that epoch. Once recorded, the pair is trusted without asking again, so a follower that restarts while the control plane is down still accepts its primary. A caller the record doesn't know, while the control plane can't be reached, is answered `UNAVAILABLE` and retries; becoming a new primary needs the control plane anyway.

4. **Placement in flux: both rings count for one membership epoch, and epochs decide the rest.** Holder and candidate checks are per epoch and don't depend on the ring. The ring-based checks (a follower that a stream reaches must be a replica; a node that asks a primary for a snapshot must be one of its followers) accept a node in the replica set under the receiver's current ring or the ring before it, so a membership change, where nodes publish the new ring at different moments, never refuses a legitimate stream or snapshot. A database's replica-set membership is decided in one function, `replicas_of`, which live migration (E6) extends with its target replica set until its cutover epoch, after which only the new set counts.

5. **Refusals are `PERMISSION_DENIED`, name the binding, and are audited.** The message is `<Method> refused for node '<node>': <reason>`, where the reason is one of `the request names node '<other>'`, `not a replica of database '<db>'`, `not the holder of database '<db>' at epoch <e>`, `not the candidate of database '<db>' at epoch <e>`, or `not a follower of database '<db>' on this node`. The response carries `fleetring-binding` metadata (`self`, `replica`, `holder`, `candidate`, `follower`) so that tests and tooling don't parse messages. Each refusal is logged once on the `fleetringd::audit` target with the node, method, database, epoch, and binding, as FR-047 logs scope refusals. A check that can't be made because control state is unreachable is `UNAVAILABLE`, never `PERMISSION_DENIED`.

6. **What a stolen node key can still do.** Act as that node: serve, follow, and lead the databases placed on it, at the epochs control state gives it; report its own positions in heartbeats (reports from outside a replica set are recorded but never make a node a candidate and never show in `Locate`); and join or drain itself. It can't stream, fence, fetch, snapshot, or promote any other database. Revoking a node is removing it from the cluster and refusing its certificate (FR-046's authority rotation), as today.

## Alternatives considered

- **Lease certificates signed by the control node,** carried in every stream and fence and verified offline. No control round trip at all, but it needs a signing key on the control node, its distribution to every node, and a rotation story, to save one `Locate` per new epoch per replica.
- **Checking caller roles inside `apply`,** with a caller field on every node command. It would put identities into the replicated log, against ADR-0025 point 5, and change what old logs replay to, for a check the service can make against the same state (point 2).
- **Relying on epochs alone.** Epochs stop a deposed primary; they don't stop a node that was never a holder from presenting the current or a higher epoch first.
- **Refusing everything during membership changes until all nodes publish the same ring.** Simple, and it would stall replication on every join and leave.

## Consequences

- The control service gains four state checks before submitting; replication gains an epoch-authority check before recording a new holder, one `Locate` per new epoch per replica, and a ring check for streams and snapshots. `Placement` gains one optional field. The control crate and the logs don't change.
- `fleetringd::auth::RPCS` rows for node calls gain a binding, stated in the proto and the daemon README like the scopes, and enforced by the same kind of table test.
- `SECURITY.md`'s threat model (FR-048) can state the blast radius of a stolen node key as the databases placed on that node.

## Amendment (2026-11-03, FR-050)

Implementing the decision found four places where it was silent or too loose. Each refinement keeps the decision's intent and is the more conservative reading; the text above stands.

1. **The previous ring doesn't make a node a follower (point 4).** A view keeps the ring before it until the next membership change, not just while one change propagates: right after a cluster forms, the previous three-member ring names every node a replica of a database the four-member ring places elsewhere. Counting it for `Snapshot` would let a stolen key read a database it doesn't host for as long as membership stays still, which the simulation showed. So a primary serves a snapshot only to a follower on its current ring, or to a member of the replica set control state names now (asked through `Locate` only when the caller isn't on the ring), which also covers a new replica whose primary hasn't published the newest ring yet. A node that doesn't serve the database at the epoch answers a replica with `FAILED_PRECONDITION`, as before, and anyone else with the `follower` refusal.
2. **A stream's receiver may also be a replica by control state (point 4).** The receiver checks itself against its current ring, the ring before it, and the replica set control state names in the same `Locate` that checks the holder. A replica added by a membership change that a primary reaches before the replica has published the new ring is then accepted, instead of refused until it catches up. The previous ring stays here: the sender has already passed the holder check, and a holder streams only to its own replica set.
3. **Stale epochs are stale, not unbound (points 1 and 5).** When control state has moved past a stream's or a fence's epoch, the call is answered `FAILED_PRECONDITION` (superseded), not `PERMISSION_DENIED`: a deposed primary or a superseded candidate made it legitimately. An epoch at or beyond control state's that the caller doesn't hold, or isn't the candidate of, is refused for its binding. For `Fence` and `Promote`, the holder at the epoch counts as well as the candidate, since a promotion's candidate becomes its holder when it completes and a fence or notice sent before that may arrive after. On the control node, `RecordFenced` and `CompletePromotion` for an epoch past the database's are refused for their binding, since a promotion to that epoch could start before the command applies; for an epoch whose promotion is over or never was, `apply` answers as before.
4. **`TransferLease` is bound to the lease's holder at the lease's epoch (point 1).** A draining node whose promotion stalled hands its lease over again, and its lease is then older than the database's epoch; `apply` still refuses a transfer while a live promotion is in progress. The lease changes holder only when a promotion completes, whose candidate is never draining, so a check made before the command applies can't transfer another node's lease.

Two clarifications that change no decision: `Leave`, `Drain`, and `TransferLease` are client calls a daemon makes as itself (ADR-0026), so they carry a binding although their requirement isn't `node`, and the table test requires a binding on every `node` row and allows one only on rows nodes may make. A plaintext connection carries no identity, so `insecure_plaintext` daemons make no binding checks, as they make no scope checks.

## Amendment 2 (2026-11-11, FR-102): a membership change hands a replica set over on joint quorums

- **Status:** Accepted (2026-11-12, by the owner); revised on 2026-11-12 after its reviews.
- **Amends:** point 4 of this record, and its stream binding (point 8 below). It changes which replica set ADR-0018's promotion quorum (point 4) and ADR-0022's promotion (point 1) fence after a membership change, and what a primary counts toward a write; their rules don't change. It adds a fleet feature under ADR-0038's point 4, and gives every database the hand-over ADR-0046's point 3.10 gives a ready fork.
- **Related:** ADR-0017, ADR-0018, ADR-0022, ADR-0038, ADR-0046 (point 3.10, as built); tickets FR-085, FR-102 (#157).

### Context

Point 4 lets both rings count for the binding checks, so that a stream or a snapshot isn't refused while nodes publish a new ring at different moments. It says nothing about quorums, and neither does ADR-0018: a membership change (a join, a leave, a drain's leave, or a member's new weight) moved a database's replica set in control state at once, while its primary went on counting the old set's write quorum until it next read the ring. With R = 3 and W = 2, {P, A, B} becomes {P, A, X}; P acknowledges a write that P and B hold; P crashes; the promotion fences Q = 2 of {P, A, X}, takes A and X, and neither holds the write. The simulation reproduced it on every seed it was given (`membership_lag.rs`, seed 157 first): an acknowledged write was lost. ADR-0046's as-built note on point 3.10 closed the same window for a ready fork's holders with joint quorums; this amendment does the same for every database.

### Decision

1. **A membership change never changes the replica set promotions fence; only a release does.** When a join or a leave moves the placement of a database that has had a lease, and that isn't a fork whose recorded holders are its replica set, control state keeps the set it moved off, in its preference order (`Database::kept_replicas`). `State::replica_set`, and so `replicas_of`, the candidates of `StartPromotion` and `TransferLease`, the members `RecordFenced` and `CompletePromotion` count, `AcquireLease`'s check, and `Locate`'s `replicas`, answer the kept set until it is released. A second change before the release keeps the first set; a change that moves placement back onto the kept set stops keeping it. A database that never had a lease has acknowledged nothing, and follows placement at once. `apply` compares placement under the ring before the change with the ring after it, and only when the membership epoch grows, so a rejoin that changes nothing costs one ring.
2. **A primary counts the replica sets control state showed it.** `Placement` gains `placed_replicas`, where the ring places the database, and `membership_epoch`, the epoch of the state it was read from. A primary counts the write quorum of each distinct set among them toward every write: W of the kept set and W of placement while they differ, W of placement otherwise. A ready fork's primary that still sees its holders kept counts them beside every set control state showed, so a release of the holders it hasn't seen yet, and a membership change after that release, are both covered; it follows the sets before the fork's view, from the same placement, wherever it follows the view, and its `PlacementCaughtUp` names the membership epoch of the placement it counts, not its ring's. A primary reads the placement when it starts to lead; again as soon as its ring is newer than the placement it counts; and every few retry intervals while a set is kept, to learn of the release. It never replaces a placement with one read at an earlier membership epoch, nor with one of another incarnation than its copy records. A write that isn't held back for a short group is refused with `UnderReplicated`, as for a ready fork.
   - *Under a control node that shows no sets* (0.7, or one rolled back before the feature was enabled), a primary counts placement by its ring, but never a ring newer than the last `Locate` that answered: it pins the placement of the ring it had when it asked, and while its ring is newer it counts the pinned placement and its current ring's both, until a `Locate` asked under the current ring answers. An answer without sets replaces sets control state showed only when no placement with sets was followed after the question was asked, so an answer from before the control node's upgrade never undoes one from after it, and a primary under a control node that was rolled back follows it at its next read. So "never its own ring" holds once the control node shows sets; before, the primary's ring decides only together with the last answer.
3. **The report.** Once placement's write quorum holds everything the primary has committed, read after it began counting both, it reports `DatabaseStatus.replicas_caught_up { incarnation, epoch, membership_epoch }`, naming the membership epoch of the placement it counts. A report without `membership_epoch` reads as absent.
4. **The release.** The control node's timer proposes `ReleaseKeptReplicas { database, incarnation, epoch }` (`State::releases_due`), up to 64 per tick and together, so that a join that moves many databases doesn't hold up the promotions the same timer drives; and `apply` accepts it only for the database's incarnation, while it keeps a set, at the epoch of its lease with no promotion in progress, when the lease holder's latest report names that epoch and the current membership epoch. From then on the database follows placement.
5. **Why it is safe.** Call the set promotions fence S. By point 1, S changes only at a release. A primary counts S at every moment it acknowledges a write:
   - *It learned S from control state.* It counts what one placement showed, which named S and placement then; a membership change leaves S as it was, and the primary goes on counting what it counted until it reads a newer placement, which still names S. A placement read at m before a release at m names the kept set and placement both, which covers the new S; one read after control state moved past m shows the release, since a release at m happens only while m is current; and a primary never goes back to a placement older than one it reported about.
   - *It started under a control node that shows no sets.* Such a control node keeps no set, and once the feature is enabled a rollback to one is refused (point 6), so its S was placement by its ring when it answered. The primary counts that placement, pinned, until a `Locate` asked under a newer ring answers. The upgraded control node's first change that keeps a set keeps the set it moved off, the placement the pinned ring gave if no change came between, and the primary counts the pinned set beside its new ring until the answer, which shows the sets. A change made by a control node that showed no sets, before the feature was enabled, moved S at once, and its window is the one point 6 leaves open in a fleet that isn't upgraded yet.
   - *It leads a ready fork whose holders are kept.* It counts the holders, which are S until `ReleaseForkHolders`, beside every set the placement it last followed showed; that placement names the set the release moves S to, and a later change keeps that set, which the next read shows.

   So until a release every acknowledged write reached W of S, and a promotion's Q of S intersects it (W + Q > R). A release at membership epoch m needs the primary's report about placement at m, which says that W of placement holds every batch it had committed, and every batch it publishes after it adopted that placement counts placement's write quorum; so after the release, every acknowledged write reached W of the new S. A promotion during the hand-over fences Q of the kept set, and its candidate, which reads the placement first, hands over the same way at its own epoch. The simulation checks it after every step that changes S, not only at promotions: each write acknowledged before the change is on W of the new S (`AcknowledgedWritesFenced`).
6. **Upgrades (ADR-0038).** The behaviour is the fleet feature `handover`. A membership change keeps a set only once the feature is enabled, and only the logged command `EnableHandover` enables it: the control node's writer logs it just before the first join or leave that would move the placement of a leased database (`State::handover_due`), once every member, live or down, supports the feature. The control node logs the enabling on the audit target, since it closes rollback. From then on a member without it, such as a 0.7 node, can't join, and `upgrade --rollback` below 0.8 is refused, naming it: a 0.7 primary would count only its ring and never report, so a kept set would be short of its writes and never released, and a 0.7 control node would drop the kept set it doesn't know.
   - *Why a command, not the members' software.* The first draft enabled the feature, and kept the set, inside the membership change's own transition whenever every member's recorded software supported it. But a control node of 0.6 or 0.7 records feature names it doesn't know (ADR-0041, amendment 1), so its log already satisfies that condition once its members run 0.8, and a 0.8 control node, which recovers from a snapshot and replays up to a thousand logged commands with its own `apply`, would replay that log to kept sets its writer never had, re-deciding promotions in the tail against them. With the command, what a change does depends on the log alone, and a log written without it replays to its writer's states. No other fleet feature changes a transition by members' software: every other one is enabled by the command that needs it, and the transitions that read a feature read whether it is enabled, which the log decides.
   - *Data nodes are upgraded before the control node* (ADR-0038, point 9), so 0.8 primaries lead under a 0.7 control node first; point 2's pinned ring covers the moment the control node starts to show sets, and their first read under it learns them.
   - *A control node rolled back to 0.7 before the feature was enabled* answers placements without sets again; each 0.8 primary follows the answer at its next read, which a ring change or a kept set's poll brings, and counts placement by the ring pinned there. `Replication::replica_set`, which a promotion's candidate reads after asking control state, answers the ring once a placement without sets was followed, never sets a rolled-back control node no longer shows.
   - *In a mixed fleet*, until the feature is enabled, a membership change moves replica sets at once, as in 0.7, and the window this amendment closes stays open. A primary under a control node that shows sets also counts its ring while that is newer than the sets it counts, until its read answers, which covers such a change in that window from the moment its ring shows it. `ReleaseKeptReplicas` needs the feature, and reports are recorded only once it is enabled. The new state field and report are left out when empty, so states and logs from before the feature load and reserialize unchanged, and replay to the same states (`a_log_written_without_keeping_replays_to_the_writers_state`).
7. **What it costs, and the wait that doesn't end.** For a few heartbeats after every membership change that moves a leased database, its writes need both quorums, and are refused while either lacks W reachable replicas, as while placement's new members take their snapshots. A primary reads its database's placement once per serve, once per membership change, and every few retry intervals while a set is kept. `fleetring_control_kept_replica_sets` counts the databases that keep a set, and `db locate` prints `placed on:` (`placed_replicas` in JSON) beside the kept replicas.
   - *A kept set that lost its quorum waits until a member comes back.* With {P, A, B}, B fails and is removed, and P fails before the release: the promotion needs Q = 2 of the kept set, and only A is live. Removing members no longer recovers, since a removed member stays in the kept set: removal would shrink R and Q there, and a promotion of the smaller set could miss a write the larger one's quorum held. The database stays unavailable, and the wait is permanent unless a member of the kept set comes back. In this order: restart P, whose disk holds every write it acknowledged; else restart B on its old disk; and only when neither disk survives, start a node under B's ID on an empty disk, with a certificate for that ID. It joins again, counts in the kept set, and a promotion fences A and it and adopts A's log, so every write that only P and the old B held is forfeit; restarting P would have kept them. The daemon README's runbook says so, and a simulation runs the last resort (`a_kept_member_back_on_an_empty_disk_lets_the_promotion_complete`). An operator release that moves a kept set onto placement without its primary's report, audited, with a reason, and accepting that writes only the lost members held are gone, is deferred to its own ticket.
8. **Bindings (point 4).** A `Replicate` stream's receiver, and a node asking a primary for a `Snapshot`, counts as a replica also when it is in the placement control state names beside a kept set, as it does when it is in the replica set: the primary streams to both sets, and a new member it reaches before publishing the new ring, or one that asks before the primary has read the newest placement, is refused otherwise. A seeded fork's receiver still counts only under its recorded holders.
   - *A member removed with `Leave` stays in the kept set, but counts as down there.* It stays in R and Q (point 7). Bindings would let it in (a follower's `Snapshot` check accepts control state's replica set, and the placement beside a kept set, as a stream's does), but control state has no address and no liveness for a node that isn't a member: `Locate` shows it down without an address, a primary's stream to it fails for want of an address, and a promotion's fence of it fails. So until the release a kept set with a removed member tolerates one failure fewer: after a drain and a leave of B, its databases tolerate no further failure until their primaries hand over, and a hand-over that can't finish keeps them so. Removal isn't revocation; revoking a node is removing it and refusing its certificate (point 6). Keeping a kept member's last address, so that it counts while it runs, is a follow-up ticket.

### Alternatives considered

- **Polling sooner.** A shorter heartbeat narrows the window but never closes it: a primary cut off from the control node never polls.
- **Fencing both sets at a promotion,** Q of the old set and Q of the new, with no change on the primary. Control state would still need to remember the old set and to know when to forget it, which is the release; and a promotion would need more replicas live.
- **A second mechanism beside the fork's.** ADR-0046's hand-over already counts both quorums, reports, and releases; this amendment reuses its rules, its counting on the primary, and its report-then-release shape. The kept set is a field of its own, not the fork's `holders`, so that a report or a command about a database never reads as one about a fork identity (ADR-0046, point 12 (d)).
- **Dropping removed members out of the kept set.** Shrinking a kept set changes R and Q under writes acknowledged on the larger set (point 7).

### Not changed

A ready fork keeps its holders exactly as ADR-0046 says, and a membership change doesn't keep a set for a fork whose holders are its replica set. `RenewLease` still doesn't check the replica set: a primary that a release leaves off placement goes on leading, counting placement's write quorum, which is safe, and nothing hands its lease to a placed node (noted on FR-102, a separate ticket).
