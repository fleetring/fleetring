# ADR-0045: `db watch` tails a database's recorded row changes from its primary, one transaction per line, resumable by position

- **Status:** Proposed
- **Date:** 2026-11-07
- **Related:** ADR-0016 (engine adapters), ADR-0018 (leases and quorums), ADR-0022 (failover), ADR-0023 (durability modes), ADR-0024 (logical change capture), ADR-0025 and ADR-0026 (principals, scopes, enforcement), ADR-0028 (replicated sink positions), ADR-0031 (node calls bound to placement), ADR-0038 (version compatibility), ADR-0041 (agent kit, MCP), ADR-0043 (the CLI, point 9); tickets FR-075 (#103, item 7), FR-039, FR-041

## Context

#103 asks for `fleetring db watch <db>`: tail a database's change stream from the command line, for agents and debugging, with `--json`, refused without the `stream` scope. Its acceptance criterion is that a write's rows arrive within a second. ADR-0043 (point 9) deferred it to its own record, because the RPC behind it has questions of its own: which replica serves it, failover, resuming, slow consumers, the scope, and how it relates to sinks' positions.

What exists:

- **Capture.** A database that some logical sink names records its row changes inside itself, in `_fleetring_cdc`, through temporary triggers on the primary's write connection (ADR-0024). The rows commit, replicate, and survive with the data, so a promoted follower holds the record of everything the old primary acknowledged. A database no logical sink names records nothing. Dev mode's configuration names every database in a logical file sink, so on a dev node every database records.
- **Reading.** `LogicalChanges::changes_between(after, until)` returns the rows of the transactions that started at or after `after` and before `until`, flattened, with no transaction boundaries and no check that rows weren't pruned.
- **Pruning.** Rows are deleted once every logical sink of the database has delivered them: pumps report their positions, the lowest becomes `release`, and the next write transaction (at most every 64) deletes the rows of transactions that started before it (ADR-0024 point 6, ADR-0028 point 7). Nothing in the database records how far the table was pruned, so a reader can't tell "nothing was recorded between these positions" from "it was recorded and pruned".
- **Sinks.** A pump reads from the primary, never past the write quorum's position, and delivers at least once, in commit order; its position is a mark in the database (ADR-0028).
- **Scopes.** `stream` is an action of its own, implied by no other (ADR-0025); `NodeStatus` already shows a principal its sinks' progress with `stream`. A server stream opened with a token ends when the token expires or is revoked (ADR-0026 point 7).
- **`WatchLeases`** is the closest existing stream: a snapshot message first, then events, through a bounded buffer whose overflow ends the stream with `RESOURCE_EXHAUSTED`.

The owner proposed defaults: a live tail by default and a resume from a position only if the node still holds the changes from it, refusing otherwise with the oldest position available and never skipping; served by the primary, with the CLI reconnecting through placement after a failover and resuming after the last position it printed, at least once; scope `stream`; one transaction per line; bounded buffering per watcher and a per-node limit; a clear error against an older node; and a recommendation on MCP.

## Decision

1. **A new server stream on the `Database` service: `WatchChanges(WatchChangesRequest) returns (stream ChangeUpdate)`.** The request names the database and, optionally, a position to resume after (`after`). The first message is `ChangesOpened`: the position the stream starts after, the primary that serves it and its lease epoch, and the database's capture mode. Every later message is one `ChangedTransaction`: one committed transaction's row changes, with its `start` and `position` (point 5) and the epoch of the primary that served it. A transaction whose statements changed no captured row (a `CREATE TABLE`, an `UPDATE` that matched nothing) has no rows in the record, and produces no message.

2. **It serves what logical sinks read, and nothing new is captured for it.** The primary reads the recorded changes of ADR-0024 through a new `LogicalChanges` method, `transactions_after(after, until, limit)`, which returns whole transactions, each with its start and end, and refuses, instead of returning less, when the record no longer holds every transaction after `after` (point 4). A database that doesn't record its changes on the serving node, because no logical sink there names it, is refused with `FAILED_PRECONDITION` saying so; an engine that can't record row changes answers `UNIMPLEMENTED`. `db watch` doesn't turn capture on: recording is per node configuration, every node must agree on it for a failover to continue the record (ADR-0028 point 7), and rows recorded for a watcher alone would have no sink to release them after it leaves. Capture without a sink is a follow-up (see Consequences).

3. **The primary serves it; any other node redirects, as for `Query`.** The handler routes the request as every data call does (ADR-0031), so a follower answers with the primary's address and the client follows. It drops the request's admission at once, so a long-lived watch never holds up a drain. The stream reads only up to the write quorum's position, as a pump does, so with `acks = quorum` or `all` a watcher never sees a write that a failover could lose; with `acks = local` it can, as a sink can (ADR-0023). A read covers at most 256 transactions or 10,000 rows, whichever comes first, but always one whole transaction, since a line is a transaction; a single transaction is held whole in memory, as a sink's batch is. Time reaches the stream only through `tokio::time`, to recheck every second that the node still serves the database; nothing about safety depends on it.

4. **Start point: a live tail by default; `--from <position>` resumes after that position, if the primary holds every recorded change after it; otherwise a refusal naming the oldest position it holds. Never a silent skip.**
   - **Live:** the stream starts after the end of the primary's log when it opens, and `ChangesOpened` names that position, so a client can resume from it even before it has printed a transaction.
   - **Resume:** `after` must be a position of the database's log no further than its end; a position past the end is refused with `OUT_OF_RANGE` (with `acks = quorum` this can't happen after a failover; with `acks = local` it means acknowledged writes were lost). A malformed position is `INVALID_ARGUMENT`.
   - **Held, exactly.** Whether every recorded transaction after a position is still there is decided by the record itself. The SQLite adapter keeps a *floor* row at the front of `_fleetring_cdc`: a commit-type record whose `table_name` is the reserved `_fleetring_floor` and whose `start` is a position from which every transaction is both recorded and retained. The first write transaction after recording starts writes one when it finds the table empty, at its own start; each prune, which deletes every row of the transactions that started before the released position, writes one at that position, in the id just freed in front of the first row it keeps. `change_id`s stay contiguous and `start` never decreases along them, so the reads and the binary search of ADR-0024 are unchanged, and the floor costs one row per prune. A position is held when it is at or after the floor. A table written by an older release has no floor until its first prune under this one; for it the start of its oldest row stands in, which is conservative: it may refuse a position that was held, never accept one that wasn't. An empty table holds nothing after a position the log has moved past. Older releases read a floor as a commit record, which they skip.
   - **The refusal** is `OUT_OF_RANGE`: `the changes of notes after <position> are no longer held: the oldest position its primary holds changes from is <floor>`, and the CLI's hint is to watch from that position with `--from`, or from now without it.
   - **Rechecked on every read.** The check and the read run as one request on the database's actor, which serializes them with writes and prunes, so no prune falls between them. A stream whose next read finds its position below the floor ends with the same `OUT_OF_RANGE`, never by skipping ahead.
   - **Not detectable:** a gap left by a node that stopped recording the database (its configuration stopped naming it in a logical sink) and started again. The record has no way to show it, and sinks share the blind spot (ADR-0024). Sink configuration must be the same on every node, as ADR-0028 point 7 already requires.

5. **Each transaction carries two positions: `start`, where it began, and `position`, where to resume after it.** `start` is the log position the transaction started from, the same on every replica. `position` is past the transaction and at or before the next recorded one: the next recorded transaction's start, or the end of the range the read covered. Resuming after `position` continues with the next recorded transaction, so a client resumes after the last `position` it printed. Two reads may give the same transaction different `position`s, both valid; `start` identifies it. The de-duplication rule a consumer applies is therefore: **drop a transaction whose `start` is less than the `position` of the last transaction kept**, comparing positions as bytes (their hex strings compare the same way for one engine, as positions are fixed-width). The commit time isn't part of the record: ADR-0024's adapter reads no clock, so `change_time` was left out, and the output has no time field. An engine that records one (Turso's `change_time`) can add it as a field later.

6. **When the primary changes, the stream ends and the client resumes elsewhere; delivery is at least once.** A stream ends with `UNAVAILABLE` once its node stops serving the database at the epoch it opened under: a drain, a lost lease, a failover, or the node stopping. The message names the position to resume after. `db watch` then locates the database again through the control plane, opens a new stream on the new primary with `after` set to the last position it printed (or the position `ChangesOpened` named, if it printed nothing), and goes on. Each reconnection waits with backoff from 100 ms to 2 s; after 30 s without a stream opening, the command exits 4 with the position to resume after in its hint. With `acks = quorum` or `all` the new primary holds every transaction the old one served (ADR-0018), with the same positions, so nothing is skipped and, in practice, nothing is repeated; delivery is still specified as at least once, with point 5's rule to discard repeats, since a client may resume from an older position than it needs, and an `acks = local` failover can lose what was printed.

7. **A watcher is not a sink.** It keeps no mark and is invisible to the database's record; its position is what the client last printed. While it is connected, its position joins the positions the release of row changes takes the lowest of (ADR-0024 point 6), so sinks that have moved on don't prune the rows it is about to read. It holds back no checkpoint, because it reads the change table, not the log. A disconnected watcher holds nothing, so a resume after the sinks have pruned past its position is refused (point 4). A release computed before a watcher registered can still land after it, since releases are asynchronous; point 4's recheck turns that race into a refusal, not a skip.

8. **Resources are bounded per watcher and per node.**
   - **Per watcher:** a buffer of 64 transactions between the reader and the connection. A watcher that lets it fill is cut off: the transactions already buffered are sent, then `RESOURCE_EXHAUSTED` naming the position to resume after, and the stream ends. `db watch` resumes from its last printed position, as after a failover, so a reader that is only briefly slow loses nothing; one that is always slower than the writes cycles through reconnections without the node's memory growing. The token guard of ADR-0026 point 7 adds its own bounded buffer, so a watcher's memory is bounded by those buffers and one read.
   - **Per node:** at most 64 watchers at once. The next one is refused with `UNAVAILABLE` (`node data-1 already serves 64 change watchers; retry later`), which the CLI reports with exit 4. The limit is a constant for now; a configuration setting can follow if a deployment needs another number.

9. **Authorization: `stream` on the database, and nothing else implies it.** The RPC table gives `WatchChanges` the requirement `Database(Stream)`, with no placement binding, checked by the handler against the database the request names (ADR-0026 point 1). `read`, `write`, and `admin` don't imply `stream` (ADR-0025), so a principal that may only read a database can't watch it, and the refusal is `PERMISSION_DENIED` (`WatchChanges needs stream on 'notes'`), exit 3. A node certificate has no scopes, so a node can't watch (ADR-0026 point 9). A stream opened with a token ends with `UNAUTHENTICATED` once the token expires or is revoked.

10. **`fleetring db watch <db> [--from <position>] [-o table|json|jsonl | --json]`.** It belongs to the `db` noun, in the Databases group; `watch` is the verb that follows a stream until interrupted (`docs/cli.md`, section 1).
    - **`--from <position>`** takes a position as `db watch` printed it, and the stream starts with the first transaction *after* it, so a script passes the last position it kept. The protocol field is named `after` for that reason. `db restore --from` takes a database name, against `docs/cli.md` section 2's "one flag, one kind of value"; the owner chose `--from` all the same, and the guide records the exception.
    - **Text:** one line per transaction, flushed as it arrives: the position, then each row change, separated by `; `. A row change is `<operation> <table> (<key>)`, then the old values in braces when the capture mode records them, then `-> ` and the new values in braces when it records them: `0000…01a8 insert note (id=1) -> {id=1, body='hi'}`. Values are SQL literals: `NULL`, numbers, text in single quotes, blobs as `x'…'`.
    - **JSON:** `-o jsonl`, and `-o json` and `--json`, which print `jsonl` as every `watch` does, print one object per line: `database`, `start` (`null` for the log's beginning), `position`, `lease_epoch`, and `changes`, each `table`, `operation` (`insert`, `update` or `delete`), `key`, `before`, `after`, and `updated`. `key`, `before`, and `after` are objects from column name to value in the table's column order, values as `db query` prints them (`null`, a number, a string, or `{"blob": "<base64>"}`); `before`, `after`, and `updated` are `null` when the capture mode doesn't record them (ADR-0024 point 3).
    - **Untrusted data.** Table names, column names, and values are text the database's writers chose. Text output escapes every character that could move the cursor or hide itself, as for every row the CLI prints; JSON carries them only in string fields.
    - **Elsewhere:** a note on stderr, unless `-q`, says what the stream opened on (`watching notes after <position> on data-1, epoch 3; capture mode after`), and another each time it resumes. Exit 0 when stdout closes, 130 on Ctrl-C, 3 when refused for scope, 4 when unavailable (no primary, the per-node limit, or reconnections that never succeed), and 1 otherwise, including a position no longer held.

11. **Compatibility (ADR-0038).** The call is new, and no control command or log entry changes, so there is no fleet feature to gate. A node that predates it answers `UNIMPLEMENTED`, or its request boundary refuses the unknown path with `PERMISSION_DENIED` naming no scope requirement; the client turns both into `UNIMPLEMENTED`, `the primary runs an older release of fleetring, which can't stream changes; upgrade it`, as `Schema` does. In a mixed fleet, a watch that follows the primary onto an older node ends there with that error and the position to resume after. The floor row is the only change to data at rest; older releases skip it (point 4), so rolling back keeps working.

12. **MCP: not now.** A bounded tool, `changes(database, after, limit)`, returning at most `limit` transactions after a position and the position to continue from, would fit the MCP server's request and response shape over this same RPC (open, read until `limit` or caught up, close). It isn't built here, because agent identities don't carry `stream`: dev mode mints `admin:agent-<id>-*`, which doesn't imply it (ADR-0025, ADR-0043 point 8), so the tool would be refused for every agent until someone decides whether agents get `stream` on their own databases. **Recommendation:** add the tool in the release after this one, together with that scope decision, and offer it only in read-write mode at first.

## Alternatives considered

- **Serving from followers.** It would spread watchers across replicas, but a follower's copy lags its primary, its record of a transaction arrives only once the frames do, and a follower doesn't know the write quorum's position; ordering and "nothing a failover can lose" would both get weaker. Redirecting to the primary costs one hop.
- **Turning capture on for a watcher.** Convenient on a database no sink names, but it would let a principal with `stream` add write amplification to every write, record on the primary only (a follower promoted later wouldn't record), and leave rows that nothing releases once the watcher leaves.
- **A watcher as an ephemeral sink with a mark.** A mark would let a watcher resume after any disconnect, but every watcher would write a row into the database per delivery, and marks of watchers that never come back would hold pruning forever. Watchers are many and short-lived; sinks are few and configured.
- **Holding checkpoints, or pruning, for disconnected watchers for a while.** It would make resumes after long disconnects succeed more often, at the price of a timer that decides what the table keeps. The floor makes a refused resume explicit and cheap to recover from.
- **Back-pressure instead of a cut-off.** Blocking the reader while the client is slow keeps the stream alive, but a stuck client then holds its pruning position, and the node's buffers, indefinitely. Cutting it off with a resumable position bounds both, and the CLI resumes on its own.
- **One line per acknowledged batch,** as sinks receive. Simpler, but a batch can hold many transactions, and the owner asked for a transaction per line. Batches stay a sink's unit.
- **Detecting a recording gap,** by writing a commit record for every transaction, including those that capture nothing. It would make every write, even one that changes nothing, a new batch in the log.

## Consequences

- **The protocol gains `WatchChanges` and its messages** (`WatchChangesRequest`, `ChangeUpdate`, `ChangesOpened`, `ChangedTransaction`, `RowChange`, `Columns`, `Column`, `CaptureMode`). The data client gains `Client::watch_changes`; `fleetring_client::output` gains the JSON line's types.
- **The engine boundary gains `LogicalChanges::transactions_after`,** with a default that answers `Unsupported`, the `RecordedTransaction` and `ReadLimit` types, and `EngineError::ChangesReleased`. A Turso adapter (FR-040) implements it over `turso_cdc`, whose floor it must keep the same way or answer conservatively.
- **`_fleetring_cdc` gains floor rows,** one per prune and one when recording first writes into an empty table. They change no reader that exists today.
- **Change streams track connected watchers** and include them when they release row changes, and limit them per node.
- **Docs:** `docs/cli.md` (the command tree, the JSON fields, the `db watch` line of "Where `fleetring` stands"), the lexicon (*watcher*), the daemon README, and the release notes. ADR-0043 point 9's deferral is settled by this record.
- **Follow-ups:** capture without a sink, for databases that should be watchable without one; the MCP `changes` tool with the agents' `stream` scope (point 12); a configurable per-node watcher limit if one is needed; and a simulation workload that watches through failovers.
