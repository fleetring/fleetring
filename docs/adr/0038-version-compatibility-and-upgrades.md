# ADR-0038: A fleet runs two adjacent release lines at once, gates new control commands as fleet features, and upgrades a node with a verified, atomic binary swap

- **Status:** Accepted (2026-11-04)
- **Date:** 2026-11-04
- **Related:** ADR-0017 (control state machine), ADR-0018 (leases, epochs, quorums), ADR-0019 (gRPC transport), ADR-0020 (simulation), ADR-0022 (failover), ADR-0035 (Raft control group); tickets FR-038 (drain), FR-048 (signed releases), FR-054

## Context

Upgrading a node today means re-running `install.sh` and restarting by hand. Nothing checks that the new release can run beside the rest of the fleet, nothing says which releases may mix, and a control command that a new release adds would be applied by a new control node while members that don't know it carry on. The roadmap's "Recoverable" criterion asks for a tested rolling upgrade from the previous release.

Forces:

- **0.3.0 is the baseline.** It is the first release after the clean break of the 0.3.0 renames (ADR-0032, FR-062). 0.2 and 0.3 speak the same bytes on the wire, but the `cluster` scope became `fleet`, so fleet-scoped tokens and `[[principal]]` lists differ between them; FR-062's documented path is to upgrade every node, then reissue fleet-scoped tokens. Moving from 0.2 is therefore not a rolling upgrade, and is out of scope. 0.3.0 nodes send no version in `Join` or `Heartbeat`, so the first rolling upgrade, 0.3.0 to the next release, has to work with members that say nothing about themselves.
- **One control node applies the log today; a Raft group will (ADR-0035).** Every new `Action` variant is a change to the control log. An older control node can't decode it: after a rollback of the control node today, and on a lagging voter under Raft. `control.db` already carries a format number (1 today, 2 once ADR-0035 lands), which describes the file, not which commands the log may hold.
- **The binary comes from the network.** `upgrade` replaces the program that holds the fleet's data. Releases are signed keylessly with cosign as one bundle, `SHA256SUMS.sigstore.json`, by the release workflow on a `fleetringd-v` tag (FR-048, `RELEASING.md`); `install.sh` verifies that signature when cosign 2.4.2 or newer is installed, and only warns otherwise.
- **Safety never depends on the upgrade.** Epochs fence and W + Q > R (ADR-0018). A drain is a promotion with a chosen candidate (FR-038, ADR-0022), so moving a node's primaries off before it restarts costs clients a redirect, not a failover, and is as safe as a failover.
- **Three ways to run a node:** systemd, the container image (distroless, UID 65532, binary owned by root), and a plain process in a terminal.

Precedents: CockroachDB lets a cluster mix the current and previous major release, gates new behaviour behind a cluster version that is finalized once every node runs the new release, and refuses nodes older than the finalized version. Kafka gates features by version levels that brokers advertise. etcd supports rolling upgrades one minor release at a time and refuses a member two minors apart. Nomad, Consul, and Vault document "upgrade followers, then the leader" with `-version` checks.

## Decision

1. **Versions and the window.** A *release* is a `fleetringd` version, `MAJOR.MINOR.PATCH` with an optional prerelease (`0.4.0-rc.1`). Its *release line* is `MAJOR.MINOR`; a prerelease belongs to its line. **A fleet runs at most two adjacent release lines at once: one line and the one before it, within one major.** Patch releases of a line always mix. Under 1.0 the minor is the unit, as the issue proposes: 0.3 and 0.4 mix, 0.3 and 0.5 don't. An upgrade never skips a line: from 0.3 to 0.5, every member reaches 0.4 first. A downgrade within the window is allowed unless a feature the older release lacks is enabled (point 4).

2. **Every node reports its software.** A new protocol message, `Software { version, protocol, control_format, features }`, rides on `JoinRequest.software` (field 3), on `HeartbeatRequest.software` (field 3), and on each `Member.software` (field 4) of a membership update. `version` is what `fleetringd --version` prints; `protocol` is the highest protocol version the node speaks; `control_format` is the newest `control.db` format it reads (1 in this release, 2 once ADR-0035 lands); `features` names the fleet features (point 4) it can apply and act on. `PROTOCOL_VERSION` moves from 1.0 to 1.1.
   - **Control state records it** on the member (`Member::software`), so replaying the log restores it. Unlike a changed address, new software doesn't grow the membership epoch (amended, see below): the control node sends a membership update when a member's software changes all the same, so every watcher sees the new versions.
   - **Heartbeats correct the record.** A member that joined while the control node was older has no record; the control node fills it from the member's next heartbeat. The control node includes the software in the `Heartbeat` command only when it differs from the record, so the log doesn't grow by a version per heartbeat.
   - **A member that reports nothing is a 0.3.0 node:** version `0.3.0`, protocol 1.0, control-log format 1, and no features. This is what makes the first rolling upgrade, 0.3.0 to the next release, work: the new control node and the new nodes see the 0.3.0 members as the previous line and accept them, and the 0.3.0 control node ignores the new fields, which are optional in the protocol and in the log's JSON.

3. **What is refused, and with which error.** Each refusal is `FAILED_PRECONDITION` with a message that names both nodes and both versions, and a `hint:` in the CLI where there is a next step.
   - **A join from another protocol major**, as today (`check_protocol`).
   - **A join whose release line is outside the window** with any member's, live or down: `Rejection::IncompatibleVersion` (`node 'n4' runs fleetringd 0.5.0, which can't run beside node 'n1' on 0.3.0: a fleet runs at most two adjacent release lines`). A data node whose join is refused keeps retrying and logs the reason, as for any refused join.
   - **A join from a member that lacks an enabled feature**: `Rejection::MissingFeature`.
   - **A command that needs a feature some member lacks**: `Rejection::FeatureUnsupported` (point 4).
   - **Heartbeats are never refused for a version.** A refused heartbeat would make a live node look down and fail its databases over.
   - **`fleetringd upgrade` refuses before it downloads** a release that would put the fleet outside the window, naming the member that blocks it, and refuses any release whose signature or checksum doesn't verify (points 6 and 7).

4. **New control commands are fleet features, enabled on first use once every member supports them.** `fleetring_control::Feature` lists the commands that not every member can read or act on. A command that needs one (`Action::feature`) is accepted only if the feature is already enabled, or if every member, live or down, reports it; that first accepted command enables it for good in control state (`State::features`). Enabling is part of the command's own transition in `apply`, so it is pure, logged, and replayed like everything else. Otherwise the command is rejected with `FeatureUnsupported`, naming the feature and the first member that lacks it with that member's version, and the state is untouched: a mixed fleet refuses the command instead of applying it on some nodes only.
   - **The control node screens a command against the gate before it logs it** (`State::check_admission`), and doesn't log a refused one. The screen covers every refusal for software: a command whose feature some member lacks, and a join refused for its release line or for a feature it lacks (point 3) (amended, see below). Rejections leave the state untouched, `State::now` included, so an unlogged rejection replays the same; an older control node, after a rollback, never meets a command it can't decode in a log that never used the feature; and it never replays a join it would accept but the fleet refused.
   - **Once a feature is enabled, members that lack it are refused** (`MissingFeature`). The enabled features ride on every membership update (`MembershipUpdate.features`), and `fleetringd upgrade`, given `--config` or `--control` so that it can ask the control plane (amended, see below), refuses to install, or roll back to, a release whose binary lacks one, before it swaps anything, on a data node and on a control node that is no member alike; `fleetringd upgrade --software` prints what a binary supports, and a binary without the flag, such as 0.3.0, supports nothing. Rolling back is therefore safe until a new command is first used, and refused, naming the feature, after.
   - *Note (2026-11-12):* [ADR-0031, amendment 2](0031-node-calls-bound-to-placement.md#amendment-2-2026-11-11-fr-102-a-membership-change-hands-a-replica-set-over-on-joint-quorums) (proposed) adds `handover`, whose command `EnableHandover` changes nothing but the feature: the control node's writer logs it just before the first membership change that would keep a replica set, once every member supports it, so the feature is still enabled on first use. A transition never reads members' software to decide what it does, since a release that knows a feature reads it in software an older control node recorded without knowing it, and would replay that node's log differently. The control node logs every feature's enabling on the audit target, since it closes rollback to a release without it.
   - **The first feature is `undrain`:** `Control.Undrain` and `fleetringd node undrain <node-id>` clear a member's draining mark without a restart, for a drain that turns out not to be needed, such as an upgrade abandoned after its drain. 0.3.0 can't decode it in its log.

5. **`fleetringd upgrade [--version X.Y.Z] [--check] [--no-restart] [--rollback]`.** It finds the newest final release (`fleetringd-vX.Y.Z` tags, prereleases only when `--version` names one) from GitHub's releases API, for the target the running binary was built for, and downloads the archive, `SHA256SUMS`, and `SHA256SUMS.sigstore.json` into a fresh temporary directory. `--base-url` (or `FLEETRING_BASE_URL`) reads a mirror laid out as `install.sh`'s `--base-url` expects, and needs `--version`; `--releases-url` (or `FLEETRING_RELEASES_URL`) points the newest-release lookup at a mirror's copy of the releases list. Only `https://` is fetched, and `http://` only from a loopback address. `--check` reports the newest release (or the one `--version` names), the installed one, and, given `--control` or `--config`, whether the fleet's window and its enabled features allow it, and changes nothing; it exits 1 when the fleet doesn't allow it. Checking a release older than the installed one, once a feature is enabled, downloads and verifies it, since only its binary says what it supports. Naming the installed version with `--version` reinstalls it.

6. **Verification: cosign, or nothing.**
   - **The signature first.** `cosign` on `PATH`, at 2.4.2 or newer as `install.sh` requires, runs `cosign verify-blob SHA256SUMS --bundle SHA256SUMS.sigstore.json --certificate-identity-regexp '^https://github.com/fleetring/fleetring/.github/workflows/release.yml@refs/tags/fleetringd-v' --certificate-oidc-issuer https://token.actions.githubusercontent.com`, the same identity `RELEASING.md` documents. A missing or older cosign is a refusal that says how to install it; there is no flag to skip verification. Unlike `install.sh`, which only warns, `upgrade` replaces a running node's binary without a person looking at it, so it never installs unverified.
   - **Then the checksum:** the archive's SHA-256 must match its line in the verified `SHA256SUMS`.
   - **Then the binary:** the one file the archive's `fleetringd-<version>-<target>/` directory holds as `fleetringd` is extracted, and must print `fleetringd <version>` for the version asked for.
   - **No in-process verification for now.** The `sigstore` crate (0.14, Apache-2.0) describes itself as experimental, declares no MSRV, and its `verify` feature pulls in its Fulcio and Rekor clients: 355 crates in a scratch build, more than this workspace's whole lock file (305), including `aws-lc-sys` (a C and CMake build), `reqwest`, `openidconnect`, `tough`, and `webbrowser`. That is too much code, and too much build tooling, to add to a security-critical path to save installing one binary. Revisit when a verify-only feature without network clients exists.

7. **Atomic replacement, with the previous binary kept.** The new binary is written beside the installed one as a temporary file, made executable, synced, and renamed over it, so the path always holds a whole binary; the installed one is first hard-linked (or copied) to `fleetringd.previous` the same way. `upgrade --rollback` swaps the two, so the upgraded binary becomes `fleetringd.previous` and a second rollback rolls forward; run as `fleetringd.previous`, it swaps the pair it belongs to, so a new binary that doesn't run at all can still be rolled back. The binary replaced is the one `upgrade` runs as; with `--config`, a running daemon's binary must be that same file. On Windows, `upgrade` checks but doesn't install: download the `.zip`, as `install.sh` says.

8. **Restart in place.** A daemon writes `<data_dir>/fleetringd.process` (its PID, its binary's path, its version, and how many times it has restarted in place) once it has started, and removes it when it stops. The signal handlers are installed before the file is written, so nobody learns the PID while `SIGHUP` would still end the process. `SIGHUP` restarts it in place: it drains as a stop does (as `[membership] on_shutdown` says), but stays a member, since it comes straight back and leaving would change the ring twice; it releases the data directory, and executes its binary's path again with the same arguments and a restart count one higher, keeping its PID. With `--config` naming a running node, and unless `--no-restart`, `upgrade`:
   1. checks the window against the fleet's members, before downloading;
   2. downloads, verifies, and swaps the binary;
   3. drains the node (`Control.Drain`) and waits, bounded, until it is primary for nothing;
   4. sends `SIGHUP`, and waits until the process file counts the restart;
   5. waits until the control plane lists the member as live on the new release (or, from a 0.3.0 control node, which records no releases, as live);
   6. waits until each of the node's replicas has reached the position its primary reported when the node rejoined.

   It works the same under the three supervisors: systemd keeps tracking the same PID, a container's PID 1 stays PID 1, and a plain process stays in its terminal. Where the binary can't be written, as in the container image, the image is the release: upgrade by running the new tag, and give `docker stop` time to drain. A daemon that wrote no process file (0.3.0) can't be restarted in place; `upgrade` swaps the binary and says to restart the node with its supervisor (`systemctl restart fleetringd`, or stop and start it), which drains it on the way down.

9. **The rolling-upgrade test runs nightly and before a release, never per pull request.** An ignored integration test starts a three-node fleet on the previous release's binary, writes and reads throughout with one retry per write, and upgrades each node in turn, the control node last: with the previous release's own `upgrade` when it has one, and otherwise with the manual steps the daemon README documents (drain, swap the binary, restart). It then reinstalls one node with the current build's `upgrade`, restarting it in place, and checks the whole history: no write failed beyond its one retry (a write the primary refused before committing anything is resent, as a client would, and counted apart), every acknowledged write is read back, nothing is stored that wasn't written, and no read saw less than the writes acknowledged before it began. While the fleet is mixed it checks that `undrain` is refused, and once every node runs the current build, that it is accepted. The baseline comes from `FLEETRINGD_BASELINE_VERSION`, which the current build's own `upgrade --version <baseline> --no-restart` downloads and verifies with the real cosign into a scratch directory, or from `FLEETRINGD_BASELINE_BIN`, a binary built locally. A scheduled workflow runs it with the newest final release at or after 0.3.0, and `RELEASING.md`'s pre-flight requires a green run. The fast tests of `upgrade` (refusals, swap, rollback, restart) run on every pull request against a local release server and a stand-in `cosign` that checks the arguments it is given, with no network.

## Alternatives considered

- **An explicit "finalize" step**, as CockroachDB's cluster version. It is one more command an operator must remember, and until it runs every new command is refused. Enabling a feature on its first use needs no step and keeps rollback possible for as long as nobody uses the new command.
- **Gating by control-log format number.** The number ADR-0035 gives `control.db` describes the file, and moves only when the storage changes; tying every new command to it would either bump it per command or bundle unrelated commands. Named features gate each command on its own, and the format stays the storage's.
- **Refusing a mixed fleet outright.** Simple, but it rules out the rolling upgrade the roadmap asks for.
- **A wider window,** such as any two lines within a major. Every release would then have to read every older release's log and speak every older protocol minor, and the tests would have to cover each pair.
- **Verifying in process with the `sigstore` crate.** Point 6.
- **Installing with only a checksum when cosign is missing,** as `install.sh` does. A checksum downloaded from the same place as the archive proves nothing about who built it.
- **Restarting through the supervisor** (`systemctl restart`). It ties the command to one supervisor, and has no equivalent for a plain process. Re-executing in place works under all three.
- **A remote "restart" RPC.** It would make restarting any node a network capability to guard; a signal needs the node's own operating-system user.

## Consequences

- Rolling upgrades are supported from 0.3.0 on, one release line at a time, and the fleet enforces the window rather than the operator remembering it.
- Every future control command that older members can't read or act on adds a `Feature` variant, reports it in `Software.features`, and is refused until every member supports it. FR-064's group commands are the next users.
- Rollback is safe until a feature is first used. The README says so, and `--rollback` refuses, naming the feature, when the previous release lacks one the fleet has enabled.
- A member that died for good still counts toward the window and the gate. `fleetringd node remove <node-id>` (the `Leave` call, fleet scope, refusing a live member unless `--force`) takes it out; without it, a node that died on 0.3.0 would hold every later upgrade and every new command back.
- `upgrade` needs cosign on the machine; the README says how to install it.
- `<data_dir>/fleetringd.process` is a new file in the data directory, and `SIGHUP` now restarts a daemon instead of terminating it.
- A nightly workflow downloads the previous release; per-pull-request CI grows only by the fast `upgrade` tests.

## Amendments

- **2026-11-04, after review, before merge.**
  - **New software no longer grows the membership epoch.** A join with new software was an update, and a heartbeat that corrected the record grew the epoch too. A control node rolled back to 0.3.0 decodes the same log without the `software` fields, so it replayed those joins as rejoins and those heartbeats as plain heartbeats, reaching a lower epoch than its data nodes held, and they would have ignored its membership updates until its epoch caught up. The epoch now grows only for a member's ID, placement attributes, and address; the control node sends a membership update when only software changes, and data nodes keep their ring when only software differs. A log replayed without software reaches the same epoch and ring (`a_log_replayed_without_software_reaches_the_same_membership`).
  - **Joins refused for software are never logged either.** The control node screened only commands that need a feature, and logged a join it then refused for its release line or a missing feature. 0.3.0 has no such check and drops the software when it decodes the log, so a control node rolled back to it would accept the logged join: a node the fleet refused would become a member, and the membership epoch would grow once for every retry, which a refused node sends each heartbeat interval. The writer now screens joins too (`State::check_admission`, which `apply`'s join shares, so the two can't drift), and answers a refused one with the same `FAILED_PRECONDITION` as before; the joining node still logs the reason and retries (`a_join_refused_for_its_software_is_never_logged`).
  - **Upgrades check the fleet's features as well as its window**, as point 4 now says, so a rollback or a downgrade can't leave a node refused at its join, or a control node unable to read the log. Like the window, the features are checked only when `--config` or `--control` names a control plane to ask; without one, `upgrade` checks neither, and the README says to pass one.
  - **`fleetringd node remove`** takes a member that is gone for good out of the fleet (Consequences).
  - **`upgrade` signals the daemon in process** (rustix's `kill_process`, already in the tree through `tempfile`) rather than running `kill`, and reads the process file again just before it signals, so a daemon its supervisor restarted meanwhile is neither signalled by a stale ID nor waited for in vain.
- **2026-11-05, by ADR-0041 (amendment 1).** Point 4's rollback promise had a gap for every feature after the first: a release that decodes a member's feature list strictly can't load a log in which a newer member reports a feature it doesn't know, even before any command uses it. A stored `Software` now writes in `features` only the names the 0.5 line decodes, and every other name in `newer_features`, which 0.5 ignores; from 0.6 on, both are read and unknown names are kept but never supported.
- **2026-11-05, by ADR-0041 (amendment 3).** Point 4's "every member supports it" no longer holds vacuously: a command that needs a feature that isn't enabled is refused while the fleet has no members, so an empty fleet can't enable a feature that would refuse every later join.
- **2026-11-08, the configuration check (#95).** Point 7's swap left one outage open: a release that makes a setting required, or refuses one (0.5's `allow_http`, which 0.4 refused as an unknown key), installs fine and then exits at load when point 8 restarts the node, which stays down until someone edits its configuration. So the release is asked first.
  - **`fleetring serve --check`** runs what a start runs before it touches anything, in the same code (`Daemon::check`, which `Daemon::start_with` calls first): `Config::load`, `serve`'s flags, `Config::validate`, an identity or `insecure_plaintext`, an identity for `[admin] tls`, and `[engine] page_size`. It reads none of the files the configuration names, no environment variable and no data directory, and binds nothing, so its answer doesn't depend on who asks: an upgrade run as root, from a shell without the unit's environment, gets the answer the node's restart would. It exits 0 if the node would start, and otherwise prints the first problem, naming the file, the dotted field, and the line and column, and exits 1; `--json` prints the same as one object. It is a flag of `serve` rather than a `config check` command because it checks `serve`'s whole command line, flags included, and because the style guide keeps top-level commands few; `upgrade --check` is the precedent for a flag that reports and changes nothing.
  - **Point 8's sequence gains a step between verifying and swapping.** With `--config`, `upgrade` runs the release's own binary as `<it> <the node's arguments> --check`: an argument vector with no shell, within `--timeout`, in the directory the node started in. The process file records that directory (`cwd`, a new optional field; 0.6 and 0.7 readers ignore it). The process file is the daemon user's, and `upgrade` may run as root, so the recorded command line is used only when it can do nothing but check the node's configuration: it runs `serve` (or 0.6's bare daemon flags, after `--log-format` alone), holds no help or version flag and no short flag but `-q`, its `--config` is the file `upgrade --config` named, and its directory still exists. Otherwise, and for a node that doesn't record both its arguments and its directory, as a 0.7 node or a dev node, the check is `serve --config <file> --check` for the file `--config` named. At most 64 KiB of each of the release's stdout and stderr is kept; the rest is read and dropped. Exit 0 lets the swap go on; any other exit, or no answer in time, refuses it with the release's output, escaped and indented, and the fix: `--no-restart`, edit the configuration until `serve --check` passes, then restart. With `--no-restart` the swap goes on and the report says the same, since a release that needs a setting the running one refuses can only be configured once it is installed; it adds that until the edit, any restart (a supervisor's, a crash, a reboot) leaves the node down. A refused configuration stops the upgrade even when the node isn't running, and `upgrade --check` doesn't run the configuration check (the owner's decisions of 2026-11-08). `--rollback` asks the previous binary the same way.
  - **A release says whether it can check** in `upgrade --software`'s `config_check`; a release before 0.8 doesn't, and is installed with a note that the configuration wasn't checked. A 0.7 `upgrade` knows nothing of the check, so an upgrade from 0.7 to 0.8 is unchecked, and the 0.8.0 notes say to run 0.8's `serve --check` first.
  - **The rolling-upgrade test** (point 9) runs this build's `upgrade` against a stand-in next release, a script that runs this build except that its `serve --check` refuses the heartbeat interval the test's nodes use, and checks that nothing was swapped and the node runs on under the writes; this build's own release, which accepts the configuration, is then installed. A stand-in keeps a test-only refusal out of the shipped binary.
