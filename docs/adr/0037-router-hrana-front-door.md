# ADR-0037: The router is a Hrana-over-HTTP front door that authenticates each request and runs it in a session on its database's primary

- **Status:** Proposed
- **Date:** 2026-11-03
- **Related:** ADR-0016 (engine adapters), ADR-0018 (leases, epochs, quorums), ADR-0019 (gRPC; the `Database` service is v0.1-only), ADR-0023 (durability), ADR-0025 (principals and scopes), ADR-0026 (amends point 4), ADR-0031 (node calls bound to placement), ADR-0033 (surfaces); tickets FR-061, FR-066

## Context

Applications can't use FleetRing without speaking its gRPC `Database` service, which ADR-0019 keeps for tests and the command line and says the router replaces. The router is MVP step 4 and roadmap E7: a front door that existing libSQL and Turso clients reach with no code change, and the point where client requests are authenticated before they touch a node. FR-061 (#63), the Rails adapter, is blocked on it.

What the clients speak is libSQL's Hrana protocol. Hrana carries SQL statements and their results over a *stream*: a sequence of requests that share one SQLite connection's state, so that `BEGIN` in one request and `COMMIT` in a later one form one transaction. Over HTTP, a stream is continued by a *baton*, an opaque string the server returns with each response and the client sends with the next. Hrana 2 defines the HTTP pipeline endpoint (`/v2/pipeline`); Hrana 3 adds a cursor endpoint (`/v3/cursor`) that streams a batch's rows, `get_autocommit`, the `is_autocommit` batch condition, and a protobuf encoding. Both define a WebSocket transport too. `@libsql/client` and the `libsql` Rust crate's remote client use HTTP for `https://` and `libsql://` URLs and probe `GET /v3` before falling back to v2.

Four facts of FleetRing shape the design:

- **Every write goes to one primary per database,** chosen by a lease at an epoch (ADR-0018), and a write is acknowledged only once its write quorum holds it (ADR-0023). Clients today find the primary through `Locate` and follow `fleetring-primary` redirects; a lost reply is never resent by a proxy, because a write's outcome is then unknown.
- **The data plane runs a whole request as one transaction.** `Database.Execute` wraps its statements in `BEGIN IMMEDIATE … COMMIT`, refuses statements that control transactions, and returns only a row count. Hrana needs SQLite's own semantics: each statement autocommits unless the client began a transaction, a failed batch step doesn't roll back earlier ones, and results carry columns, rows, the affected row count, and the last insert row ID.
- **A router is a client, not a node.** ADR-0026 point 3 lets a principal with `forward_tokens = true` carry its callers' tokens, each request acting as the caller with the token's scopes alone, and point 9 refuses database calls to node certificates. A router that held a node certificate could do nothing for its callers.
- **Tokens are verified offline but revoked through the control plane.** A data node holds the denylist from its heartbeats (ADR-0026 point 6); a client doesn't.

## Decision

### The process

1. **The router is a separate long-running process, `fleetringd router --config <file>`,** with its own configuration file and its own identity. Its code lives in `crates/fleetringd/src/router/`, in the `fleetringd` package: a separate library crate that depended on `fleetringd` would form a package cycle with the `fleetringd` binary, which runs it. `router` is a new top-level command because it is a process with an identity of its own, like the daemon itself (`docs/cli.md`, section 1).
2. **It is a client of the fleet.** It connects to nodes with a client certificate for a principal, conventionally `router`, that every node lists with `forward_tokens = true` and `scopes = []`. It acts only with its callers' tokens; with no token it can do nothing. Any number of routers can run, on any machine, behind a load balancer or beside an application.

### The protocol

3. **Hrana over HTTP with JSON, versions 2 and 3:** `GET /v2` and `GET /v3` (version probes, `200` with an empty body), `POST /v2/pipeline`, `POST /v3/pipeline`, and `POST /v3/cursor`. On a v2 endpoint, v3-only requests (`get_autocommit`) and conditions (`is_autocommit`) are refused as protocol errors. HTTP/1.1 and HTTP/2 through `hyper`.
4. **Out of v1:** WebSocket Hrana (the `hrana2` and `hrana3` subprotocols), the protobuf encoding (`/v3-protobuf/…`), sqld's legacy `/v1/execute` and `/v1/batch`, and reads served by followers. Each can be added behind the same sessions later.
5. **TLS** through `rustls`, with the router's own server certificate and key (`[http] cert`, `key`), from any authority, a public one included, since application clients verify the server against their own trust store, not the fleet's authority. Plaintext HTTP is served only on a loopback address unless `[http] allow_plaintext = true`, so a bearer token never crosses a network in the clear by default (ADR-0026 point 3 refuses tokens on plaintext node connections for the same reason).

### Naming the database

6. **The path form:** `/db/<database>/` followed by the endpoint (`/db/tenant%3Aacme%2Fnotes/v3/pipeline`), where `<database>` is the database name percent-encoded as one path segment, so that any name, `/` and `:` included, fits. Repeated slashes between segments are tolerated, since clients that join paths by string concatenation produce them. Clients set their URL to `https://router:8080/db/<database>/`, **with the trailing slash**: hrana-client-ts resolves endpoint paths relative to the URL, and without the slash the last segment, the database, would be replaced.
7. **The host form,** when `[routing] host_suffix` is set: a request whose `Host` is `<label>.<host_suffix>` names the database `<label>`, for clients or proxies that can't set a path. Only names that are DNS labels (`[a-z0-9]([a-z0-9-]{0,61}[a-z0-9])?`) can be reached this way.
8. **Anything else is `404`** with a Hrana error naming both forms.

### What v1 supports

9. **Every Hrana stream request:** `execute`, `batch` with the conditions `ok`, `error`, `not`, `and`, `or`, and `is_autocommit`, `sequence`, `describe`, `store_sql`, `close_sql`, `get_autocommit`, and `close`; positional and named arguments; Hrana's values (integers as decimal strings, floats, text, base64 blobs, and null); batons; `base_url`; and interactive transactions across requests. `store_sql` is kept by the router per stream, and the node only ever sees SQL text.
10. **`base_url`:** with `[http] advertise_url` set, every response that returns a baton also returns it as `base_url`, so a client's follow-up requests reach the router instance that holds its stream, behind any load balancer.

### Sessions on the primary

11. **A new data-plane RPC, `Database.Session`, carries one Hrana stream to the primary.** It is a bidirectional stream: the router opens it with the database's name, the node answers with its node ID and epoch if it holds the lease and with a `not_primary` redirect if it doesn't, and then the router sends *calls* (execute, batch, sequence, describe, get autocommit), each answered in order. One session serves one Hrana stream for its whole life, so the connection state the stream sees (its open transaction) stays on one node.
12. **Statements run with SQLite's semantics on the primary's write connection.** An autocommit statement commits by itself; `BEGIN`, `COMMIT`, `END`, `ROLLBACK`, `SAVEPOINT`, and `RELEASE` are allowed in sessions and only there (`Execute` keeps refusing them); a failed batch step leaves earlier steps committed, as SQLite would. Read-only statements outside a transaction run on the read connection, so readers never wait for a writer. Whether a statement is read-only, and whether it controls a transaction, is SQLite's answer when it prepares the statement (`sqlite3_stmt_readonly` and the authorizer's transaction and savepoint actions), never a parse of the text. The same confinement as every other user statement applies (ADR-0026 point 8). A `SAVEPOINT` outside a transaction is refused: sessions start transactions with `BEGIN`.
13. **A commit is acknowledged as an `Execute` is.** Each transaction a session commits is captured, hash-chained, recorded for change streams, and published through the `BatchPublisher` exactly as an `Execute` transaction is, one batch per transaction; a call that committed is answered only once its last transaction's write quorum holds it, and the answer carries how many replicas acknowledged it, R, and the epoch. If the quorum can't be had, the call's result is an error with code `FLEETRING_UNACKNOWLEDGED` (the write may or may not survive, as an `ABORTED` `Execute`), and the node ends the session with `ABORTED`. Before a call that may write, the primary checks the replica floor (ADR-0023) as it does before an `Execute`, and refuses with `UNAVAILABLE` if it isn't met.
14. **An open transaction holds the database's writer.** While it is open, other writes to the database, from `Execute` or from other sessions, wait in the database's actor, up to `[sessions] max_waiting_writes` (64 by default) and beyond that are refused with `RESOURCE_EXHAUSTED`; reads go on. A transaction older than `[sessions] transaction_timeout_ms` (30 s by default) is rolled back and its session ended, so a client that walks away can't hold a database. A session that ends for any reason rolls back its open transaction.
15. **A lease that moves ends every session on it.** When the node stops holding the database's lease, it rolls back any open transaction and ends each session with `UNAVAILABLE` and a `fleetring-primary` hint. Nothing a session didn't commit before then was acknowledged.
16. **Engine neutrality (ADR-0016).** Sessions are an engine capability, beside logical change capture: an engine that can't run SQL sessions answers `FAILED_PRECONDITION`, and nothing above the adapter knows which statements control transactions or how SQLite reports read-only statements. The router is a front door for SQLite and libSQL databases; a Postgres database (ADR-0021) would be reached through its own protocol.

### Authorization

17. **`Database.Session` needs `read` on the database** in `auth::RPCS`. A caller without `write` on it gets a read-only session: every statement SQLite reports as not read-only, and every statement that controls a transaction, fails with the code `PERMISSION_DENIED` and a message naming `write` on the database, and the refusal is logged on the `fleetringd::audit` target. **This amends ADR-0026 point 4,** which kept `Execute` at `write` so that authorization wouldn't depend on classifying statements. For sessions, the classification is SQLite's own read-only flag, read in the engine, while the scope decision stays in the handler; a read-only token can then run a dashboard's `SELECT`s through the router, which is the common case point 4's reasoning didn't weigh. `Execute` and `Query` don't change.
18. **The router authenticates every request before any network call.** It requires `Authorization: Bearer <token>`, a FleetRing token (libSQL clients send their `authToken` this way); verifies it with the fleet's authority certificates and the fleet name its own certificate carries (`Identity::token_verifier`); and checks `read` on the database the request names. A missing or invalid token is `401`, and a token without `read` is `403`, each with a Hrana error body. It then forwards the token unchanged on every call it makes for the request. The router has no denylist, so data nodes stay the authoritative check: a revoked token passes the router and is refused by the node within the bounds of ADR-0026 point 6.
19. **A baton is bound to the principal that opened its stream.** A request that continues a stream with another principal's token is `403`.

### Routing

20. **Placement is cached per database** for `[routing] placement_ttl_ms` (60 s by default), up to `placement_cache_size` entries (100,000), the oldest evicted first. A miss is filled by `Control.Locate` with the caller's token forwarded, and a `fleetring-primary` hint replaces the entry. The router uses one HTTP/2 connection per node address, shared by every session to that node; control calls go through the control client, which follows `fleetring-leader` redirects (and the control-node list of FR-064 once it exists).
21. **A session open is retried; a call is never resent.** Opening a session follows up to three redirects and retries `UNAVAILABLE` without a hint, which a promotion in progress answers, with backoff for up to `[routing] open_retry_ms` (5 s). `NOT_FOUND` becomes a `404` naming the database. Once a call has been sent, its outcome belongs to the client: if the session breaks before the call's result arrives, the Hrana request fails with an error saying the outcome is unknown, and the stream is broken. Between requests, a stream in autocommit whose session ended opens a new one on its next request, wherever the primary now is; a stream with an open transaction fails its next request with `FLEETRING_TRANSACTION_ABORTED`.
22. **Responses name the primary.** A response whose last call committed carries `fleetring-primary`, `fleetring-epoch`, `fleetring-acknowledged-by`, and `fleetring-replicas` headers. Clients ignore them; the simulation's history checker uses them to hold the router to one primary per epoch.

### Streams

23. **A baton is `base64url(stream ID ‖ 16 random bytes ‖ sequence)`,** with the stream ID a big-endian `u64`, the sequence a big-endian `u32`, and the random bytes from an injected generator (`ring::rand::SystemRandom` in production, the simulation's seeded generator under ADR-0020). A baton is accepted only with its stream's current sequence, so a replayed or forked baton fails. Streams idle for `[streams] idle_timeout_ms` (10 s) expire, and their sessions close. `[streams] max_streams` (10,000) bounds the streams a router holds, answering `503` beyond it, and `max_request_bytes` (8 MiB) bounds a request body. A pipeline without a baton that ends with `close` opens and closes its session within the request.

## Alternatives considered

- **A node role, or a router inside every data node.** No extra process, but a node holds a node certificate, which ADR-0026 point 9 forbids from acting on databases, and every node would grow a public HTTP listener next to the data. A router's blast radius stays that of a principal with no scopes of its own.
- **A sidecar library linked into applications** (the embedded client of E7). It skips a hop, but only Rust applications get it; the point of the router is that any libSQL client works unchanged. Both will exist.
- **A separate binary in its own crate.** Clean dependency boundaries, but either the crate cycles with `fleetringd` or the client code it needs moves first; and it breaks the one-binary rule of ADR-0015 for no gain. A move to `fleetring-client` (FR-056) later doesn't change the router's behaviour.
- **Forwarding every request as an `Execute` or `Query`.** No new RPC, but Hrana's semantics don't fit: no interactive transactions, no per-statement results, no `last_insert_rowid`, and writes a client meant to autocommit one by one would become one transaction. Clients and ORMs would break in ways their tests don't expect.
- **Detecting `BEGIN` in the router and pinning only then.** Fewer sessions, but it means parsing SQL in the router, which `/* comments */`, `begin` inside a batch, and `SAVEPOINT` all defeat. A session per stream is one HTTP/2 stream on a shared connection; it holds nothing on the node unless a transaction is open.
- **Running sessions on any replica and forwarding writes.** Reads would scale, but a stream's reads would see a follower's lag and its writes another node's state, which no libSQL client expects. Follower reads come later as an explicit choice.
- **WebSocket Hrana in v1.** It is what older clients use by default, but the current clients use HTTP, and a WebSocket transport doubles the protocol surface to test. Deferred, not rejected.
- **Letting the router hold the fleet scope or wide scopes of its own.** Simpler placement lookups and a router that could watch membership, but a compromised router would reach every database. With `forward_tokens` and no scopes, it reaches only what its callers' tokens reach.
- **Keeping `read` sessions out (sessions need `write`).** It keeps ADR-0026 point 4 unchanged, but a dashboard or an analytics job would need a token that can write. The engine already refuses writes on its read path; using SQLite's own read-only flag for sessions is the same kind of check.
- **Routing by a custom header or by the token.** A header needs client code most libSQL clients can't add; a token names prefixes, not one database. The path and host forms need only a URL.

## Consequences

- Existing libSQL and Turso clients reach FleetRing through a URL change and a FleetRing token. FR-061's Rails adapter and the framework adapters of E7 build on this, and FR-061 is unblocked once FR-066 is done.
- The engine gains a session capability, and the actor a transaction holder: the one place a client can make writes wait. The bounds in points 14 and 23 keep that wait finite, and the metrics FR-063 adds (`fleetring_router_*` and the actor's waiting writes) make it visible.
- ADR-0026 point 4 is amended for sessions; `Execute` and `Query` keep their requirements. The daemon README's scope table gains `Database.Session`, and the proto states it in a `Scope:` line.
- The protocol gains new messages and one RPC; existing messages don't change. `PROTOCOL_VERSION`'s minor version goes up by one.
- A request whose reply is lost fails at the client rather than being retried for it, which is the same contract `Execute` has. Clients that retry blindly on network errors can double a write; that is their existing behaviour against any Hrana server.
- A router holds tokens in memory for the streams it serves, and never writes or logs them. `SECURITY.md` gains the router as an actor: what a compromised router can do is what its callers' unexpired tokens allow, until they expire or are revoked.
- Follow-ups: WebSocket Hrana and the protobuf encoding; follower reads; the router's use of `fleetring-client` (FR-056); a `WatchLeases`-driven placement cache instead of TTLs at large scale (E4).
