# ADR-0036: Faults are injected into real daemons by an in-repo harness: five `fleetringd` processes in Docker, judged by the history checker

- **Status:** Accepted (2026-11-03)
- **Date:** 2026-11-03
- **Related:** ADR-0009 (toolchain and CI), ADR-0014 (OS test matrix), ADR-0018 (leases, epochs, quorums), ADR-0020 (simulation), ADR-0022 (failover), ADR-0025 (principals and scopes); tickets FR-036, FR-065

## Context

The first "safe to use" criterion in `docs/roadmap.md` is that there is no known way to lose an acknowledged write, shown three ways: the history checker (FR-036) on every simulation run, nightly sweeps over random seeds, and "a fault-injection run on real processes". The first two exist. The third doesn't.

The simulation (ADR-0020) runs the real daemon code, but not the real world around it:

- **The network is turmoil's.** It simulates TCP, not the kernel's: no real retransmission timers, no half-open connections after a partition, no HTTP/2 keepalives timing out on their own schedule, no connection that a peer's kernel resets after a restart.
- **Time is simulated and shared.** Every host reads one clock. A process can't pause while the others run on, and no wall clock jumps; skew between hosts exists only where a test injects a different `SimClock` base.
- **Storage runs inline.** SQLite runs on the simulation thread, so the dedicated database threads, their scheduling, and real `fsync` latency never appear.
- **The binary isn't the one shipped.** Tests drive `Daemon::start_with` in one process; configuration loading, signal handling, certificate files on disk, and the release profile are outside the simulation.

Each of these hides a class of bug that has cost other systems acknowledged writes: a primary paused past its lease that wakes and acknowledges one more write; a stale connection that delivers a batch after a fence; a control node whose clock jumps backwards. ADR-0018 claims safety never depends on clocks or timing, and only a test on real processes, with real clocks moved under them, can show it.

Jepsen is the established method: run the system on real machines, record every client operation as an invocation and a completion, inject faults (partitions, kills, pauses, clock changes) from a scheduler, and check the history against the system's guarantees afterwards. FR-036 already implements the checking half for FleetRing: `fleetringd::sim::history::check` takes a `History` of operations and the rows each replica holds on disk, and checks durability, no phantom writes, one primary per epoch, read-your-writes, and monotonic reads. What is missing is the other half, on real processes.

Constraints:

- The harness must run on one Linux host, so a nightly GitHub Actions job can run it, and on a developer's Linux machine with Docker.
- It must reuse the checker, the client, and the certificate tooling unchanged, so that it tests the same guarantees with the same code the simulation does, and so that a fix to one benefits both.
- It must not change the daemon. Nothing in `fleetringd` may exist only to make the harness work; the daemon under test is built from the same sources and profile as a release.

## Decision

1. **An in-repo Rust harness, `fleetring-chaos`.** A new workspace crate, `crates/fleetring-chaos`, with one binary of the same name (`publish = false`, `rust-version = "1.89"` as `fleetringd`). It depends on `fleetringd` with the `simulation` feature, behind the crate's own `harness` feature, so that it reuses `sim::workload::History`, `sim::history::check`, `sim::check::control_log_replays`, `sim::SimRng`, and `data::Client` as they are. Two small items in `fleetringd::sim` become public for it: reading a replica's rows from a data directory, and performing a create, write, or read operation against a `data::Client` and returning its `Outcome`. Both are extracted from code the simulation already runs.

2. **Five real daemons in Docker containers on one bridge network.** Containers `fleetring-chaos-n1` to `fleetring-chaos-n5` run on a user-defined bridge network `fleetring-chaos` (subnet `10.77.0.0/24`, gateway `10.77.0.1`, nodes at `10.77.0.11` to `10.77.0.15`). `n1` has node role `both` and is the control node; `n2` to `n5` are data nodes. Each runs `fleetringd` built by the harness's image (`deploy/chaos/Dockerfile`): a Debian bookworm build stage running `cargo build --locked --release -p fleetringd`, so the binary links glibc dynamically, and a `debian:bookworm-slim` runtime with `iptables`, `libfaketime`, and `procps`. Each node's data directory, configuration, and clock file are bind-mounted from the run's directory, so the harness reads the data after the run. Members stay members across restarts (`[membership] on_shutdown = "stay"`), so kills test failover, not leaves. The harness drives the `docker` command-line tool through `std::process::Command`; there is no Compose file and no Docker API client. The harness's clients run on the host and reach the nodes at their bridge addresses.

3. **The fleet's identity comes from the build under test.** The harness runs the image's own `fleetringd cert init --fleet chaos`, `cert node nX --addresses 10.77.0.1X`, and `cert client chaos`, and every node's configuration lists the principal `chaos` with the scopes `["admin:chaos/*", "fleet"]`. Every connection is mutual TLS, as in production (ADR-0025); nothing runs with `insecure_plaintext`.

4. **Faults.** The word is *fault*, as in the simulation (`sim::Fault`). Every fault is undone at its end, and only one is active at a time.
   - **Partitions** cut node-to-node links with `iptables` in each container's network namespace: for each cut pair, `docker exec --user 0:0 <container> iptables -A INPUT -s <peer> -j DROP` and `iptables -A OUTPUT -d <peer> -j DROP` on both sides; a heal flushes both chains on every container. Four shapes: *random halves* (two nodes against three), *a primary isolated* (the current primary of a random database, found with `Locate`, cut from every other node), *the control node isolated*, and *a bridge* (two halves that share one node, which reaches both). The harness's clients are not partitioned: they keep reaching every node, as a client beside a cut-off primary would.
   - **Kills:** `docker kill --signal KILL <container>`, then `docker start <container>` at the fault's end.
   - **Pauses:** `docker kill --signal STOP <container>`, then `--signal CONT`. The process keeps its sockets and its memory and wakes with every timer overdue.
   - **Clock skew and strobe** on the control node, through `libfaketime`: the container runs with `LD_PRELOAD` set to the library, `FAKETIME_TIMESTAMP_FILE` naming a bind-mounted file whose content (`+0s`, `-42s`) the harness rewrites, `FAKETIME_NO_CACHE=1` so a rewrite takes effect at once, and `FAKETIME_DONT_FAKE_MONOTONIC=1` so only wall-clock reads move. Those are the control node's command stamps, which decide lease expiry (ADR-0017), and certificate time checks. A skew holds one offset for the fault; a strobe flips between `+X` and `-X` every 500 ms. Offsets stay within ±60 s, and the first fault starts at least 65 s after the certificates were issued, so no certificate is ever outside its validity.
   - **Scenarios** pick the kinds: `partitions` (the four partition shapes), `kills`, `pauses`, `clock` (skew and strobe), and `mixed` (all eight). A run alternates quiet periods of 5 to 10 s with faults of 5 to 20 s, and every choice (kind, duration, targets, offsets) comes from `sim::SimRng` seeded by `--seed`.

5. **A workload that the checker understands.** Eight databases, `chaos/db-0` to `chaos/db-7`, each with replication factor 3: six with `acks = quorum` and two with `acks = all`. Ten client tasks, each with its own `data::Client` over mutual TLS, send about 200 operations a second in total: 70 % writes of a value unique within the run to the database's `writes` table, 30 % reads of the whole table. Each operation is recorded in a `History` when it is sent and when it ends, with times measured from the workload's start by `tokio::time::Instant`. An operation with no answer within 5 s is recorded as indeterminate (`info`): the checker then allows it to have happened or not, as it does in simulation.

6. **The checker of FR-036 judges the run.** After the fault phase the harness heals everything, lets the fleet run quiet for 30 s, reads every database once more (retrying for up to 60 s), waits up to 60 s for every replica's hash chain to agree with its primary's (`Database.Verify`, FR-044), and stops the containers with `SIGTERM`. Then it reads the `writes` rows of every node's copy of every database from the bind-mounted data directories, and runs `sim::history::check` over the history and those rows, `sim::check::replicas_converged` over each database's replica set, and `sim::check::control_log_replays` over `n1`'s `control.db`. The exit code is the verdict: 0 when every check passes, 1 for a violation, 2 when the harness itself failed (Docker missing, a container that never started, a workload that acknowledged fewer than 100 writes), so infrastructure trouble never reads as a pass or as a bug.

7. **A self-test, so a harness that checks nothing can't pass.** `--self-test` creates the databases with `acks = local`, which may lose acknowledged writes on failover (ADR-0023), but tells the checker they are `quorum`, and injects only primary isolations long enough for a failover (15 to 20 s). The checker must report a lost acknowledged write; the self-test exits 0 only if it does, and 1 if the run looks valid.

8. **Runs are reproducible as far as real processes allow.** Each run writes `target/chaos/<scenario>-<seed>/`: `history.txt` (every event, in time order), `schedule.txt` (each fault with its start, end, and resolved targets), `verdict.json`, `nodes/nX.log`, and the nodes' data directories. A failing run prints its seed and the command that reruns it. The seed fixes the fault schedule and the workload's choices; it can't fix the interleaving of real processes, and the documentation says so.

9. **CI runs it nightly, never on pull requests.** `.github/workflows/chaos.yml` builds the image once, then runs the five scenarios and the self-test in parallel, each for 600 s, on `ubuntu-24.04`, nightly and on manual dispatch, uploading the run directory when a job fails. The harness's pure parts (schedule generation, Docker command building, configuration rendering) have unit tests that run in the normal CI jobs without Docker. The `run` subcommand refuses to start on a host that isn't Linux.

10. **Control-group faults follow the control group.** When FR-064 lands three control nodes, the harness gains faults that isolate the control leader, kill two of three control nodes, and skew clocks between control nodes. Until then the control node is one process, and its faults are those above.

## Alternatives considered

- **Jepsen itself.** The reference tool, with Knossos and Elle as checkers, and the most credible result to point to. It needs a Clojure project, five SSH-reachable LXC or Docker nodes plus a control node, and a FleetRing client on the JVM: either a gRPC client generated for Java, or a CLI process per operation, which is too slow for a meaningful rate. Its checkers would judge a history FleetRing already checks with FR-036, under a second definition of the guarantees that could drift from the first. The harness's history format is close to Jepsen's (invocations and completions with `ok`, `fail`, `info`), so a Jepsen run can be added later for an external review; this decision doesn't rule it out.
- **The simulation alone.** ADR-0020's harness is faster, deterministic, and runs on every pull request, and it stays the main line of defence. It can't reach real TCP, HTTP/2 timeouts, thread scheduling, `fsync`, process pauses, or wall-clock jumps, which is the whole point of this decision.
- **A userspace TCP proxy between nodes, in the style of Toxiproxy.** Rootless and portable to macOS. But every peer dials the one address a node advertises, so a proxy in front of a node can't tell which peer a connection comes from and can't cut one pair while keeping another; a partition into halves needs per-pair control. It also can't pause a process or move a clock.
- **Network namespaces and `ip netns` directly.** The same isolation as Docker without an image, but it needs root on the host for every operation and doesn't run on a developer's macOS machine at all, where Docker Desktop at least lets the image build and the containers start. Docker's bridge network gives each node its own address and network namespace with no host configuration.
- **Kubernetes chaos tools (Chaos Mesh, Litmus).** Capable, but they need a cluster, which a nightly job and a laptop don't have, and they schedule faults from their own controllers, outside the seeded schedule the history is judged against.
- **A fault-injection mode in the daemon** (a clock offset read from a file, hooks to drop messages). It would make faults precise, but it adds code to the daemon that exists only for tests and could be left on by mistake, and the daemon under test would no longer be the daemon shipped. `libfaketime` moves the clock from outside; `iptables` and signals do the rest.

## Consequences

- The roadmap's "fault-injection run on real processes" exists, and E9's "chaos on a real three-node fleet in CI" is covered by the nightly job.
- One more crate in the workspace. Its `harness` feature turns on `fleetringd/simulation`, so it is off by default: Cargo unifies features across the packages of one build, and a default-on feature would build and run the simulation suite in the macOS, Windows, default-feature, and no-default-feature test jobs that ADR-0014 keeps it out of. Running the harness therefore needs `--features harness`. The 1.88 MSRV check excludes the crate, and the 1.89 check includes it.
- A nightly run proves no more than the faults and interleavings it happened to hit. A pass is evidence, not proof; the simulation's seed sweeps and the external review (roadmap E3) remain necessary.
- Real timing doesn't replay. A violation found at night reruns with the same schedule but may not recur; its history, schedule, and logs in the run directory are what the investigation starts from, and a simulation test that reproduces it is the fix's regression test.
- Disk faults (lost `fsync`s, torn pages) are still untested, as in the simulation (ADR-0020's limits). A fault-injecting filesystem (FUSE, or `dm-flakey`) can be a later decision.
- The checks a real run applies are the simulation's, by construction. A new invariant added to `sim::history` applies to both.
