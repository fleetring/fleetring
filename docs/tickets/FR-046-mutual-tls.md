# FR-046: Mutual TLS between nodes and clients, with a built-in certificate authority

## Context

Every gRPC connection in `fleetringd` is plaintext, and a node is whoever says it is in `Join`. ADR-0025 decides that every connection is TLS 1.3 through `rustls`, that nodes and clients present certificates issued by a cluster authority, and that a node's certificate names its node ID as a URI subject alternative name, `fleetring://<cluster>/node/<id>`, so the ID a node claims in `Join` and `Heartbeat` is checked against its certificate. CockroachDB's `cockroach cert` is the model for the operator experience: one command creates the authority, one issues each node's certificate, one issues a client's. etcd and rqlite reach the same shape with external tooling. The daemon only ever needs a certificate, its key, and the trusted authority's certificate, so certificates from Vault, cert-manager, or SPIRE work unchanged.

## Scope

- **`fleetringd cert init --cluster <name>`** creates the authority: an Ed25519 key and a self-signed certificate in a directory the operator chooses; the key never goes to a node. **`cert node <id> --hosts <ip-or-dns>,…`** issues a node certificate with the node URI SAN and the hosts; **`cert client <principal>`** issues a client certificate with the principal URI SAN. Lifetimes default to 30 days for nodes and 7 for clients, settable. Use `rcgen` for issuance and `rustls` with `tokio-rustls` through tonic's `tls-ring` or `tls-aws-lc-rs` feature; check `deny.toml`.
- **Configuration:** a `[tls]` section with `ca`, `cert`, and `key` paths; the daemon refuses to start without them unless `--insecure-plaintext` is given, which logs a warning on every start and exists for the simulation harness and local experiments only. The CLI takes `--ca`, `--cert`, `--key` (and reads `FLEETRING_TLS_DIR`), and a client certificate names the principal the CLI acts as.
- **Verification both ways:** servers require a client certificate chaining to the authority; clients verify the server's certificate against the authority and its hosts. The membership service rejects a `Join`, `Heartbeat`, `Leave`, or `Drain` whose node ID differs from the certificate's URI SAN with `PERMISSION_DENIED`. Node-to-node data calls (replication, promotion, snapshots) accept only node certificates.
- **Reload without restart:** certificate, key, and authority files are re-read when they change (a watcher, or a check on each new connection, bounded to once a second); new connections use the new material, established connections keep theirs. Two authority certificates may be trusted at once so a rotation can overlap.
- **Principal extraction** as a request extension, so FR-047 can authorize on it: node ID for node certificates, principal name for client certificates, nothing for plaintext.
- **Tests:** a cluster over real TCP with issued certificates; a node with a certificate for another ID is refused on join and on heartbeat; a client without a certificate is refused; a rotated node certificate is picked up by the next connection while an open replication stream continues; an expired certificate is refused. The simulation harness runs under TLS with a generated authority so turmoil covers the same code paths.
- **Not in scope:** tokens and scopes (FR-047), the threat model and signed releases (FR-048), revocation.

## Definition of done

- [x] A cluster started with `cert init`, three `cert node` certificates, and a `cert client` certificate runs the README walkthrough end to end with no plaintext listener, and a plaintext client is refused.
- [x] A node presenting a certificate for a different ID cannot join, heartbeat, or replicate, and the refusal names the mismatch in the server log without printing key material.
- [x] Certificate rotation needs no restart, and the test proves an in-flight replication stream survives it.
- [x] The fixed-seed simulation runs under TLS and stays under its time budget; the ARM, macOS, and Windows jobs pass, including the s390x and wasm emulation jobs where the daemon is built.
- [x] `deploy/fleetringd.toml`, the daemon README, and `docs/review.md` describe the `[tls]` section, the `cert` commands, and the plaintext escape hatch.

## Progress

- 2026-11-02: Done. The fixed-seed simulation passes under TLS, and PR #30 was green on all 17 CI jobs, including ARM, macOS, Windows, s390x, and wasm.
  - **Dependencies:** `rustls` 0.23 (`ring`, `std`; TLS 1.3 only), `tokio-rustls` 0.26, `rcgen` 0.14 (`ring`, `pem`) for issuance, `rustls-pki-types` for PEM loading, `x509-parser` 0.18 to read the URI subject alternative name, and `time` for certificate dates. tonic stays without its TLS feature: its server TLS takes one fixed configuration and offers no custom client verifier, and reload needs the handshake under our control. `ring` is the one crate with C in its build, through `cc`; no OpenSSL, no bindgen. Every licence in the closure is in `deny.toml`'s list (`ring` is `Apache-2.0 AND ISC`).
  - **`fleetringd::tls`:** `Authority` (create, load from `ca.crt` and `ca.key`, issue node and client certificates: Ed25519, URI SANs `fleetring://<cluster>/node/<id>` and `fleetring://<cluster>/principal/<name>`, node certificates also carry the hosts as IP or DNS SANs; serial numbers are hashed from the subject and validity so equally issued certificates are the same size, which keeps the simulation's traces deterministic). `Issued` and `Authority::write` write files with `create_new`, so nothing is overwritten, and keys with mode 0600. `Identity` holds the rustls server and client configurations behind an `ArcSwap`; when loaded from files it re-checks their modification time and size on a new connection, at most once per second, and rebuilds both configurations when they changed, keeping the old ones and warning if the new files don't load. The `ca` file is a bundle, so two authorities are trusted during a rotation. The server verifier is rustls's `WebPkiClientVerifier` over the trusted authorities, so a missing, untrusted, or expired client certificate fails the handshake; after it, the peer's certificate is parsed into a `Peer` and a certificate for another cluster is refused. `Security` is `Tls(Identity)` or `Plaintext`. `Debug` on every type that holds a key shows the subject and never the key; errors name files, never contents.
  - **Transport:** `Network` is now a struct of a link (TCP or turmoil) and a `Security`; every channel, the control client's and the peer pool's included, dials through one connector that opens the raw stream and runs the client handshake on it, verifying the server against the authorities and the host part of the address (an IP or DNS name). The server side accepts on `transport::Listener` (TCP or turmoil) and `transport::incoming` runs each handshake on its own task with a 10 s bound, so a silent peer holds nothing up, and hands tonic an `Accepted` whose `Connected::ConnectInfo` is the `Peer`; tonic then inserts it into every request's extensions, and `Peer::of(&request)` reads it (`Plaintext` when absent). The daemon loads `[tls]` at start, or takes the identity the environment's network already carries (the simulation), or refuses to start unless `insecure_plaintext` is set, in which case it warns.
  - **Checks:** the control service's `Join`, `Heartbeat`, `Leave`, `Drain`, `AcquireLease`, and `RenewLease` refuse a node certificate whose ID differs from the request's with `PERMISSION_DENIED`, logging both IDs; `RecordFenced` is exempt because its node is the fenced replica, reported by the candidate. The whole `Replication` service (`Replicate`, `Fence`, `Fetch`, `Promote`, `Snapshot`) refuses principals, and a replication stream whose primary metadata names another node than the certificate's is refused. Principals pass the membership calls for now; FR-047's scopes decide for them.
  - **Command line:** `fleetringd cert init --cluster <name> --dir <dir> [--ttl 3650d]`, `cert node <id> --hosts a,b --dir <dir> [--ttl 30d]`, `cert client <principal> --dir <dir> [--ttl 7d]`. Every subcommand takes `--ca`, `--cert`, `--key`, or reads `FLEETRING_TLS_DIR` (`ca.crt`, `client.crt`, `client.key`), or `--insecure-plaintext`; the daemon takes `--insecure-plaintext` as well.
  - **Simulation:** `Cluster::build` creates one authority per cluster and issues every host a node certificate for its name and address and every client a principal certificate, so every seed runs under TLS over turmoil's TCP; certificates span from the epoch for a century because rustls checks validity against the wall clock. The fixed-seed suite (`--cfg tokio_unstable`, 27 tests) took 211 s before and 156 s after on the development machine (the two runs had different background load; TLS added no measurable cost); no plaintext toggle was needed.
  - **Tests:** `tests/tls.rs` (a daemon without `[tls]` refuses to start unless plaintext is allowed; plaintext, foreign-authority, and expired clients fail at the transport; a node certificate for another ID can't join, heartbeat, leave, or drain, and can as itself; a principal can't fence while a node can; a certificate reissued by a second authority, with the authority bundle rotated, is served to a client trusting only the new authority without a restart while the open replication stream keeps acknowledging on both replicas at the same epoch). Every cluster fixture in `tests/` (`database`, `membership`, `control`, `changes`, `replication`, `daemon`'s binary tests) runs under the shared `tests/support` authority; the binary tests pass `FLEETRING_TLS_DIR`.
  - **Not done:** revocation, tokens and scopes (FR-047), the threat model (FR-048). `cert` issues only from the built-in authority's files; certificates from another authority are used, not issued, here.
