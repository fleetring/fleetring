# FR-047: Principals and scopes: tokens and prefix rules enforced at every RPC

## Context

With FR-046 every caller is identified: a node by its ID, a client by the principal in its certificate. Identity alone still lets any principal read and write every database. ADR-0025 decides that authorization is a set of scopes per principal, `<action>:<pattern>` with the actions `read`, `write`, `admin`, and `stream` over exact keys or prefixes ending in `*`, default deny, checked at the request boundary before any state is touched. It also decides a second credential: a signed, expiring bearer token that names the principal and carries its scopes, verified with the authority's public key with no lookup, for applications, the router, and the MCP server. Kafka's prefixed ACLs with default deny and NATS's signed user JWTs are the precedents; Turso's scoped tokens show the shape clients expect.

## Scope

- **Scopes:** `Scope { action, pattern }` parsed from `read:tenant:acme/*`, `admin:*`, `stream:ledger`; `write` implies `read`, `admin` implies both, `stream` is separate; `cluster` is the scope for key-less control operations. Reuse the matcher the change sinks use. A `Scopes::allows(action, key) -> bool`-shaped check with unit tests over the implication rules; keep the policy pure and in one module.
- **Where scopes come from:** a client certificate's principal maps to scopes through a `[[principal]]` list in the daemon configuration (`name`, `scopes`), identical on every node, validated at start. A token carries its own scopes in one claim. Node certificates get implicit full scope towards nodes and `cluster`.
- **Tokens:** Ed25519-signed JWTs with `iss` (the cluster), `sub` (the principal), `exp`, `nbf`, `kid`, and one claim `fleetring.scopes: ["…"]`. Issued by `fleetringd token issue --principal <name> --scope <scope>… --ttl <duration>` using the authority key (off-node), verified on nodes with the authority's public key; a second issuer key may be trusted for delegated tokens later. Sent as `authorization: Bearer <token>` metadata. A client certificate and a token on the same request must name the same principal.
- **Enforcement:** one interceptor per service that resolves the principal (from FR-046's extension or the token) and a per-RPC check on the request's key with the action the RPC needs; `PERMISSION_DENIED` with a message naming the action and key, never the scopes the caller has. `WatchLeases`, `NodeStatus`, `Verify`, and `Locate` need `read` on the key or `cluster`; `Execute` needs `write` (or `read` for a statement the adapter classifies as read-only); `CreateDatabase`, `DropDatabase`, `ChangeDurability`, `TransferLease` need `admin`; change sink positions in `NodeStatus` need `stream`. Node-to-node RPCs are never authorized by key.
- **Revocation:** a denylist of token IDs or key IDs published through an additive control command (`RevokeToken`), applied on nodes before verification; short lifetimes keep it small.
- **Audit:** one structured log line per denied request and, at debug, per allowed one, with principal, action, key, and RPC, never the credential.
- **Tests:** scope algebra; a principal with `read:tenant:*` can read `tenant:acme` and not write it or read `ledger`; `admin:*` can create and drop; an expired, a tampered, and a revoked token are refused; the CLI with a client certificate acts as that principal; the router-shaped case where a token is forwarded unchanged.
- **Not in scope:** a policy language, per-table permissions, delegated token issuance (Authem).

## Definition of done

- [x] Every data and control RPC is covered by an explicit scope requirement listed in the proto comments and in `docs/spec/` or the daemon README, and a test enumerates the RPCs against that table so a new RPC without a requirement fails the build.
- [x] A principal limited to `read:tenant:acme/*` can query that database and is refused on write, on another prefix, and on every admin and cluster operation, through both a client certificate and a token.
- [x] Token verification needs no network or control round trip, and a revoked token is refused on every node within one heartbeat interval of the revocation command.
- [x] `deploy/fleetringd.toml` documents `[[principal]]`, the README walkthrough issues a token for the application step, and `SECURITY.md` links the scope table.

## Progress

- 2026-11-02: Implemented on top of FR-046 and FR-044; in review as a draft PR.
  - **Scope policy (`fleetringd::auth`, pure):** `Action` (`read`, `write`, `admin`, `stream`) with `Action::covers` encoding the implications (write covers read, admin covers both, stream stands alone); `Scope` parsed from `<action>:<pattern>` (split at the first `:`, so keys may hold colons) or the bare word `cluster`, the pattern being the change sinks' `DatabaseMatcher`; `Scopes::allows(Target)` where `Target` is `Key(action, &key)` or `Cluster`; default deny. `admin:*` does not imply `cluster`, and `cluster` grants no key. Unit tests cover every implication, prefix versus exact patterns, parsing and printing, and JSON round trips.
  - **Revocation (`fleetring-control`, additive):** `Action::RevokeToken { revoked: Revoked::Token(TokenId) | Revoked::Key(KeyId), until }` puts an ID on `State::revocations` until `until` (the token's expiry, or `Timestamp::MAX` for a key); revoking again keeps the later time; one whose `until` has passed is rejected as `RevocationPassed`; ticks and revocations forget the entries the time has passed. The state serializes the list only when it isn't empty, so earlier snapshots and logs are unchanged. The replay generator now emits revocations and `the_generated_log_exercises_every_kind_of_change` requires them.
  - **Tokens (`fleetringd::auth::token`):** compact JWS, header `{"alg":"EdDSA","typ":"JWT","kid"}`, claims `iss`, `sub`, `jti`, `iat`, `nbf`, `exp`, and `fleetring.scopes`. `TokenSigner` (from the authority's Ed25519 PKCS#8 key) issues; `TokenVerifier` (the cluster name and one or more trusted public keys, so rotations overlap and a delegated issuer is one more key) verifies with no I/O, in the order size (8 KiB cap), header, trusted and unrevoked key, signature, then claims, issuer, validity window, and the token's own revocation. Only `EdDSA` is accepted, unknown header fields (`crit` included) and unknown claims are refused rather than ignored, `exp` is strict and `nbf` allows 30 s of clock skew. The key ID is the first 12 bytes of the SHA-256 of the raw public key, base64url. `BearerToken`'s `Debug` hides it and errors never quote it. Built on `ring` (already in the tree through rustls in FR-046) and `base64` (already in the tree through tonic) with `serde_json`, so no new crate enters the lock file; `jsonwebtoken` would have added its own crypto and PEM stacks for a format this small.
  - **Requirement table (`fleetringd::auth::policy`):** `RPCS` lists every RPC by its gRPC path with a `Requirement`: `Node` (node-to-node: `Join`, `Heartbeat`, `AcquireLease`, `RenewLease`, the promotion calls, all of `Replication`), `Cluster` (`WatchMembership`, `Leave`, `Drain`), `Key(action)` (`Locate` and `Query` read, `Execute` write, `CreateDatabase`, `DropDatabase`, `ChangeDurability`, `TransferLease`, and `Database.Create` admin), or `Listing(action)` (`ListDatabases`, `NodeStatus`, `WatchLeases`: each database shown only if the caller may read it, everything to `cluster`). `Caller::authorize` returns a `Denied` whose message names the method and the action and key needed, never the caller's scopes. `every_rpc_in_the_proto_has_exactly_one_requirement` parses `fleetring.proto` and fails on an RPC missing from the table or a table entry missing from the proto. FR-044's `Verify` will be one line, `rpc("/fleetring.v1.Database/Verify", Requirement::Key(Action::Read))` (or under whichever service it lands in), and the test fails until it is added.
  - **Revocation on the wire (additive):** `Control.RevokeToken(RevokeTokenRequest { Revocation }) returns RevokeTokenResponse { until_ms }` (requirement `cluster`) submits `Action::RevokeToken`; `HeartbeatResponse.revocations` (field 3) carries the whole list on every reply, and `Membership` replaces its shared `auth::Denylist` with it after each successful heartbeat, so a live data node refuses a revoked token within one heartbeat interval. `ControlClient::revoke_token` follows the leader. `tests/control.rs::a_revocation_reaches_data_nodes_through_their_heartbeats` revokes a token and a key over gRPC and watches a `Membership`'s denylist fill; a passed revocation answers `FAILED_PRECONDITION` and a bad ID `INVALID_ARGUMENT`. A node cut off from the control plane keeps the last list it had (revocations made meanwhile reach it with its next heartbeat); the list is sent whole because short token lifetimes keep it small.
  - **Request boundary (`fleetringd::auth::boundary`):** `AuthLayer`, a tower layer on the daemon's `Server`, wraps every service. Per request it looks the path up in `RPCS` (an unlisted path is refused), reads FR-046's `Peer` from the extensions and any `authorization: Bearer` header, resolves a `Caller` with `Authorizer::resolve`, enforces `node`, `cluster`, and listing requirements itself, and hands handlers an `Authorized` extension. Handlers parse the request's key and call `require_key` before touching state (`CreateDatabase`, `DropDatabase`, `ChangeDurability`, `Locate`, `TransferLease`, `Execute`, `Query`, `Create`, `Verify`); a handler reached without the layer fails closed. Listings filter: `ListDatabases` and `NodeStatus` databases by `read`, `NodeStatus` sinks by `stream`, and `WatchLeases` (snapshot and events) by `read`; everything for `cluster`. Refusals are `PERMISSION_DENIED` naming the method, action, and key; bad tokens `UNAUTHENTICATED`. Audit lines go to the `fleetringd::audit` target (warn for refusals, debug for allowed requests) with principal, credential (`certificate` or `token:<jti>`), action, key, and RPC, never the token.
  - **Callers:** a node certificate is `Caller::Node` (full scope); a principal certificate takes its scopes from `[[principal]]` (none if unlisted); a token replaces them with its own, and must name the certificate's principal unless that entry has `forward_tokens = true`; a token on a node's connection, or on plaintext, is refused; plaintext without a token is anonymous with full access, as `insecure_plaintext` always was. `Locate` and `Verify` need `read` on the key or `cluster` (`Requirement::KeyOrCluster`); `Execute` always needs `write`.
  - **Configuration:** `[[principal]]` (`name`, `scopes`, `forward_tokens`) in `Config::principals`, parsed with the scope grammar and checked for duplicates at start; `Principal` now deserializes.
  - **Tokens and TLS:** `Authority::token_signer` signs with the authority's key; `Identity::token_verifier` trusts every Ed25519 certificate in the `ca` bundle (reloaded with it), with the cluster name as issuer. The daemon judges token lifetimes by the environment's clock (`SimClock` under simulation) and checks the denylist from its own control state on a control node, or from the heartbeat-fed `Denylist` on a data-only node.
  - **Clients and CLI:** `transport::Credentials` (an interceptor that adds the bearer header; `Debug` hides it) on `Network::with_credentials`, applied by `ControlClient` and `data::Client`. `fleetringd token issue --principal --scope… --ttl --dir` (one hour by default, 30 days at most, a random 128-bit `jti`) prints the token and, on stderr, its ID and key; `fleetringd token revoke --token-id | --key-id [--ttl]`. Every command takes `--token` or `FLEETRING_TOKEN`. `watch-leases` now takes the TLS flags too (it dialed in plaintext before).
  - **Verify (FR-044):** one table line, `Database/Verify` with `KeyOrCluster(Read)`, and `require_key` in its handler.
  - **Docs:** `Scope:` comments on every RPC in the proto, with tests that hold them and the daemon README's table to `RPCS`; the README's "Principals and scopes" section and walkthrough (an `admin` `[[principal]]`, then a `notes-app` certificate and token for the application step); `deploy/fleetringd.toml`'s `[[principal]]` entries; `SECURITY.md` links the table. ADR-0026 (proposed) records the decisions ADR-0025 left open.
  - **Tests:** `tests/scopes.rs` runs a control daemon and a data-only daemon over TLS: a `read:tenant:acme/*` principal reads its database and is refused write, another prefix, create, drop, durability, drain, and membership, through its certificate, through a token on a scope-less certificate, and through a token a `forward_tokens` router carries; a token naming another principal than the certificate is refused; expired and tampered tokens are `UNAUTHENTICATED`; a revoked token is refused by the control node at once and by the data node within a few heartbeats, while another token from the same key keeps working. Unit tests cover the boundary (`auth::boundary`), config parsing (`tests/daemon.rs`), and the table. Existing tests now act as nodes through node certificates (`tests/control.rs`, `tests/membership.rs`), the test fixture grants `tester` full principal scopes, and the simulation's clients act as one principal, `workload`, issuing a node certificate for each node a workload impersonates.
  - **Command line:** `tests/scopes.rs::the_command_line_acts_as_its_certificate_or_its_token` runs the binary: `cert client` and `token issue` against the test authority, `db query` and `db exec` as a `read:tenant:acme/*` certificate and as a scope-less certificate with `FLEETRING_TOKEN`, then `token revoke` as the operator and a refused query.
- 2026-11-02: Security review fixes.
  - **Commit order:** `Verify` and `KeyOrCluster` now land with the RPC table, so every commit passes its own tests.
  - **Token lifetime:** `MAX_TOKEN_LIFETIME` (30 days, `nbf` to `exp`) is enforced by `TokenSigner::issue` (`IssueError::TooLong`) and by `TokenVerifier::verify` (`TokenError::Lifetime`) whatever minted the token. `Control.RevokeToken` keeps a token's entry at most 30 days and 30 seconds from the control node's clock (`ControlService::with_clock`); a key's entry may last forever. `token revoke` keeps a token's entry 30 days by default.
  - **Stale denylists:** `JoinResponse.revocations` (field 3) gives a starting node its list before its first heartbeat. `Denylist` remembers when it last arrived (`tokio::time`); a data node refuses tokens, not certificates, with `UNAVAILABLE` until the first list and whenever the last is more than three heartbeat intervals old (`DENYLIST_HEARTBEATS`). Unit tests with paused time cover both windows; `tests/scopes.rs` stops the control node and waits for the data node to refuse a token while still serving a certificate, and starts a data node that can't reach the control plane and checks it refuses tokens from the start.
  - **Streams:** `Authorized::guard` ends a `WatchLeases` or `WatchMembership` stream opened with a token, with `UNAUTHENTICATED`, once the token expires or is revoked (checked before each item and every `STREAM_RECHECK`, one second), and with `UNAVAILABLE` if the denylist goes stale. Unit tests cover expiry and revocation; `tests/scopes.rs` watches a stream end after a revocation.
  - **Boundary:** a TLS daemon refuses a request without the connection's `Peer` (`UNAUTHENTICATED`, audit error) instead of treating it as plaintext; token refusals are logged in `admit` with the principal, action, rpc, and reason.
  - **Listings:** `NodeStatus`'s floor is `read` or `stream` on some key (`Requirement::Listing(&[Read, Stream])`): databases are filtered by `read`, sinks by `stream`.
  - **Tests:** `tests/scopes.rs` adds a stream-only principal on `NodeStatus` (with a file sink on the data node), `WatchLeases` filtering, `Verify`, `TransferLease`, and `Database.Create` for a limited principal.
  - **ADR-0026:** stream termination and stale-denylist bounds, and that the engine adapter must confine a statement to the database it names (the `ATTACH` fix lands separately in `confine-statements`; its scope test follows once it merges).
  - **Not done:** delta-encoded denylists (the whole list rides every reply); the `ATTACH` test, which waits for `confine-statements`; per-table permissions and delegated issuance (out of scope).
